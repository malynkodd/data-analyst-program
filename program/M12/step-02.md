# M12.02. Называет две причины, по которым вывод может быть неверным

Умение: H2
Модуль: M12
Требуется до этого: `step-01.md` этого модуля — executive summary написан
Новые файлы, объявляемые этим шагом: `program\M12\work\caveats.md`
Время: 2–3 ч

## 1.1. Цель и связь с умением

Умение H2 части 1 blueprint: «Называет 2 причины, по которым его вывод
может быть неверным, и что нужно, чтобы их проверить». Критерий: «обе
причины конкретны (названы колонка/период/сегмент), ни одна не
формулировка вида «данных мало»».

## 1.2. Теория своими словами

**«Данных мало» — не причина, а отказ назвать причину.** Конкретная
формулировка называет, каких именно данных не хватает и что изменилось
бы, будь они доступны: не «нужно больше данных», а «нужны данные о цене
конкурентов для 60 партнёров — без них неизвестно, уйдут ли они при
повышении ставки».

**Причина должна указывать на проверку, а не только на сомнение.**
«Вывод может быть неверным, потому что...» — это половина требования;
вторая половина — «...и чтобы проверить, нужно...». Без второй половины
причина не действует ни на что, кроме общего впечатления
неуверенности.

**Справочник.**

- [Amplitude, «You're Measuring Daily Active Users Wrong»](https://amplitude.com/blog/measuring-active-users)
  — типовой разбор того, как верно посчитанное число даёт неверный
  вывод. Здесь это нужно с другой стороны: вы называете такие причины
  в собственном отчёте до того, как их назовут вам.
- [`git log`](https://git-scm.com/docs/git-log) — если ограничение
  вывода связано с тем, что определение метрики менялось, история
  коммитов это докажет (тот же приём, что в `M1/step-02.md`).

## 1.3. Разобранный пример

Вывод из `step-01.md`: «крупным партнёрам стоит поднять комиссию».

**Причина 1 (сегмент).** Вывод построен на 60 партнёрах одного
полугодия — нет данных о том, как партнёры реагировали на изменения
тарифа в прошлом (потому что тариф не менялся ни разу за этот период).
Проверка: поднять ставку для одной небольшой подгруппы крупных
партнёров экспериментально и измерить отток за квартал, прежде чем
менять правило для всех.

**Причина 2 (период).** Данные охватывают ровно 6 месяцев — если
крупные партнёры сезонны сильнее мелких (например, привязаны к
крупным контрактам, заключаемым раз в год), полугодовой срез мог
случайно застать их в удачный период, завышая впечатление о размере
оборота относительно типичного. Проверка: сравнить с тем же периодом
прошлого года, если такие данные существуют, или продлить наблюдение
до полного года перед выводом.

## 1.4. Задание

1. Для своего вывода из `step-01.md` назовите две причины, по которым
   он может быть неверным — каждая называет конкретную колонку, период
   или сегмент данных, ни одна не формулировка «мало данных» без
   уточнения.
2. Для каждой причины — что конкретно нужно сделать, чтобы её
   проверить (не «собрать больше данных» вообще, а какие именно данные
   и как их использовать).
3. Сохраните `work\caveats.md`.
4. Коммит:

   ```
   > git add program\M12\work\caveats.md
   > git commit -m "M12.02: две причины, по которым вывод может быть неверным"
   ```

## 1.5. Критерий готовности

Три проверки, каждая — «да/нет» без второго человека.

| Проверка | Эталон | Допуск |
|---|---|---|
| причин | 2 | меньше — шаг не сдан |
| конкретность | каждая называет колонку/период/сегмент по имени | формулировка «данных недостаточно» без уточнения, какие данные, — не засчитывается |
| проверка | у каждой причины — конкретное действие для проверки | «нужно больше данных» без указания, каких именно, — не засчитывается |

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 1 ошибку
этого шага, каждую с признаком, по которому её видно в своём результате.

## 1.6. Типичные ошибки

**Ошибка:** называете причину «данных недостаточно» или «выборка
маленькая» без уточнения, какая колонка/период/сегмент имеются в виду.
**Почему выглядит правильно:** формально это правда — любой вывод можно
дополнительно подтвердить бо́льшим объёмом данных, и фраза звучит как
типичная научная оговорка.
**Почему неправильно:** формулировка не проверяема и не действует ни
на что — неясно, какие именно данные собрать, чтобы вывод стал
надёжнее. Критерий блюпринта прямо запрещает эту формулировку как
образец непроверяемой оговорки.
**Как правильно:** называть конкретный пробел («нет данных о ценах
конкурентов», «период не включает пик сезона», «сегмент „крупные
партнёры" — всего 5 наблюдений из 60») и конкретное действие для его
закрытия.

## 1.7. Честная оценка времени

2–3 ч. Оценка проектная, не измерена (`research/self.md` пуст). Из чего
складывается: поиск двух непересекающихся причин — 1–1,5 ч; формулировка
проверки для каждой — 1–1,5 ч.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы порекомендовали изменение на основе анализа. Руководитель
спрашивает: „А если ты не прав?“ Что вы ответите, кроме „я уверен в
данных“?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Называет конкретное ограничение анализа (не общую фразу про
   неопределённость), связанное с реальным пробелом в данных.
2. Предлагает способ проверить вывод дешевле, чем полное внедрение —
   пилот, эксперимент на подгруппе, короткий тестовый период.
3. Отличает «вывод может быть неверным» от «я не уверен в расчётах» —
   первое про ограничения данных и метода, второе про качество работы;
   смешивать их подрывает доверие без необходимости.
4. Формулирует, что именно изменит вывод, если предположение окажется
   неверным — не просто признаёт риск, а называет его последствие.
