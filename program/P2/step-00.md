## Проект

P2 «Почему упала конверсия в первую оплату» — часть 5 blueprint. Второй
проект портфолио, синтетический: события пользовательского уровня
(регистрация → первая оплата → продления) не существуют в открытых
источниках, только агрегаты.

**Заказчик:** продуктовый менеджер сервиса подписки. **Вопрос:**
почему упала конверсия в первую оплату.

**Инструменты:** M3 (SQL, ядро проекта) + M10 (Git).

**Требуется до этого:** M3 целиком, M10.

## Датасет — синтетика с генератором, три встроенных дефекта

`program/P2/data/generate_p2.py`, `SEED = 20260821`. Период регистраций
2025-01-01…2025-12-31, наблюдение платежей до 2026-06-30.
`raw/signups.csv` (17434 строки) и `raw/payments.csv` (31021 строка:
первые оплаты, ежемесячные продления, дубли ретраев).

| Дефект | Число | Что проверяет |
|---|---|---|
| Дубли платежей от ретраев шлюза — тот же `user_id`/`amount`, разница секунды-минуты | 1752 строки из 31021 | критерий 5: находит дубли, не путает их с легитимными ежемесячными продлениями (интервал ~30 дней) |
| Задвоенные аккаунты — один email на двух `user_id` | 671 email из 16763, у 386 хотя бы один аккаунт платит | критерий 6: находит по email (не по `user_id`), считает влияние на результат отдельно |
| Три канала с меняющейся месяц к месяцу долей регистраций — доля `paid_social` (низкая конверсия) растёт с ≈30% до ≈68% за год | конверсия каждого канала растёт (organic 41.8%→56.3%, referral 57.9%→62.0%, paid_social 18.6%→20.8%), смешанная падает (37.1%→32.3%) | критерии 3–4: симпсоновский парадокс, найден реальным прогоном, не сконструирован на бумаге |

Дополнительно (не отдельный дефект, а измеримое следствие задержки
между регистрацией и оплатой, 1–45 дней): если считать конверсию
наивным отношением «оплаты этого календарного месяца / регистрации
этого же месяца», первый месяц выборки занижается искусственно
(цензурирование по краю окна наблюдения) — критерий 1–2, полное
объяснение в `reference_answers.md`.

Контрольная точка и все эталонные числа —
`program/P2/data/reference_answers.md`, посчитаны `reference_p2.py`
независимо от списков генератора.

## Acceptance criteria — публикуются до задания (решение 3)

Дословно из части 5 blueprint:

1. Определение конверсии зафиксировано письменно **до** первого запроса (проверяется по истории коммитов).
2. Обе трактовки (когорта регистрации / когорта оплаты) посчитаны, обе цифры в отчёте.
3. Явно назван парадокс: конверсия по каналам и в целом ведёт себя противоположно.
4. Указана причина парадокса — изменение долей каналов; доли приведены таблицей.
5. Дубли платежей найдены; их число названо; правило дедупликации записано одной строкой.
6. Двойные аккаунты найдены; их число названо; влияние на результат посчитано отдельно.
7. Каждая цифра из выводов воспроизводится приложенным SQL-запросом, результат сходится.
8. Использована ≥1 оконная функция и ≥1 CTE.
9. Retention-таблица по 12 когортам сходится с эталоном.
10. Репозиторий: ветка → PR → merge; в истории нет коммитов «fix»/«update»; есть `.gitignore`.
11. Executive summary ≤200 слов с ≥1 числом и ≥1 рекомендацией.
12. Названы 2 причины, по которым вывод может быть неверным.
13. ≥4 диаграммы с подписанными осями и единицами.
14. Человек не из data, прочитав только summary, за 60 секунд называет рекомендацию.

Текст задания для учащегося — `program/P2/project.md`.
