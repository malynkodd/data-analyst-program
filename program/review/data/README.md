# Эталоны возвратных точек

Точки `program/review/` (R1…R5, решение 49) не приносят новых данных: они
работают на тех же датасетах, что и модули. Здесь лежит только то, чего в
модулях нет, — **новые срезы уже существующих датасетов**.

## Зачем новые срезы, если задание возвратное

По умолчанию задание точки — «получите тот же результат заново», с
эталоном модуля. Для запроса, модели или пайплайна этого достаточно:
помнить ответ бесполезно, результат всё равно надо построить.

Но там, где результатом шага было **одно число**, дословный повтор
проверял бы память на это число, а не умение его получить. Критерий эти
два случая не различает. Для таких мест посчитаны срезы с теми же
правилами и другими числами.

Пример: `838` (строки с `product_id` вне справочника) напечатано в M2
девять раз — как задание возвратной точки не годится. R2 спрашивает,
сколько среди них **различных** `product_id`; этой величины в репозитории
нет нигде.

## Как считается

`build_review_reference.py`, прогон из корня репозитория:

```
> .venv\Scripts\python.exe program\review\data\build_review_reference.py
```

Ручной ввод чисел в тексты точек запрещён так же, как в модулях
(`program/M2/data/build_reference.py`, докстрока). Скрипт печатает всё, что
попадает в текст, и переписывает CSV рядом с собой.

Два источника, оба — состояние, в котором датасет остаётся после модуля:

- **M3** — `schema.sql` + `seed.sql` + `retention_seed.sql` в памяти
  (366 заказов, 252 клиента). Это состояние базы после `M3/step-07.md` и
  до конца модуля. Таблица `activity_log` из `step-08.md` на эти запросы
  не влияет.
- **M2** — `sales_extract_raw.csv` и `product_lookup.csv`, 20 000 строк.
  Функции очистки **импортируются** из `program/M2/data/build_reference.py`,
  а не переписываются здесь: изменится правило очистки в M2 — эталоны
  точек изменятся вместе с ним, а не разъедутся молча.

## Что отбраковано прогоном

Планировался шестой эталон — когортный retention с горизонтом M3
(`+3 month`), прямое продолжение ряда M1/M2 из `M3/step-07.md`. Прогон
2026-08-24 показал ноль по всем двенадцати когортам:
`generate_retention.py` возвращает клиента максимум через два месяца.
Эталон из одних нулей сходится и при неверном запросе — как проверка он
не работает, и в репозиторий не попал.

Заменён на `rv_a3_cohort_retention_m1_m2.csv` — два уже существующих
горизонта одним запросом. Форма новая (разбиение по горизонтам переезжает
из `WHERE` внутрь агрегата), и сходимость проверяется дважды: колонка
`retained_m1` обязана совпасть с `M3/data/a3_cohort_retention_m1.csv`
построчно, `retained_m2` — с `..._m2.csv`. На прогоне 2026-08-24 совпали
обе.
