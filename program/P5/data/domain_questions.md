# P5 — 5 доменных интервью-вопросов (критерий 11)

Формат — как в M11 (`step-04.md`): вопрос, эталон из 4 пунктов, ответ
защищается, если покрыты ≥3 из 4. Специфичны для истории P5 (смена
скоринга + конфаундер + горизонт наблюдения), не общие вопросы про
кредитный риск вообще.

## Вопрос 1

**«Риск-менеджер говорит: `fpd30` упал с 10.1% до 6.9% после смены
скоринга — победа. Вы согласны?»**

Эталон:
1. Называет число целиком, не только направление: 0.1009 (n=4230) до,
   0.0694 (n=216) после — 216 займов одной когорты, не сопоставимо по
   объёму с базой «до».
2. Отмечает, что fpd30 — быстрый, но не единственный сигнал: полный
   горизонт (`ever_90dpd`) для этой же когорты ещё не наступил (n=0
   зрелых после смены) — вывод «победа» преждевременный.
3. Указывает на конфаундер: доля `affiliate` (более рискованный канал)
   упала с этим же временем — часть улучшения может быть не про
   скоринг вообще.
4. Формулирует, что нужно для уверенного ответа: подождать, пока
   апрельская-майская когорта достигнет 180-дневной зрелости (примерно
   октябрь 2026 при CUTOFF 2026-07-01), и повторить сравнение на
   `ever_90dpd`.

## Вопрос 2

**«Почему нельзя просто досчитать `ever_90dpd` для займов, выданных
после 2026-04-01, раньше срока?»**

Эталон:
1. Объясняет: `ever_90dpd` — это «был ли хоть один платёж 90+ дней
   просрочен за весь срок займа» — по определению нельзя знать
   раньше, чем истечёт срок займа плюс 90 дней.
2. Показывает счёт: заём с `origination_date` = 2026-04-01, последний
   платёж due 2026-07-01, +90 дней = 2026-09-29 — позже CUTOFF
   (2026-07-01) почти на три месяца.
3. Называет это цензурированием (censoring), не пропуском данных:
   данные не потеряны, событие ещё не могло произойти к моменту среза.
4. Отвергает обходной путь «досчитать по текущему статусу» — займ,
   который на сегодня «в срок», ещё может уйти в просрочку позже;
   заём, который сегодня «30 дней просрочен», ещё может выйти на 90.
   Текущий статус не заменяет дозревшее наблюдение.

## Вопрос 3

**«В чём разница между `dpd_strict` и учётом пролонгации, и почему
эталон считает по `dpd_strict`?»**

Эталон:
1. Формулирует разницу: `dpd_strict` меряет просрочку от исходной даты
   по графику всегда; альтернатива мерила бы от `extended_due_date`,
   если пролонгация выдана — то есть просрочка «обнуляется» на 30 дней
   после пролонгации.
2. Объясняет, почему альтернатива опаснее для риск-отчётности: заём,
   которому продлевали срок трижды подряд, по альтернативному счёту
   мог бы никогда не показать высокую просрочку, хотя фактически
   заёмщик ни разу не заплатил в изначальный срок.
3. Признаёт легитимность второго определения для ДРУГОЙ цели —
   например, для расчёта, сколько реально получит кредитор по текущему
   действующему графику (после согласованных изменений) — но не для
   вопроса «стало ли меньше риска».
4. Указывает, что оба числа вычислимы из одних и тех же `raw`-файлов
   (`schedule.csv` неизменен, `payments.csv` хранит и факт, и флаг
   `extended`) — выбор трактовки, не ограничение данных.

## Вопрос 4

**«Почему `roll_rate_30_60` = 0.72, а доля займов 60+ dpd среди всех
зрелых = 0.18 — это не противоречие?»**

Эталон:
1. Называет оба числа с базами: 611/849 (roll rate, условно на «уже
   была 30+ dpd») против 611/3431 (безусловная доля среди всех зрелых).
2. Объясняет: числитель один и тот же (611 займов), разница —
   знаменатель: 849 (уже проблемные) против 3431 (весь зрелый портфель).
3. Формулирует, что означает каждое число по отдельности: 0.72 —
   «если заём уже плохой (30+ dpd), с вероятностью 72% станет ещё
   хуже (60+ dpd)»; 0.18 — «какая доля всего портфеля плохая (60+ dpd)».
4. Указывает практическое следствие: roll rate — метрика для решения
   «стоит ли раннее вмешательство по уже проблемным займам», доля
   среди всех зрелых — метрика для решения «насколько плохо качество
   портфеля целиком»; путать их — отвечать не на тот вопрос.

## Вопрос 5

**«Approval rate за весь период — 70.9%. Это говорит о качестве
скоринга?»**

Эталон:
1. Отмечает, что approval_rate посчитан за ВЕСЬ период (2025-01…
   2026-06) при ДВУХ разных порогах одобрения (580 до 2026-04-01, 620
   после) — единое число смешивает два разных режима.
2. Указывает, что approval_rate сам по себе не мера качества: высокий
   approval rate с высоким дефолтом — плохой скоринг; низкий approval
   rate с низким дефолтом — не обязательно хороший, если отсекает и
   платёжеспособных клиентов (это не измеряется в этом датасете —
   заявители, которым отказали, не наблюдаются дальше).
3. Связывает с конфаундером: снижение доли `affiliate` тоже двигает
   approval rate независимо от порога — состав заявителей изменился,
   не только правило.
4. Формулирует, что нужно для ответа на «качество скоринга»: approval
   rate нужно смотреть ВМЕСТЕ с default rate на сопоставимой базе — то
   есть с `ref_default_comparison.csv`, а не отдельно.
