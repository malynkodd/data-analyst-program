## 1.1. Цель и связь с умением

После шага у вас есть папка, за изменениями в которой следит Git: вы
можете инициализировать репозиторий, добавить файлы в индекс и
зафиксировать их коммитом с содержательным сообщением. Это ровно тот
фрагмент I1, который решение 14 переносит из M10 в M0 — не потому что
Git как система полностью изучается здесь (branch, PR, merge — в M10,
перед вторым проектом), а потому что привычка коммитить закладывается с
первого файла, а не после восьми месяцев программы. Без этого шага
`M1.2` не выполним буквально: его критерий готовности проверяется по
`git log`, а не по дате изменения файла.

## 1.2. Теория своими словами

Git — программа, которая запоминает состояние файлов в папке в виде
пронумерованной истории снимков (коммитов). Три команды этого шага:

1. **`git init`** — превращает обычную папку в репозиторий: создаёт
   скрытую служебную папку `.git`, где будет храниться история. Делается
   один раз на папку.
2. **`git add <файл>`** — помечает файл как «включить в следующий
   снимок». До этой команды Git видит файл, но не отслеживает его
   содержимое.
3. **`git commit -m "сообщение"`** — сохраняет снимок помеченных файлов
   с текстовым сообщением. Сообщение — не формальность. `git log`
   показывает только его, а не содержимое файлов построчно, и через
   месяц история — это ровно то, что вы в ней написали. «fix» и «update»
   не говорят ни о чём. Правило вводится здесь и работает дальше в `M1.2`
   и в M10: сообщение называет, что именно сделано, в нескольких словах.

Отдельно — `.gitignore`: текстовый файл в корне репозитория, где каждая
строка — шаблон файлов, которые Git обязан не замечать (не предлагать
добавлять, не отслеживать). Он держит вне истории временные файлы вроде
`*.tmp` и всё, что не должно уехать в публичный репозиторий.

**Ещё три команды — посмотреть и вернуть назад.** Первые три команды
только записывают. Записывать, не умея отменять, — худший из возможных
порядков: испортив файл на третий день, вы будете восстанавливать его по
памяти, имея на диске полную его историю.

4. **`git status`** — что сейчас изменено и что из этого помечено к
   коммиту. Читается сверху вниз: `Changes to be committed` — уже
   помечено через `add`; `Changes not staged for commit` — изменено, но
   не помечено; `Untracked files` — Git про файл ещё не знает.
5. **`git diff <файл>`** — что именно изменилось построчно с последнего
   коммита. Строки с `-` были, строки с `+` стали. Без аргумента
   показывает все изменённые непомеченные файлы. Если файл уже помечен
   через `add`, `git diff` покажет пусто — тогда `git diff --staged`.
6. **`git restore <файл>`** — вернуть файл к состоянию последнего
   коммита. **Изменения после этого не восстанавливаются никак** — они
   нигде не были сохранены. Поэтому порядок ровно такой: сначала
   `git diff` (посмотреть, что потеряете), потом `git restore`.

Правило, из которого следует всё остальное: **Git умеет вернуть только
то, что было закоммичено.** Файл, ни разу не попавший в коммит, командой
`git restore` не восстановить — его для Git не существует. Отсюда
практический вывод, а не лозунг: коммит стоит делать в момент, когда
состояние работает, а не когда работа закончена.

**Файловые операции в PowerShell.** Они не часть Git, но нужны с первого
дня и делаются иначе, чем в примерах из интернета (там обычно `cp`,
`mv`, `rm` — команды Unix, решение 13 их из программы исключает):

| Действие | PowerShell | Что важно |
|---|---|---|
| копировать | `Copy-Item diary.md diary_backup.md` | если файл-приёмник есть, перезапишет только с `-Force` |
| переместить/переименовать | `Move-Item a.md b.md` | переименование — частный случай перемещения |
| удалить | `Remove-Item diary_backup.md` | **мимо корзины**; отменить нечем, если файла нет в коммите |
| создать папку | `New-Item -ItemType Directory work` | `-Force` на папке безопасен, на файле — обрезает содержимое |

Опасны здесь двое: `Remove-Item` удаляет мимо корзины, и
`New-Item -Force` на существующем файле обнуляет его. Обе операции
безвредны ровно в одном случае — если файл уже в коммите.

## 1.3. Разобранный пример на сквозном датасете

Пример — не на `orders_log.csv` (Git отслеживает файлы папки, а не
данные конкретного csv), а на рабочей папке с текстовыми файлами, как в
`step-01.md`. Тот же принцип, отдельная демонстрационная папка:

```
$ git init
$ echo "# Project notes" > README.md
$ git status --short
?? README.md
```

`??` значит: Git видит файл, но он не отслеживается (не был ни разу
добавлен). Добавляем и коммитим:

```
$ git add README.md
$ git status --short
A  README.md
$ git commit -m "add README with project notes"
```

`A` (staged for Addition) — файл помечен, ждёт коммита. После коммита
дописываем в тот же файл и коммитим отдельно:

```
$ git commit -m "add note about second exercise"
$ git log --oneline
afc3d2d add note about second exercise
5fb64a7 add README with project notes
```

Два коммита, два разных, содержательных сообщения. Добавляем
`.gitignore` третьим коммитом:

```
$ git add .gitignore
$ git commit -m "add gitignore for temp files"
$ git log --oneline
fb3eb49 add gitignore for temp files
afc3d2d add note about second exercise
5fb64a7 add README with project notes
```

Три коммита в истории, самый новый — сверху. Короткие хеши (`fb3eb49` и
похожие) у вас на машине будут другими — они зависят от содержимого и
времени коммита, это ожидаемо и не является расхождением с эталоном:
здесь эталон — не сами хеши, а факт «≥2 коммита, ни один не назван
`fix`/`update`».

**Теперь то же самое наоборот — портим файл и возвращаем.** Допустим,
вы стёрли половину `README.md` и записали в него мусор:

```
$ git status --short
 M README.md
```

Пробел перед `M` — это не опечатка: первая позиция означает «помечено к
коммиту», вторая — «изменено на диске». ` M` читается как «изменено, но
не помечено». `MM` означало бы «часть изменений помечена, часть нет».

Смотрим, что именно потеряется, **до** того как отменять:

```
$ git diff README.md
diff --git a/README.md b/README.md
index 561db21..8bd6648 100644
--- a/README.md
+++ b/README.md
@@ -1,2 +1 @@
-# Project notes
-Second exercise: counting rows.
+asdf
```

Строка `index 561db21..8bd6648` — служебная, хеши на вашей машине будут
другими. Читать нужно последние четыре строки.

Две строки со знаком `-` — то, что было и уйдёт; строка с `+` — то, что
сейчас на диске. Возвращаем:

```
$ git restore README.md
$ git status --short
$ git log --oneline
fb3eb49 add gitignore for temp files
afc3d2d add note about second exercise
5fb64a7 add README with project notes
```

`git status --short` не напечатал ничего — рабочая папка совпадает с
последним коммитом. Отдельно: **`git log` не изменился, коммитов
по-прежнему три.** Отмена правки — не событие истории; в историю
попадает только то, что закоммичено. Это и отличает `restore` от отмены
уже сделанного коммита, которая как раз историю меняет; её разбирает
`M10/step-02.md`.

**Что было бы, если бы файл не был закоммичен.** `git restore` на
файле со статусом `??` отвечает:

```
error: pathspec 'notes.md' did not match any file(s) known to git
```

Не «не смог вернуть», а «не знаю такого файла». Возвращать не к чему —
состояния в истории не было.

**Копия, переименование, удаление:**

```
> Copy-Item diary.md diary_backup.md
> Move-Item diary_backup.md notes_backup.md
> Remove-Item notes_backup.md
> Test-Path notes_backup.md
False
```

`Remove-Item` не спросил подтверждения и не положил файл в корзину.
`notes_backup.md` не был закоммичен — значит, его больше нет нигде.

## 1.4. Задание

В папке, где лежит ваш `diary.md` из `step-01.md`:

1. `git init`.
2. Создайте файл `.gitignore` с содержимым `*.tmp` (одна строка) —
   добавьте и закоммитьте отдельным коммитом с содержательным сообщением.
3. Добавьте и закоммитьте `diary.md` отдельным коммитом.
4. Допишите в `diary.md` ещё одну строку и закоммитьте это изменение
   третьим, отдельным коммитом.
5. Проверьте: `git log --oneline` должен показать 3 коммита.
6. **Испортите и верните.** Откройте `diary.md`, сотрите весь текст,
   впишите вместо него одно слово `asdf`, сохраните. Затем, **не
   закрывая терминал и не создавая четвёртого коммита**:

   - `git status --short` — запишите, какие два символа стоят перед
     именем файла;
   - `git diff diary.md` — запишите, сколько строк со знаком `-` и
     сколько со знаком `+`;
   - `git restore diary.md` — верните файл;
   - `git status --short` ещё раз и `git log --oneline` ещё раз.

7. **Файл, которого нет в истории, вернуть нельзя.** Создайте
   `scratch.md` с любой строкой, **не** добавляйте его в Git и
   выполните `git restore scratch.md`. Запишите текст ошибки одной
   строкой и объясните её в одном предложении: почему Git не может
   вернуть этот файл.
8. **Три файловые операции.** Скопируйте `diary.md` в
   `diary_backup.md` (`Copy-Item`), переименуйте копию в
   `notes_backup.md` (`Move-Item`), удалите её (`Remove-Item`).
   Проверьте результат командой `Test-Path notes_backup.md`.
9. Убедитесь, что после заданий 6–8 в истории по-прежнему **ровно три
   коммита**: `git log --oneline`.

## 1.5. Критерий готовности

- `git log --oneline` показывает ≥3 коммитов (по одному на каждое из 3
  действий задания, не всё одним коммитом).
- Ни одно сообщение коммита не равно (без учёта регистра) `fix` или
  `update` и не начинается с этих слов.
- `.gitignore` существует в корне репозитория и отслеживается Git (есть
  в `git log --oneline -- .gitignore`, а не только на диске).
- `diary.md` появляется минимум в 2 разных коммитах (первичное добавление
  и правка).
- **После задания 6** `git status --short` не печатает ни одной строки,
  а `diary.md` снова содержит исходный текст: `Select-String asdf
  diary.md` даёт 0 совпадений.
- **Записанные наблюдения задания 6** совпадают с этими: статус до
  восстановления — ` M` (пробел и `M`, именно в таком порядке); в
  `git diff` строк со знаком `+` ровно 1.
- **После задания 7** записан текст ошибки, содержащий `did not match
  any file(s) known to git`, и объяснение называет причину «файл не был
  закоммичен», а не «команда не сработала».
- **После задания 8** `Test-Path notes_backup.md` печатает `False`, а
  `Test-Path diary.md` — `True`.
- **После задания 9** `git log --oneline` показывает **ровно 3**
  коммита: ни отмена правки, ни файловые операции коммитов не создают.
- Уложились в ≤1,5 ч.

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 4 ошибки
этого шага, каждую с признаком, по которому её видно в своём результате.

## 1.6. Типичные ошибки

**Ошибка:** делаете `git add .` и коммитите всю папку одним коммитом —
сразу и `.gitignore`, и `diary.md`, так быстрее.
**Почему выглядит правильно:** все нужные файлы в репозитории оказались.
**Почему неправильно:** критерий требует ≥3 отдельных коммитов, по одному
на действие задания, а `git log --oneline` покажет 1 вместо 3. Это тот же
класс ошибки, что разобран в `M1.2` про `definition.md` и `results.txt`,
сложенные в один коммит вместо двух.
**Как правильно:** отдельный коммит на каждое законченное действие. Один
коммит на всё технически возможен — и бесполезен, когда через неделю
понадобится откатить только одно из трёх.

**Ошибка:** называете коммит «fix diary» или «update readme» — рассуждая,
что запрещено голое «fix», а «fix» внутри фразы уже не считается.
**Почему выглядит правильно:** сообщение длиной с обычное и вроде бы
говорит, что сделано.
**Почему неправильно:** запрет в критерии — на начало строки, в любом
регистре. «fix diary» попадает под него ровно так же, как «fix». Правило
одно для всей программы: то же в M1.2 и в M10.
**Как правильно:** называть само действие — «add README with project
notes», а не «fix readme».

**Ошибка:** создаёте `.gitignore` и на этом останавливаетесь — раз файл
лежит в папке репозитория, Git наверняка уже что-то с ним сделал.
**Почему выглядит правильно:** файл на диске есть, его видно.
**Почему неправильно:** не сделал. `git log --oneline -- .gitignore`
вернёт ноль коммитов: файл создан, но не добавлен и не зафиксирован, и
критерий «есть в истории» не выполнен.
**Как правильно:** создали файл — сразу `git add`, потом `git commit`.
Без этих двух команд Git о файле ничего не запомнил.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Посмотрите на историю коммитов проекта: `fix`, `fix2`,
`update`, `wip`, `final fix`. Что это говорит о том, как велась работа?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Сообщения не говорят, что именно изменилось — по истории нельзя
   понять содержание правок без открытия каждого коммита.
2. Это затрудняет откат к конкретному состоянию («откатиться до того,
   где ещё не было бага» — непонятно, какой из пяти коммитов это).
3. Вероятно, коммиты делались редко и большими кусками, а не по одному
   законченному действию — иначе сообщений было бы больше и они были бы
   разнообразнее.
4. Называет, как должно быть: сообщение описывает суть изменения одной
   фразой («add validation for empty input», а не «fix»).
