## Определения (решение 30)

- **ЄДРПОУ** — 8-значный код юридического лица. **РНОКПП** —
  10-значный код физического лица (в т.ч. ФОП) — другой реестр, не в
  `UO.zip` (решение 35: только юрлица). В контрактах Prozorro оба вида
  кодов лежат в одном поле `identifier.id` без разметки — различаются
  только длиной.
- **`edrpous_needed.txt`** — 449 уникальных значений `identifier.id` у
  покупателей и поставщиков из 300 тендеров + 500 контрактов (не
  361 — см. ниже: это ДО дедупликации по факту участия именно в
  контрактах; `reference_p4.py` считает 361 уникальный код именно
  среди контрагентов контрактов, подмножество из 449).
- **CPV 15** — «Продукти харчування, напої, тютюн» (официальное
  украинское название категории, не переводится — как в П3), тот же
  префикс, что П3.

в остатке пропорциональна его собственной доле» — само по себе
недоказанное этим датасетом предположение, которое нужно называть
вслух, а не молчать о нём.

## Критерий 1 — approval-независимый агрегат: тендеры vs контракты

```
тендеров CPV15 в снапшоте: 300, сумма UAH: 67 698 682.99
контрактов CPV15 в снапшоте: 500, сумма UAH: 100 889 609.46
```

**Это не «реально потратили на 49% больше плана» — это артефакт
выборки, не финансовый вывод.** Тендеры и контракты в этом снапшоте —
две **независимые** выборки живой ленты Prozorro (`fetch_prozorro.py`,
докстрока): каждая идёт своим сканированием с собственной целью (300 и
500 карточек) и своей глубиной по времени, не связаны построчно через
`tender_id`. Дальнейший количественный вывод о «перерасходе» этим
снапшотом не подтверждается — нужен построчный join по `tender_id`
внутри одной и той же выгрузки, не сравнение двух независимых сэмплов
(критерий 15 — не делать причинного утверждения без оговорки).

## Найденный дефект — не в описании blueprint

29 из 500 строк `contracts_food.csv` содержат буквальный символ
переноса строки внутри `buyer_name`/`supplier_name` (сама Prozorro API
отдаёт название с `\n` внутри) — CSV записан корректно (RFC 4180,
`csv.writer` экранирует), но наивный подсчёт строк по числу переносов
даёт 529 вместо настоящих 500 записей. Найдено прогоном, исправлено в
`fetch_prozorro.py` (счёт через `csv.reader`, не `sum(1 for _ in f)`).

## Второй найденный дефект — начало/конец периода курса были переставлены

`reference_p4.py` брал `usd[-1]`/`usd[0]` как начало/конец периода с
комментарием «файл по убыванию даты» — неверным: НБУ отдаёт
`usd_uah.csv` по **возрастанию** даты (первая строка — 01.08.2022,
последняя — 22.08.2026, проверено прямым просмотром файла). Из-за
этого «начало периода» печаталось как курс на конец, и наоборот.
Исправлено сортировкой по распарсенной дате (`datetime.strptime`)
вместо предположения о порядке строк файла — устойчиво к тому, как
именно источник вернёт строки. На средний курс и суммы, посчитанные
по нему, дефект не влиял (они не зависят от порядка строк).

## Период снапшота — не буквально «три года»

Вопрос заказчика — «за три года». Фактический охват `contracts_food.csv`
по датам подписания — **2025-02-17…2026-08-21** (≈18 месяцев), не три
года: выгрузка шла живой лентой по убыванию даты изменения с целью
«собрать 500 карточек CPV15», а не с целью «собрать всё за 3 года» —
цель достигнута (500 карточек) раньше, чем сканирование дошло на 3
года назад. Чтобы буквально закрыть трёхлетнее окно, нужен либо больший
`MAX_SCAN`, либо обход по `offset` от даты «3 года назад» вперёд, а не
«с конца, назад» — зафиксировано как ограничение снапшота, не скрыто.
