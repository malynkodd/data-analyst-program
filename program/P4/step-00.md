# P4.00. Декларация проекта (заказчик, датасет, критерии, предусловие)

Не шаг для учащегося — служебный файл, требуемый разделом 1.3 скилла
curriculum-design (применяется к модулям и проектам одинаково). Команд не
содержит.

## Проект

P4 «Три источника, один объект» — часть 5 blueprint. Четвёртый проект
портфолио, реальные данные: три независимых источника должны ответить
на один вопрос («сколько потрачено и кто десять крупнейших
получателей»), и данные между собой не сходятся — это не брак проекта,
а сама суть задачи.

**Заказчик:** аналитик отраслевой ассоциации / журналист-расследователь.
**Вопрос:** «Сколько на самом деле потрачено по категории (продукти
харчування, CPV 15) и кто десять крупнейших получателей».

**Инструменты:** M5 (Python) + M6 (двусторонняя сверка) + M7 (BigQuery).

**Требуется до этого:** M5, M6, M7 целиком.

## Датасет — реальные публичные данные, три источника

`program/P4/data/fetch_prozorro.py`, `fetch_edr.py`, `fetch_nbu.py`.
Выгружено 2026-08-22. Prozorro и НБУ — агентом напрямую (решение 36:
`robots.txt` не блокирует); ЄДР (`UO.zip`, `data.gov.ua`) — автором
вручную (решение 36: `robots.txt` `data.gov.ua` запрещает AI-краулерам),
файл лежит в `program/P4/data/raw/uo.zip`, sha256
`171a62ce8ed6e43018df28c7539d4c25801215599d3b314432c77e3b0fff7bad`.

| Файл | Что | Объём |
|---|---|---|
| `snapshot/tenders_food.csv` | Тендеры CPV 15 (ожидание) | 300 строк |
| `snapshot/contracts_food.csv` | Контракты CPV 15 (факт) | 500 строк |
| `snapshot/edr_lookup.csv` | Прицельная выборка из `UO.xml` (3,16 ГБ, windows-1251, ~2 млн записей) по 449 нужным ЄДРПОУ | 329 строк |
| `snapshot/usd_uah.csv` | Курс USD/UAH, 2022-08-01…2026-08-22 | 1483 строки |

**Структурный факт, определяющий весь проект.** 361 уникальный код
контрагентов (покупатель+поставщик) контрактов — 245 (67.9%) находятся
в реестре ЄДР юрлиц, 116 (32.1%) нет, и все 116 объяснены исчерпывающе
(0 необъяснённых): 111 — РНОКПП ФОП (структурно другой реестр, не
дефект), 3 — филиалы (свой ЄДРПОУ, не отдельная запись SUBJECT), 1 —
ошибка ввода в Prozorro (`identifier.id = "№ 397338"` при
`scheme: "UA-EDR"`), 1 — причина не установлена (вероятно тоже
структурное подразделение).

**Найдено прогоном, не в описании blueprint:**
- Данные Prozorro API по контрактам содержат буквальный перенос строки
  внутри `buyer_name`/`supplier_name` в 29 из 500 записей — CSV
  записан корректно (RFC 4180), наивный подсчёт строк по переносам даёт
  529 вместо 500.
- Тендеры и контракты в этом снапшоте — независимые выборки живой
  ленты (300 и 500 карточек, разная цель сканирования), не связаны
  1:1 через `tender_id` — сравнение агрегатное, не построчный join.
- Охват дат контрактов — 2025-02-17…2026-08-21 (≈18 месяцев), не
  буквально «три года»: сканирование остановилось на цели (500
  карточек), не дойдя на 3 года назад.

Контрольная точка и все вычисляемые числа —
`program/P4/data/reference_answers.md`, посчитаны `reference_p4.py`
независимо от скриптов выгрузки.

## Acceptance criteria — публикуются до задания (решение 3)

Дословно из части 5 blueprint:

1. Один запуск из чистого клона: `git clone && python run.py` даёт итоговый файл; ручных шагов 0.
2. В README указаны дата снапшота и sha256 каждого исходного файла; итоговый файл побайтово совпадает с эталоном на этом снапшоте.
3. Печатается отчёт по каждому join: строк на входе, сопоставлено, потеряно; арифметика сходится (`вход = сопоставлено + потеряно`), расхождение 0.
4. Для каждой потери названа причина из списка (регистр, кодировка, отсутствующий ключ, дубль, разная нарезка периода).
5. Сделана повторная выгрузка из источника; расхождение со снапшотом посчитано в строках и объяснено ≥1 конкретной причиной.
6. Периоды приведены к одной нарезке явно; выбранная нарезка названа и обоснована.
7. Решение по несопоставленному остатку сформулировано одной строкой и применено единообразно.
8. Посчитаны **обе** версии итога (с исключением остатка и с распределением); обе в отчёте.
9. Показано, как выбор меняет первую десятку получателей; названо, кто входит и выходит.
10. ≥5 тестов pytest зелёные, среди них ≥1 на пустой вход и ≥1 на деление на ноль.
11. Ни одного `errors='ignore'`, `try/except: pass` и `df.dropna()` без комментария почему.
12. Запрос к BigQuery партиционирован; объём сканирования до/после зафиксирован, снижение ≥5×.
13. Executive summary ≤200 слов с ≥1 числом и ≥1 рекомендацией.
14. Раздел «что было сломано» — ≥5 конкретных дефектов с решением.
15. Названы 2 причины, по которым вывод может быть неверным.

Текст задания для учащегося — `program/P4/project.md`.

## Отступление: BigQuery не прогнан

Как в M7 (`program/M7/step-00.md`) — у среды написания нет доступа к
консоли BigQuery. `program/P4/data/bigquery_p4.sql` проверен на
синтаксис написанием, не прогнан. Гарантия «снижение ≥5×» здесь — не
структурная (реальные контракты распределены по датам неравномерно, не
как у M7), а посчитанная по факту распределения снапшота: январь 2026
даёт 75 из 500 строк (15.0%) — кратность ≈6.7×, с запасом. Строка —
`DEFERRED.md`, раздел «Проверка BigQuery».
