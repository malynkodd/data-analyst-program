## Проект

P3 «Дашборд, который заменяет еженедельную рассылку» — часть 5
blueprint. Третий проект портфолио, **первый на реальных публичных
данных**. Инструменты — M4 (Power BI) + M12 (executive summary, защита).

**Заказчик:** коммерческий директор компании-поставщика. Сейчас
получает 6 писем в неделю от трёх менеджеров про тендеры в своей
категории; просит один экран.

**Требуется до этого:** M4 целиком (пять связей, шесть мер, гейт
пройден), M12.

## Снапшот — реальные данные, зафиксированы 2026-08-21

Два источника, оба прошли гейт `research/sources-gate.md` (§2–3):
Prozorro API (тендеры категории CPV 15, «Продукти харчування») и API
НБУ (курс всех валют, 2020–2026). Полная методология отбора, дефекты и
эталонные числа — `program/P3/data/reference_answers.md`. Кратко:

| Файл | Строк | sha256 (первые 12) |
|---|---|---|
| `snapshot/tenders_food.csv` | 487 | `71b860624eba` |
| `snapshot/exchange_rates.csv` | 109125 | `c1d023e6561a` |

**Снапшот коммитится в репозиторий**, не гитигнорится (в отличие от
P1/P2): оба источника — живые потоки без версионирования, а не
статичные файлы, которые можно скачать повторно и получить те же
байты. `program/P3/data/README.md` объясняет почему подробно.

**Три задокументированных дефекта источника** (часть 5 blueprint
требует ≥3 из списка):

1. Перенос строки внутри поля `procuring_entity_name` у одного
   замовника — ломает наивный построчный парсер CSV.
2. Курс НБУ на выходные — не пропуск, а **задвоенное** значение
   (тот же курс, что в последний рабочий день); 47.1% строк USD
   идентичны предыдущему дню.
3. Последний период (2026-08-17…21) неполон из-за задержки конвейера
   статусов тендеров, не из-за технической обрезки файла.

Дополнительно, не из официального списка дефектов, но требующее того
же решения: один заказчик (оборонное ведомство) даёт 86.6% суммы
периода A — включать ли как есть или считать выбросом, решает
учащийся и объясняет выбор.

## Acceptance criteria — публикуются до задания (решение 3)

Дословно из части 5 blueprint:

1. На экране ровно 5 метрик; для каждой в отчёте написано, какое решение она поддерживает.
2. Перечислены метрики, которые заказчик просил, но которые не попали, — с причиной по каждой.
3. Модель — «звезда»: связи 1:*, направление фильтрации однозначно; схема приложена скриншотом.
4. ≥6 мер DAX, среди них ≥1 с CALCULATE и фильтром и ≥1 time-intelligence (YTD или MoM).
5. Все значения на дашборде сходятся с контрольным SQL до второго знака; запросы приложены.
6. Дубли справочника найдены; правило схлопывания записано; число дублей названо.
7. Пропуски курса в выходные обработаны явно; способ назван.
8. Неполный период помечен на самом экране визуально, а не в сноске.
9. Подмена исходного файла на файл следующего периода + Refresh: 0 ошибок, 0 ручных правок.
10. В README указаны дата снапшота и sha256 каждого исходного файла.
11. Сделана повторная выгрузка из источника; расхождение со снапшотом посчитано в строках и объяснено ≥1 конкретной причиной.
12. У каждой диаграммы подписаны обе оси и указаны единицы.
13. Нет 3D, «пончиков» и двойных осей; время загрузки на холодном старте измерено и указано.
14. Названы 2 причины, по которым выводы дашборда могут вводить в заблуждение.

Текст задания для учащегося — `program/P3/project.md`.

## Отступление: Power BI на этих двух файлах не прогнан автором

Тот же структурный класс ограничения, что у M15 (`step-00.md`, «нет
доступа к Tableau Public»): механика связей, DAX и обновления источника
уже измерена гейтом M4 на **другом** датасете и не переизмерялась на
`tenders_food.csv`/`exchange_rates.csv`. Отличие от M15 в размере
риска: обе таблицы этого проекта плоские (одна строка — один тендер
или одна котировка), без составных ключей и без множественных связей к
одной колонке-кандидату — того класса задач, что дал M4 большую часть
дефектов гейта (R12, R19–R21, R25 и связанные). Первый реальный прогон
— `DEFERRED.md`, раздел «Проверка Power BI на реальных данных P3».
