## Датасет — почему свой, а не база M3

Проверены оба пути. Данные M3 (`m3.db`, перенесённая в PostgreSQL база
`m3`) для M4 не берутся по трём причинам, и первая из них
дисквалифицирующая.

1. **Схема M3 не содержит ни одного из трёх случаев, которых требует
   решение 22.** Ограничение C1 (раздел «Ограничение C1» решения 22)
   обязывает датасет M4 содержать составной ключ, две колонки-кандидата на
   одно измерение и таблицы без совпадающих имён колонок — иначе задание
   «создай связь» проверяет способность не мешать Power BI. В пяти
   таблицах M3 составного ключа нет; все внешние ключи названы одинаково с
   обеих сторон (`customer_id`, `order_id`, `product_id`); двух дат в одной
   таблице фактов нет. Дописать это в M3 нельзя: `step-00.md` M3 прямо
   запрещает менять существующие определения — на них стоят числа
   `step-05.md`.
2. **Гейтом измерен CSV-путь, а не PostgreSQL-путь.** Все находки P1, P2,
   P7, P8 и весь слой 0 решения 22 — про `Csv.Document`: кодировку,
   `QuoteStyle`, культуру в `Table.TransformColumnTypes`. Про коннектор к
   PostgreSQL гейт установил ровно одно: он есть в списке (P3). Ни
   подключение, ни типы, ни поведение при Refresh не измерялись. Писать
   шаги против неизмеренного — то же, что писать число не из прогона
   (решение 21).
3. **C2 требует подмены файла.** Переформулированный критерий C2 (решение
   22) состоит из четырёх условий, и второе с третьим — про файл
   следующего месяца с новой кириллицей. На прямом подключении к базе
   подменять нечего.

**Категория датасета — синтетика с генератором, и это отступление от
раздела 1.3 скилла**, который для модулей, ведущих к P3, требует реальных
данных со снапшотом. Отступление объявлено, а не умолчано: требования
решения 22 к датасету (три случая связей плюс новая кириллица в файле
следующего месяца) — это требования к содержимому, которых снапшот
реального источника не гарантирует, а эталон C1 обязан быть известен
точно. Реальные данные остаются там, где они и назначены частью 5
blueprint, — в самом проекте P3 (Prozorro API + API НБУ). Решение
записано отдельно (решение 25 `design/decisions.md`) со своими
альтернативами.

Домен — **fintech** (решение 21, п. 2): платёжный провайдер, эквайринг
украинских мерчантов. Узнаваемых учебных датасетов раздел 5 скилла
запрещает; этот сгенерирован под модуль и нигде больше не встречается.

**Генератор и контрольная точка.** `program/M4/data/generate_m4.py`,
`SEED = 20260731`, задан до первого обращения к генератору случайных
чисел. Данные не коммитятся (решение 22, «Что коммитится»): в git лежат
генератор, скрипт эталонов и сами эталоны. Скрипт печатает после
генерации число строк и sha256 каждого файла — учащийся сверяет их с
`data/reference_answers.md`, раздел «Контрольная точка», **до** начала
задач, а не после первого несошедшегося критерия. Два прогона подряд дали
побайтово одинаковые файлы (проверено сравнением вывода).

## Схема — 5 таблиц, зафиксирована на весь модуль

Папка `program/M4/data/csv/`, пять файлов. Кодировка UTF-8 **без BOM**,
перевод строки CRLF — та же конфигурация, на которой прогонялся гейт.

| Таблица | Строк | Колонки | Роль |
|---|---|---|---|
| `transactions` | 6582 | `tx_id`, `merchant_id`, `tx_date`, `settled_date`, `mcc`, `status`, `amount_uah`, `period_ym` | Факт: операции эквайринга, 2025-01-01 … 2026-06-30 |
| `merchants` | 24 | `merchant_id`, `merchant_name`, `city`, `address` | Измерение: мерчант, город, адрес |
| `mcc_categories` | 6 | `code`, `category_name` | Измерение: категория торговой точки по коду MCC |
| `merchant_plan` | 432 | `merchant_ref`, `period_ym`, `plan_code`, `commission_pct` | Тариф мерчанта по месяцам: 24 мерчанта × 18 месяцев |
| `calendar` | 553 | `date_key`, `year`, `month_no`, `month_uk` | Измерение дат для time-intelligence: 2025-01-01 … 2026-07-07, на неделю длиннее периода операций — дата расчёта переступает его границу |

Контрольные суммы (посчитаны `reference_m4.py`, не на глаз):

- `SUM(amount_uah)` по всем 6582 операциям = **10236902.82**.
- То же по `status = 'settled'` (5609 операций) = **8703122.77**.
- Статусы: `settled` 5609, `declined` 709, `refunded` 264.
- Комиссия по составному ключу (мерчант, период) = **169676.11**.

Будущие шаги модуля могут добавлять колонки и таблицы, но не менять
существующие: на числах выше стоят критерии `step-02.md`–`step-04.md`.
Новые колонки объявляются в шапке того шага, который их вводит.

### Три случая связей, которых требует решение 22

Датасет спроектирован под ограничение C1, а не подобран задним числом.
Каждый случай закрыт названным местом схемы:

| Случай (решение 22) | Где в схеме | Почему автоопределение здесь не помогает |
|---|---|---|
| Составной ключ | `merchant_plan` (`merchant_ref` + `period_ym`) → `transactions` | Связь Power BI соединяет **одну** колонку с одной ([Model relationships](https://learn.microsoft.com/en-us/power-bi/transform-model/desktop-relationships-understand): «A model relationship relates one column in a table to one column in a different table»). Ключ приходится собирать в Power Query. По одному `merchant_ref` связь невозможна: 10 мерчантов из 24 меняли тариф внутри периода, значения не уникальны ни с одной стороны |
| Две колонки-кандидата | `transactions[tx_date]` и `transactions[settled_date]` → `calendar[date_key]` | Активной может быть только одна: «There can only be one active filter propagation path between two model tables». У 531 операции из 6582 месяц расчёта не совпал с месяцем операции — выбор меняет месячные суммы |
| Имена колонок не совпадают | `transactions[mcc]` → `mcc_categories[code]` | Автоопределение смотрит на имена колонок и без высокой уверенности связь не создаёт ([Create and manage relationships](https://learn.microsoft.com/en-us/power-bi/transform-model/desktop-create-and-manage-relationships)) |

Четвёртая связь — `merchants[merchant_id]` → `transactions[merchant_id]` —
единственная, где имена совпадают и одна сторона уникальна: та же
конфигурация, в которой гейт измерил автосоздание связи (2.5). Она в
модуле роль контраста, а не задания.

Требование решения 22 «в `relationships.tmdl` больше одной связи, и хотя
бы одна — не `AutoDetected_*`» датасет выполняет с запасом: связей пять,
не автоматических из них четыре.

### Что датасет обязан обеспечить для C2 (шаги не написаны)

Папка `program/M4/data/csv_next/` — тот же набор, продлённый по
2026-07-31. Проверено построчно: каждая строка базовой папки входит в неё

### Что в датасете сделано ради проверяемости критериев

- **Ни одно текстовое значение не начинается с `=`, `@`, `+` или `-`**
  (проверено `reference_m4.py`: 0 из всех названий, городов, категорий и
  тарифов). Решение 22 оставило ведущий апостроф в экспорте
  **обязательством, а не фактом**: `compare_csv.py` его не снимает. Из
  двух способов закрыть обязательство («датасет строится так, что таких
  значений нет» либо правка скрипта) выбран первый, и это записано здесь,
  а не оставлено на догадку.
- **Два названия мерчантов содержат запятую внутри значения**
  (`Мережа АЗС «Крок», ТОВ`; `Аптека «Добродія», ФОП`), **два адреса —
  перевод строки внутри значения**. Первое проверяет разбор кавычек,
  второе — параметр `QuoteStyle`. Разделение существенно: по
  документации [Csv.Document](https://learn.microsoft.com/en-us/powerquery-m/csv-document)
  `QuoteStyle` управляет **переводами строки** внутри значения, а
  значимость кавычек после разделителя — параметром `CsvStyle`, у
  которого умолчание `QuoteAfterDelimiter` с запятой справляется.
  Поэтому в `merchants.csv` 24 строки данных и 27 физических строк в
  файле: разница в 3 и есть то, что теряется при неверном `QuoteStyle`.
- **Суммы записаны с двумя знаками, тариф — с тремя.** Эталон считается
  `Decimal` с `ROUND_HALF_UP`, и `reference_m4.py` отдельно проверяет, что
  ни одно эталонное значение не лежит ближе 1e-6 к границе округления.
  Иначе Power BI и Python могли бы разойтись в последнем знаке из-за
  разных правил округления середины, а не из-за ошибки в мере.
- **Ни один экспортируемый визуал не приближается к потолку в 30 000
  строк**: 6, 18 и 3 строки. Требование решения 22 «не ближе чем вдвое»
  выполнено с запасом в три порядка.

## Что в этом модуле не проверено прогоном

Записано отдельно, чтобы не выдавать документацию за измерение.

**Измерено прогоном** (`research/tools-gate.md`, Часть 2): детерминированность
экспорта, кодировка и разделители экспортируемого CSV, отсутствие строки
«Applied filters», порядок строк, автосоздание связи при совпадающих
именах, содержимое `relationships.tmdl` и правило «TMDL пишет только
отклонения от умолчаний», состав `.pbip`, машинная читаемость
`visualType`/`queryRef`/`sortDefinition` из PBIR, поведение культуры
`"ru"` и кодировки при импорте CSV.

**Взято из документации, прогоном не подтверждено** — каждое место в
шагах помечено ссылкой:

- связь соединяет одну колонку с одной, составной ключ собирается заранее;
- активной между двумя таблицами может быть одна связь, остальные
  неактивны и включаются только через `USERELATIONSHIP`;
- `QuoteStyle.None` рвёт значение по переводу строки внутри кавычек;
- поведение `TOTALYTD`.

**Обязательный прогон до написания шагов C2** — решение 26. Шаги 01–04
проходятся руками в Power BI Desktop, `check_pbip.py --step 03` и `--step
04` запускаются на настоящем `.pbip`, экспорт трёх визуалов сверяется с
`ref_*.csv` через `compare_csv.py`, результат пишется в
`research/tools-gate.md`, Часть 3. Пять пунктов, которые прогон обязан
закрыть, перечислены в решении 26.

Порядок здесь существенный, и он не «до сдачи модуля», а **до первого
шага C2**: первые два утверждения из списка выше — фундамент `step-03.md`
(составной ключ, вторая колонка-кандидат), четвёртое — фундамент меры
`Settled YTD`. C2 строится поверх модели шагов 01–04; если утверждение не
подтвердится, правится схема датасета и критерий шага 03, а написанный
раньше C2 переписывается целиком.

До прогона числа шагов — эталон `reference_m4.py`, то есть одна из двух
независимых реализаций формулы, а не две сошедшиеся (правило двойного
авторства формулы, раздел 1.3 скилла).
