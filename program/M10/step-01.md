# M10.01. Заводит практический репозиторий и работает в ветке

Умение: I1
Модуль: M10
Требуется до этого: `M0/step-03.md` — `git init`/`add`/`commit`. Аккаунт
на GitHub и доступ на `push` заводятся здесь, заданием 0: в M0 их нет — там
Git работает только локально
Новые файлы, объявляемые этим шагом: отдельный репозиторий вне
`data-analyst-program` (путь и название — на ваше усмотрение,
далее в тексте — `<practice-repo>`)
Время: 3.5–5 ч

## 1.1. Цель и связь с умением

Умение I1 части 1 blueprint, первая половина: «Ветка → коммиты...». После
шага есть отдельный GitHub-репозиторий, в нём — минимум одна feature-ветка
с несколькими коммитами, ни один коммит не назван «fix» или «update».

## 1.2. Теория своими словами

**GitHub Flow — одна ветка на одну задачу, `main` всегда рабочий.**
Полный Gitflow (`develop`, `release`, `hotfix` ветки) — для команд с
циклом релизов; для одного человека и analytics/BI-задач это лишний вес
— то же самое отмечено в источнике [М, «Мифы (б)»], откуда взято
обоснование модуля. GitHub Flow короче: от `main` ответвляется
`feature/<что делаем>`, туда идут коммиты, в конце — Pull Request
обратно в `main`.

**Сообщение коммита — что и зачем, а не «fix».**
[About commits](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/about-commits)
называет сообщение коммита «a description of the changes»: не отметку о
факте («что-то поменялось»), а объяснение, какое именно. «fix» отвечает
на вопрос «коммит менял код?» — а ответ на него всегда «да». Ни на один
содержательный вопрос это слово не отвечает.

**Аккаунт и доступ на запись — не то же самое, что установленный Git.**
M0 ставит Git и учит трём локальным командам; ни одна из них наружу не
ходит, и аккаунта не требует. `git push` — первая команда программы,
которой нужны две вещи сразу: аккаунт на GitHub и способ доказать, что
вы его владелец. Пароль от аккаунта для этого не годится: аутентификация
по паролю в Git по HTTPS на GitHub не работает — вместо пароля
подставляется **токен**.

Двух способов достаточно, и выбирается один:

- **Git Credential Manager.** Ставится вместе с Git for Windows и
  включён по умолчанию. При первом `git push` открывает окно браузера,
  вы входите в GitHub обычным образом, дальше он хранит и подставляет
  токен сам. Ничего дописывать руками не нужно.
- **Personal access token вручную.** Токен создаётся в настройках
  аккаунта и подставляется вместо пароля при первом `push`. Нужен, если
  окно браузера не открывается (сервер без графики, консоль по SSH).
  Тип токена — `fine-grained` (доступ выдаётся конкретному репозиторию)
  или `classic` с областью `repo`;
  [документация GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
  даёт пошагово оба и прямо говорит про classic: «To use your token to
  access repositories from the command line, select **repo**».

Токен — пароль и хранится как пароль: не в коммите, не в тексте шага,
не в `README`. Запушенный токен GitHub отзывает сам, но до этого им
успевают воспользоваться.

**Лимит размера файла на GitHub — не редакторская рекомендация.**
[About large files on GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github):
«If you attempt to add or update a file that is larger than 50 MiB, you
will receive a warning from Git» — и «GitHub blocks files larger than
100 MiB». Между 50 и 100 МиБ пуш ещё проходит, но с предупреждением;
критерий I1 («файлов >50 МБ нет») ставит планку на первом пороге, а не
на блокирующем — практика, а не минимально необходимое.

## 1.3. Разобранный пример (демонстрация на изолированном тестовом
репозитории, не на `data-analyst-program`)

Прогон на машине автора 2026-08-20, отдельный тестовый репозиторий, не
входящий в портфолио.

```
> git init
> git branch -M main
> git add README.md
> git commit -m "init"
> git checkout -b feature/add-notes
> echo "..." > notes.txt
> git add notes.txt
> git commit -m "add project notes file"
```

```
> git log --oneline --all --graph
* 823b74c add project notes file
* b3aeefb init
```

**Проверка сообщений коммитов** — точное совпадение с «fix» или
«update» без учёта регистра, не подстрока (коммит «fix typo in README»
— не нарушение, «fix» само по себе — нарушение). Команда — PowerShell
`Select-String`, не `grep` (на Windows его нет по умолчанию — решение 13
`design/decisions.md`):

```
> git log --format=%s | Select-String -Pattern '^(fix|update)$'
```

На примере с нарушением — коммит `git commit -m "fix"`:

```
fix
```

Строка найдена — критерий не пройден. На примере из 1.3 с сообщением
«add project notes file» команда не выводит ничего — `Select-String` не
печатает строку, если совпадений нет, в отличие от ошибки.

## 1.4. Задание

0. **Аккаунт и доступ на запись** — если их ещё нет.

   1. Заведите аккаунт на [github.com](https://github.com) и
      подтвердите адрес почты — без подтверждения репозиторий не
      создаётся
      ([инструкция GitHub](https://docs.github.com/en/get-started/start-your-journey/creating-an-account-on-github)).
   2. Свяжите локальный Git с именем и почтой аккаунта:

      ```
      > git config --global user.name "<ваше имя>"
      > git config --global user.email "<почта аккаунта GitHub>"
      ```

   3. Проверьте, какой помощник хранит учётные данные:

      ```
      > git config --get credential.helper
      ```

      Печатает `manager` — Git Credential Manager на месте, при первом
      `push` он сам откроет окно входа, и больше делать ничего не надо.
      Печатает пустую строку — идите путём с токеном из 1.2: создайте
      `fine-grained`-токен на свой будущий репозиторий (или `classic` с
      областью `repo`) и подставьте его вместо пароля при первом
      `push`.

1. Создайте новый репозиторий на GitHub (веб-интерфейс: New repository)
   — публичный или приватный, не имеет значения для этого шага.
   Склонируйте локально.
2. Добавьте `.gitignore`, подходящий вашей задаче (для Python-проекта —
   как минимум `.venv/`, `__pycache__/`, `*.pyc`, по образцу корневого
   `.gitignore` этой программы).
3. Первый коммит — в `main` напрямую: инициализация, `README.md`,
   `.gitignore`.
4. Заведите ветку `feature/<короткое-имя-задачи>` и сделайте в ней
   минимум 3 коммита с содержательными сообщениями — что изменилось и
   зачем, не «fix»/«update»/«wip».
5. Проверьте историю веток:

   ```
   > git log --oneline --all --graph
   > git log --format=%s | Select-String -Pattern '^(fix|update)$'
   ```

   Вторая команда обязана не найти ничего.
6. Запушьте ветку:

   ```
   > git push -u origin feature/<короткое-имя-задачи>
   ```

## 1.5. Критерий готовности

Пять проверок, каждая — «да/нет» без второго человека.

| Проверка | Эталон | Допуск |
|---|---|---|
| `git config --get user.email` | печатает почту вашего аккаунта GitHub, не пустую строку | пустая строка — коммиты уйдут без автора, привязанного к аккаунту, и на GitHub не встанут в вашу историю |
| `git ls-remote origin` | печатает список ссылок и завершается с кодом 0 | ошибка аутентификации — доступ на запись не настроен, задание 0 не закрыто; дальше пушить нечем |
| `git log --format=%s \| Select-String -Pattern '^(fix\|update)$'` | пусто | любое совпадение — переписать сообщение (`git commit --amend` для последнего, `git rebase -i` для более раннего — с осторожностью, ветка ещё не в PR) |
| `.gitignore` существует в корне репозитория | файл на месте, непустой | пустой `.gitignore` — не считается: правило есть, применения нет |
| пуш ветки | `git push` завершился без предупреждения о размере файла | предупреждение о файле >50 МиБ — файл убрать из истории (`git rm --cached`) до пуша, не после |

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 2 ошибки
этого шага, каждую с признаком, по которому её видно в своём результате.
Своей ошибки среди них нет — идите наружу: поиск и вопрос ИИ
разрешены (`README.md`, раздел 4), но каждое такое обращение
пишется пометкой `[сторона] что искал` в `research/self.md`.

## 1.6. Типичные ошибки

Обе — не измерены прогоном на конкретном датасете (в этом модуле нет
данных), а взяты из задокументированного поведения git, проверенного на
изолированном тестовом репозитории (1.3). Это отступление от решения 28
(«гипотетическая ошибка не пишется вовсе»), и оно ограничено этим
шагом: ошибки конфликта слияния в `step-02.md`, 1.6 измерены прогоном —
там есть на чём мерить, потому что сценарий строит конфликт с
известными числами.

**Ошибка:** коммитите прямо в `main`, ветку заводите только для вида в
конце, одним коммитом «final version».
**Почему выглядит правильно:** GitHub такую ветку в Pull Request примет
без разговоров, слияние пройдёт без ошибок.
**Почему неправильно:** цель умения I1 — рабочая привычка (branch → PR →
merge), а не факт существования ветки в момент сдачи. Один коммит в
ветке неотличим от прямого коммита в `main` с точки зрения истории —
весь смысл маленьких промежуточных коммитов (можно откатить один шаг, не
весь день работы) теряется.
**Как правильно:** коммитить по мере того, как сделан осмысленный кусок
работы — несколько раз за сессию, не один раз в конце.

**Ошибка:** называете ветку `feature/fix` или `feature/update` — тот же
класс формулировки, что запрещён для коммитов, просто перенесённый в имя
ветки.
**Почему выглядит правильно:** правило про «fix»/«update» в 1.5 проверяет
только сообщения коммитов, имена веток его не касаются. Формально всё
чисто.
**Почему неправильно:** имя ветки — первое, что видно в списке веток и в
Pull Request; `feature/fix` не говорит ревьюеру (в данном случае — вам
самим через месяц) ничего о содержании задачи, тот же дефект
информативности, что и у коммита «fix», просто не пойманный
инструментом.
**Как правильно:** имя ветки — короткое существительное или
глагол+существительное, описывающее задачу: `feature/add-csv-export`, не
`feature/fix`.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Посмотрите на историю коммитов своего проекта. Как вы
поймёте, глядя только на список сообщений, не открывая diff, что делает
каждый коммит?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Формулирует правило самопроверки: сообщение должно быть понятно без
   контекста, которого нет у постороннего читателя — не «fix», а что
   именно исправлено.
2. Отличает «что» от «почему»: короткое сообщение называет изменение,
   более длинное тело коммита (после пустой строки) может объяснить
   причину, если она не очевидна из кода.
3. Признаёт, что вернуться и переписать сообщения задним числом дороже,
   чем написать сразу правильно — `git rebase -i` работает, но рискует
   сломать историю, если ветка уже кем-то склонирована.
4. Называет практический тест: если через месяц, не помня контекста,
   человек по одному сообщению может понять, что менялось, — сообщение
   годится.
