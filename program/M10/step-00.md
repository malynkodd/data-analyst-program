# M10.00. Декларация модуля (умения, разбивка, предусловие)

Не шаг для учащегося — служебный файл, требуемый разделом 1.3 скилла
curriculum-design. Команд не содержит (решение 20 `design/decisions.md`).

## Умения модуля и разбивка по шагам

Модуль M10 закрывает остаток **I1** — часть 2.1 blueprint: «Ветка →
коммиты → PR → merge на своём проекте... Топ-15 №15; 0.8% в вакансиях,
но [М, «Мифы (б)»] подтверждает ежедневную практику и рекомендует
облегчённый GitHub Flow для analytics/BI-задач, а не полный Gitflow».
`git init`/`add`/`commit` уже отработаны в `M0/step-03.md` (решение 14
`design/decisions.md`) — здесь только то, что осталось: ветка, PR,
слияние.

| Шаг | Умение | Что делает учащийся | Время |
|---|---|---|---|
| `step-01.md` | I1, часть 1 из 2 | Заводит отдельный практический репозиторий на GitHub, работает в feature-ветке, пишет коммиты по правилу | 3–4 ч |
| `step-02.md` | I1, часть 2 из 2 | Открывает Pull Request, проходит по чеклисту ревью самостоятельно, сливает через PR, разрешает конфликт слияния руками и отменяет свой коммит через `git revert` | 6–7 ч |

Инфраструктурного шага нет: GitHub-аккаунт и `git` уже есть с M0.

## Часовой бюджет

Построчная сумма двух шагов: 3–4 + 6–7 = **9–11 ч** — совпадает с вилкой
части 6.1 blueprint (9–11 ч) по обеим границам.

Вилка выросла с 7–9 ч контентным аудитом 2026-08-28 (решение 54):
`step-02.md` получил конфликт слияния и `git revert` — до этого модуль
учил работе в своей ветке своего репозитория, где ни то, ни другое не
случается, а на работе случается на первой неделе. Прежняя вилка `M10`
не правилась решением ни разу (в отличие от M4/M5): она с Фазы 1 несла обоснование
через строку [М] и решение 14 (1 ч перенесён в M0), и совпадение суммы
шагов с ней — предсказуемое, а не подозрительное: I1 — узкое умение
(четыре глагола: ветка, коммиты, PR, merge), разбивка почти без
пространства для маневра. `check_module_hours()` даст `[WARN]`
«совпадение по обеим границам» — форма та же, что у M0/M1/M2, происхождение
то же самое (решение 24 не разделяет узкие умения на «подгонку» и
«факт» — то и другое здесь верно одновременно).

## Почему не на этом репозитории и не на первом проекте

Эта программа (сам репозиторий `data-analyst-program`) работает в
`master` без веток — решение, которое обосновывает не эта программа как
курс, а сам процесс её написания (раздел 3 `HANDOFF.md`: «Git. Работа в
master»). Веткование этого репозитория задним числом ради практики
противоречило бы собственной же практике программы — учить одному,
делая другое.

P1 (первый проект портфолио, M2+M3) тоже не годится: его acceptance
criteria не требуют ветки и PR — единственный проект с таким
требованием явно в тексте — P2 (`design/blueprint.md`, часть 5,
критерий 10: «Репозиторий: ветка → PR → merge; в истории нет коммитов
«fix»/«update»; есть `.gitignore`»), а до P2 остаётся ещё M10 → P2 по
карте зависимостей (часть 3.1).

Поэтому M10 заводит **отдельный маленький практический репозиторий** —
не входящий в портфолио, только для отработки механики. Тема свободная
(предлагается: скрипт из уже пройденного модуля, оформленный отдельным
проектом — например, `compare_csv.py`-подобный инструмент или
генератор из M5/M6, переписанный с нуля своими словами) — цель шага не
код, а сам процесс ветка → PR → merge.

## Предусловие модуля

1. **GitHub-аккаунт** и `git`, настроенные в `M0/step-03.md`.
2. **`gh` (GitHub CLI) — не обязателен.** Весь процесс проходится через
   веб-интерфейс GitHub без единой команды `gh`; `gh pr create`/`gh pr
   merge` — быстрее, но не единственный путь, и в тексте шагов помечены
   как альтернатива, а не требование.

## Зависимости

`M0 → M10` — часть 3.1 blueprint (базовый git уже есть). `M10 → P2` —
жёсткая: «портфолио — репозиторий, а не скриншот», P2 — первый проект,
чей критерий явно требует ветку и PR.
