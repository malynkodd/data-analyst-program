# M10.02. Открывает Pull Request и сливает ветку через него

Умение: I1
Модуль: M10
Требуется до этого: `step-01.md` этого модуля — ветка с содержательными
коммитами запушена на GitHub
Новые файлы, объявляемые этим шагом: нет — работа целиком в
веб-интерфейсе GitHub (или `gh` CLI) над репозиторием из `step-01.md`
Время: 4–5 ч

## 1.1. Цель и связь с умением

Умение I1 части 1 blueprint, вторая половина: «...PR → merge». Критерий
части 1: «В истории: 0 коммитов с сообщением «fix»/«update», `.gitignore`
есть, файлов >50 МБ нет, **ветка смёржена через PR**» — последнее condition
шаг 01 не закрывает: ветка запушена, но ещё не слита.

## 1.2. Теория своими словами

**Pull Request — не техническая формальность, а точка проверки перед
тем, как код попадёт в `main`.** У одного человека без второго ревьюера
эта точка не пропадает — она превращается в самопроверку: PR заставляет
посмотреть на diff целиком, со стороны, а не построчно во время
написания.

**Чеклист самопроверки перед PR — то же самое решение 3, что для acceptance
criteria проектов.** Публикуется до слияния, а не после: список пунктов,
по которому проверяется собственный PR, — то, что отличает «код
компилируется» от «код готов».

**Merge commit vs squash — не всё равно, но не критично для одного
человека.**
[About pull request merges](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges)
называет три способа: обычный merge commit (сохраняет все коммиты
ветки), squash (все коммиты ветки — один коммит в `main`), rebase
(коммиты ветки переносятся поверх `main` без merge commit). Для
одного человека без параллельной работы разница на уровне «дело вкуса, а
не корректности» — в этом шаге используется обычный merge commit, потому
что он оставляет историю ветки видимой, что удобнее для самопроверки
задним числом.

## 1.3. Разобранный пример на изолированном тестовом репозитории

Прогон на машине автора 2026-08-22, не на `data-analyst-program`.

```
> git checkout main
> git merge --no-ff feature/add-notes -m "Merge pull request #1 from origin/feature/add-notes"
```

```
Merge made by the 'ort' strategy.
 notes.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 notes.txt
```

```
> git log --oneline --graph --all
*   6bf4b9d Merge pull request #1 from origin/feature/add-notes
|\
| * 823b74c add project notes file
|/
* b3aeefb init
```

Реальный Pull Request через веб-интерфейс делает то же самое действие
(создаёт merge-коммит с похожим сообщением) через кнопку «Merge pull
request», а не команду `git merge` — здесь показана механика, которую
GitHub выполняет за вас.

```
> git log --merges --oneline
6bf4b9d Merge pull request #1 from origin/feature/add-notes
```

`git log --merges` — способ проверить постфактум, что слияние
действительно прошло через merge-коммит (то есть через PR или его
локальный эквивалент), а не через `git rebase`/fast-forward, которые
merge-коммита не оставляют.

## 1.4. Задание

1. На GitHub откройте Pull Request из ветки `feature/<...>` в `main`
   (кнопка «Compare & pull request» появляется автоматически после пуша
   ветки шага 01; либо `gh pr create --base main --head
   feature/<...> --title "<...>" --body "<...>"`, если стоит `gh`).
2. В описании PR — что сделано и зачем, 2–4 предложения. Не «см.
   коммиты» — описание должно быть понятно без перехода к списку
   коммитов.
3. Пройдите по чеклисту самопроверки перед слиянием:
   - `.gitignore` в репозитории есть и покрывает то, что не должно
     коммититься (виртуальное окружение, кэш, локальные конфиги);
   - ни один файл в диффе не превышает 50 МиБ;
   - ни один коммит ветки не назван «fix»/«update» (та же проверка, что
     в `step-01.md`, — на этот раз по всей ветке, не по одному коммиту);
   - diff открыт и прочитан целиком хотя бы один раз, до слияния, а не
     после.
4. Слейте PR через кнопку «Merge pull request» (обычный merge, не squash
   и не rebase — 1.2) либо `gh pr merge --merge`.
5. Проверьте локально после `git pull`:

   ```
   > git checkout main
   > git pull
   > git log --oneline --graph --all
   > git log --merges --oneline
   ```

   Вторая команда обязана показать хотя бы одну строку — сам факт
   merge-коммита.

## 1.5. Критерий готовности

Четыре проверки, каждая — «да/нет» без второго человека.

| Проверка | Эталон | Допуск |
|---|---|---|
| `git log --merges --oneline` в `main` после `git pull` | ≥1 строка | 0 строк — слияние прошло squash'ем или rebase, а не через PR-merge; критерий I1 требует именно «смёржена через PR» |
| PR на GitHub закрыт статусом Merged | зелёная плашка «Merged», не «Closed» | «Closed» без merge — ветка не вошла в `main`, задание не выполнено |
| `git log --format=%s \| Select-String -Pattern '^(fix\|update)$'` в `main` после слияния | пусто | совпадение — сообщение коммита ветки не поймано на шаге 01, надо переписать до PR в следующий раз |
| описание PR | 2–4 предложения, не пустое и не «see commits» | пустое описание — самопроверка PR не читается позже без перехода в diff |

## 1.6. Типичные ошибки

**Ошибка:** сливает PR через «Squash and merge» вместо обычного merge.
**Почему выглядит правильно:** GitHub предлагает оба варианта как
равноправные кнопки, squash даёт чистую линейную историю `main` без
промежуточных коммитов ветки.
**Почему неправильно:** `git log --merges` после squash-слияния не
покажет merge-коммит вовсе — GitHub squash не создаёт merge-коммит,
переписывает всё в один обычный коммит поверх `main`. Критерий I1
(«ветка смёржена через PR») проверяется по наличию merge-коммита в этом
шаге, и squash его не оставляет, хотя PR формально был и слияние
формально прошло через него.
**Как правильно:** обычный merge (кнопка «Create a merge commit» или
`gh pr merge --merge`) — сохраняет и merge-коммит, и историю ветки
внутри `main`.

**Ошибка:** удаляет ветку сразу после слияния, не проверив
`git log --merges` — «GitHub же предложил удалить, значит всё в порядке».
**Почему выглядит правильно:** удаление ветки после успешного слияния —
стандартное предложение GitHub, кнопка «Delete branch» появляется сразу
после «Merged».
**Почему неправильно:** если слияние на самом деле прошло не так, как
ожидалось (например, случайно нажат squash вместо merge), ветку уже
не восстановить без `git reflog`, и разбираться придётся по локальной
копии, которая тоже может быть неактуальна.
**Как правильно:** сверить критерии из 1.5 **до** удаления ветки, не
после — удаление необратимо дёшево сделать раньше времени и дорого
исправить позже.

4–5 ч. Оценка проектная, не измерена (`research/self.md` пуст). Из чего
складывается: открытие PR и написание описания — 45 мин – 1 ч; чеклист

## 1.8. Вопрос уровня собеседования

**Вопрос:** «В чём разница между обычным merge, squash и rebase при
слиянии Pull Request — и когда каждый уместен?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Merge commit сохраняет всю историю ветки и явно фиксирует момент
   слияния отдельным коммитом с двумя родителями.
2. Squash сжимает все коммиты ветки в один — удобно, когда
   промежуточные коммиты ветки были черновыми и не несут ценности сами
   по себе.
3. Rebase переносит коммиты ветки поверх `main` без merge-коммита,
   давая линейную историю, но переписывает хэши коммитов — опасно для
   веток, которые уже кто-то склонировал или продолжает.
4. Называет практическое следствие: если процесс требует видеть факт
   слияния через PR (например, для отчётности или проверки, как в этом
   модуле), squash и rebase могут не оставить нужного следа — выбор
   способа слияния зависит от того, что должно быть видно в истории
   потом, а не только от чистоты лога.
