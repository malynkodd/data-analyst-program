## 1.2. Теория своими словами

**Python-минимум этого шага — четыре вещи**: импорт, функция с `return`,
f-строка для печати и `pathlib.Path` для пути к файлу. Всё остальное
добирается поиском по мере надобности; это штатный режим работы, а не
пробел в подготовке.

**Чтение CSV — это набор решений, а не одна команда.** У
[`pandas.read_csv`](https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html)
больше пятидесяти параметров; для первой выгрузки нужны четыре, и каждый
отвечает за одно свойство файла:

| Свойство `payouts_2026_q1.csv` | Параметр |
|---|---|
| кодировка cp1251 (не UTF-8) | `encoding="cp1251"` |
| разделитель `;` | `sep=";"` |
| десятичная запятая (`49088,78`) | `decimal=","` |
| код партнёра — цифры, но это не число | `dtype={"partner_code": "str"}` |

Имя кодировки берётся из таблицы стандартных кодировок Python
([`codecs`](https://docs.python.org/3/library/codecs.html)): `cp1251` там
описан как «windows-1251 | Belarusian, Bulgarian, Macedonian, Russian,
Serbian».

**Дата разбирается отдельной командой с явным форматом.**
[`pandas.to_datetime`](https://pandas.pydata.org/docs/reference/api/pandas.to_datetime.html),
параметр `format` — «The strftime to parse time, e.g. `"%d/%m/%Y"`». В
этой выгрузке даты записаны как `дд.мм.рррр`, то есть `format="%d.%m.%Y"`.
Без явного формата разбор идёт эвристикой, и на числах ≤12 в первой
позиции она молчаливо переставляет день с месяцем.

**Тип колонки — часть результата, а не деталь реализации.** Колонка
`partner_code` состоит из цифр, и без указания типа pandas читает её
`float64`: код `30000148` превращается в `30000148.0`. Ни ошибки, ни
предупреждения при этом нет — расхождение всплывает через два шага, на
join'е, и выглядит как пустой результат.

**Паспорт выгрузки — шесть чисел, которыми файл описан после чтения.**
Число без определения не проверяемо (решение 30 `design/decisions.md`):
«сколько в выгрузке партнёров» — не вопрос, пока не сказано, что делать с
краевыми пробелами и регистром. Поэтому каждое из шести чисел паспорта
приходит вместе со своим определением, а в 1.3 показано, насколько
определение двигает число.

**`value_counts` — распределение значений колонки одной командой, и он
по умолчанию скрывает пустые.**

Первое, что делают с незнакомой выгрузкой, — смотрят, какие значения
вообще встречаются в ключевых колонках и сколько раз.
[`pandas.Series.value_counts`](https://pandas.pydata.org/docs/reference/api/pandas.Series.value_counts.html)
отвечает на это одной строкой:

```python
q1["status"].value_counts()
```

```
PAID       1699
PENDING     189
FAILED      108
```

Сумма — 1996, то есть все строки выгрузки. Здесь скрывать нечего:
пустых статусов в файле нет.

**А теперь та же команда на колонке кода партнёра.** По умолчанию у
параметра `dropna` значение `True` — «Don't include counts of NaN», как
сказано в документации. Значит, `q1["partner_code"].value_counts()`
вернёт 57 строк, и самая частая будет `30000036` с 49 записями. С
`dropna=False` первая строка другая:

```python
q1["partner_code"].value_counts(dropna=False)
```

```
NaN         262
30000036     49
30000057     40
...
```

**262 строки без кода партнёра — крупнейшая группа в файле, и по
умолчанию её не видно.** Она в пять с лишним раз больше самого крупного
настоящего партнёра. Определения к этим числам: база — все 1996 строк
`payouts_2026_q1.csv` после чтения семью верными типами, ключ —
`partner_code`, пустые считаются отдельной группой при `dropna=False` и
не считаются вовсе при умолчании, дубли не снимались, сравнение точное.

Отсюда правило для паспорта выгрузки: `value_counts` вызывается с
`dropna=False`, а не потому, что «так надёжнее», — потому что иначе
самое важное свойство файла (четверть строк не привязана ни к одному
партнёру) не попадает ни в один отчёт и всплывает на join'е в шаге 04
как необъяснимая потеря строк.

## 1.3. Разобранный пример на сквозном датасете

Прогон на машине автора 2026-08-19, `.venv` из `step-01.md`, pandas 3.0.5.
Читается **только** `raw\payouts_2026_q1.csv` — все числа ниже относятся к
этому файлу и ни к какому другому.

```python
import pandas as pd

df = pd.read_csv(
    RAW / "payouts_2026_q1.csv",
    sep=";", encoding="cp1251", decimal=",",
    dtype={"partner_code": "str"},
)
df["payout_date"] = pd.to_datetime(df["payout_date"], format="%d.%m.%Y")
print(df.dtypes.to_string())
```

Вывод `df.dtypes` — семь колонок:

```

partner_code               str
partner_name               str
payout_date     datetime64[us]
amount                 float64
currency                   str
status                     str
```

Первые три строки таблицы:

```

2    1000003     30000099    ПП «Калина Маркет»  2026-01-01  31413.68      UAH     PAID
```

**Паспорт выгрузки.** Шесть чисел; определение — не комментарий, а часть
числа. Эталон — `data/ref_source_passport.csv`, строки с
`файл = payouts_2026_q1.csv`, считает их `reference_m5.py` без pandas.

| Показатель | Значение | Определение |
|---|---|---|
| строк данных | 1996 | строк файла без строки заголовка |
| колонок | 7 | полей в строке заголовка |
| сумма `amount` | 84 632 855.40 | все строки файла, статус не фильтруется; десятичный знак приведён к точке |

| строк без кода партнёра | 262 | код пуст после обрезки краёв |
| вариантов названия партнёра | 278 | уникальных значений `partner_name` в этом файле, как прочитано: края не обрезаны, внутренние пробелы не схлопнуты, регистр учтён |

Три замечания к этой таблице, каждое — измеренное.

**Сумма печатается округлённой.** `df["amount"].sum()` возвращает
`84632855.39999999`: pandas складывает `float64`, эталон складывает
`Decimal`. Расхождение измерено на всём модуле и не превышает
1.46 × 10⁻¹¹ (`data/reference_answers.md`, раздел про прогон pandas),
поэтому сравнивается округление до второго знака, а не сырое значение.

**«Строк без кода» = 262 при двух разных определениях.** В этом файле все
262 пустых кода приходят как `NaN`, и `isna()` даёт то же число, что
`fillna("").str.strip() == ""`: непустых кодов с краевыми пробелами в
выгрузке **0**. Совпадение проверено, а не предположено; писать надо второе
определение — оно не сломается на второй выгрузке.

**«Вариантов названия» — 278 только при этом определении и только по
этому файлу.** Три сравнения дают три числа:

| Как сравниваются названия | Вариантов в `payouts_2026_q1.csv` |
|---|---|
| как прочитано | **278** |
| `.str.strip()` — обрезка краёв | 217 |
| обрезка краёв + схлопывание внутренних пробелов | 167 |

По **обеим** выгрузкам после склейки (шаг 03) те же три сравнения дают
302, 240 и 181. Ни одно из этих чисел не равно ни одному из первых трёх:
поменялась база, а не расчёт. Полная таблица — `data/ref_name_variants.csv`,
двенадцать чисел; её правая колонка (62 варианта по правилу нормализации
из шага 04) показывает предел: 302 исходных написания — это 60 партнёров
справочника плюс два, которых в справочнике нет.

**Что делает `encoding_errors="ignore"` — измерено на этом же файле.**
Строк 1996 — столько же. Сумма `amount` 84 632 855.40 — совпадает с верной
до копейки, равенство `float` проверено и даёт `True`. Вариантов названия
при этом **22 вместо 278**, и общих с верным чтением — **0**: испорчены все
названия до одного. Проверка суммой такое чтение не отличает.

## 1.6. Типичные ошибки

**Ошибка:** смотрите распределение колонки через `value_counts()` без
`dropna=False` и делает вывод о составе данных.
**Почему выглядит правильно:** команда отрабатывает, таблица частот
выглядит полной, сумма похожа на число строк.
**Почему неправильно:** сумма частот по `partner_code` при умолчании —
1734, а строк в выгрузке 1996. Разница 262 — это записи без кода
партнёра, крупнейшая группа файла, в пять раз больше самого частого
настоящего кода (49). При умолчании она не выводится и в сумме не
участвует, и заметить её можно только сложив частоты и сравнив с
`len(df)` — чего никто не делает, потому что таблица уже выглядит
ответом.
**Как правильно:** `value_counts(dropna=False)` в паспорте выгрузки
всегда, а сумма частот сверяется с числом строк — 1996.


Все четыре измерены на этом файле; воспроизводятся прогоном
`python reference_m5.py --traps` из `program\M5\data\`.

**Ошибка:** читаете файл без `encoding` — «по умолчанию же UTF-8».
**Почему выглядит правильно:** остальные три файла датасета читаются без
указания кодировки, и на них это работает.
**Почему неправильно:** чтение падает на 89-м байте:
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd2 in position 89:
invalid continuation byte`. Файла в UTF-8 не получится: `0xd2` — это
кириллическая «Т» в cp1251.
**Как правильно:** `encoding="cp1251"`. Кодировка выгрузки — её свойство,
а не деталь чтения; она записана в `data/README.md` для каждого файла.

**Ошибка:** после падения добавляете `encoding_errors="ignore"` — чтение
проходит, и работа продолжается.
**Почему выглядит правильно:** строк ровно 1996, как в контрольной точке;
сумма `amount` — 84 632 855.40, совпадает с эталоном до копейки; ошибок
нет.
**Почему неправильно:** вариантов названия партнёра становится **22
вместо 278**, а совпавших с верным чтением — **0**. Каждое название
искажено, но обе проверки, которыми это обычно ловят (число строк и
сумма), проходят.
**Как правильно:** назвать кодировку. Параметр `errors` в этом шаге
запрещён критерием, и то же требование стоит в проверке умения B1
части 1 blueprint.

**Ошибка:** не называете `decimal=","`.
**Почему выглядит правильно:** файл читается, таблица на экране выглядит
нормально, в колонке `amount` видны привычные `49088,78`.
**Почему неправильно:** `dtype` колонки — `str`, а `.sum()` не падает, а
склеивает строки: результат — текст длиной **15 539** знаков, начинающийся
с `49088,7887701,6831413,68`. Ни одно из шести чисел паспорта, кроме числа
строк и колонок, при этом не считается.
**Как правильно:** `decimal=","`. Проверка — `df["amount"].dtype`:
`float64` против `str`.

**Ошибка:** оставляете тип `partner_code` на усмотрение pandas.
**Почему выглядит правильно:** колонка состоит из цифр, читается без
ошибок, в выводе видно `30000148.0` — «те же цифры плюс ноль».
**Почему неправильно:** `dtype` колонки — `float64`. После `astype(str)`
ключ выглядит как `30000148.0`, и со справочником партнёров совпадает
**0 строк из 1996** вместо 1726 при 1734 непустых кодах. Ни исключения,
ни предупреждения; шаг 04 получит пустой join.
**Как правильно:** `dtype={"partner_code": "str"}` при чтении. Правило
общее: колонка из цифр, над которой не делают арифметику (код, ИНН, номер
договора, телефон), читается строкой.

основная часть; чтение файла четырьмя параметрами — час-полтора вместе с
разбором двух падений; шесть чисел паспорта — час; повторный прогон и
замер — полчаса.

Известная точка неопределённости: `step-00.md` называет эту оценку первой
из трёх причин, по которым сумма часов модуля может оказаться заниженной.
Если шаг занял больше 10 ч, это данные для правки вилки части 6.1
blueprint, а не повод торопиться: строка в `research/self.md` с числом
часов и местом, где встали.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы прочитали выгрузку из внутренней системы, сумма по колонке
сошлась с бухгалтерией до копейки. Соединяете с справочником по коду
контрагента — в результате ноль строк. Что проверите первым?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Тип колонки-ключа с обеих сторон: числовой ключ против строкового
   совпадений не даёт, а код из цифр читается числом по умолчанию.
2. Как выглядит само значение ключа после чтения — печатает несколько
   значений, а не только тип: `30000148.0` против `30000148`.
3. Пропуски и пустые значения в ключе — сколько строк с пустым кодом и что
   с ними должно происходить по правилу расчёта.
4. Отмечает, что сумма как проверка чтения ничего не говорит о ключе:
   она сходится и при испорченной кодировке, и при неверном типе кода.
