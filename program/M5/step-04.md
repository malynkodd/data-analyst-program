## 1.1. Цель и связь с умением

Умение B2 части 1 blueprint: «Соединяет 4 таблицы по неидеальному ключу и
печатает отчёт: сколько строк потеряно на каждом join и почему». Шаг
закрывает умение целиком: четыре таблицы — выплаты, справочник партнёров,
курс НБУ, комиссии; ключей два разных (код и название), а у одного из
join'ов ключа как такового нет вовсе — курс берётся по ближайшей более
ранней дате.

Проверка B2 оттуда же: «Сумма сходится: `строк на входе = сопоставлено +
потеряно`; каждая потеря объяснена одной причиной из эталонного списка».
Обе половины стоят в 1.5. Первой половины мало, и это измерено: у решения,
где правило 3 канона выполнено наполовину, сумма сходится тоже —
3534 = 2912 + 480 + 3 + 139.

Порядок join'ов задан и не выбирается: партнёр → курс → комиссия. При
другом порядке числа «потеряно» будут другими — это не ошибка, а другой
отчёт, и сверить его не с чем.

## 1.2. Теория своими словами

**`merge` по умолчанию не левый.** У
[`pandas.DataFrame.merge`](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.merge.html)
`how="inner"` — «use intersection of keys from both frames». Несопоставленная
строка исчезает молча: ни исключения, ни предупреждения. Поэтому потери
считаются до того, как строки выброшены, — соединением `how="left"` и
маской по пустому полю справа, а не разницей длин до и после.

**Join не только теряет строки, но и добавляет.** Если ключ в правой
таблице не уникален, каждая левая строка размножается по числу совпадений.
Разница длин при этом перестаёт быть потерей: она становится смесью
потерянного и размноженного, и обе величины в ней уже не разделить.
Единственный способ услышать прирост в тот момент, когда он происходит, —
параметр `validate`: `"m:1"` означает «ключ уникален в правой таблице». На
этом датасете он срабатывает дважды — на справочнике с дублями и на
комиссиях с дублями пагинации, — и оба раза даёт `MergeError: Merge keys
are not unique in right dataset; not a many-to-one merge`.

**Ключ бывает не один.** Правило 3 канона модуля (докстрока
`data/reference_m5.py`): партнёр сопоставляется по коду, а если кода в
строке выплаты нет — по нормализованному названию (обрезка краёв,
схлопывание внутренних пробелов, снятие кавычек, `casefold`). Одним
вызовом `merge` это не выражается: таблица выплат делится на две части по
наличию кода, каждая соединяется своим ключом, результаты складываются
`concat`. Попытка обойтись одним соединением по коду разобрана в 1.6 — она
стоит 469 строк.

**Курс берётся не равенством дат.**
[`pandas.merge_asof`](https://pandas.pydata.org/docs/reference/api/pandas.merge_asof.html)
— «Perform a merge by key distance»; `direction="backward"` (умолчание)
берёт последнее значение не позже левой даты, то есть ровно правило 5
канона. Два условия жёсткие. Первое: «Both DataFrames must be first sorted
by the merge key in ascending order before calling this function» — иначе
`ValueError: left keys must be sorted`. Второе: обе колонки дат — даты, а
не строки; на строке из листа «Курс НБУ» получается `MergeError:
Incompatible merge dtype, dtype('<M8[us]') and <StringDtype(storage=
'python', na_value=nan)>, both sides must have numeric dtype`. Параметра
`validate` у `merge_asof` нет — уникальность правой таблицы проверяется
руками: `rates["Дата"].nunique()` даёт 127 при 127 строках.

## 1.3. Разобранный пример на сквозном датасете

Прогон на машине автора 2026-08-19, pandas 3.0.5. Загрузка — функции из
`load_all.py` шага 03; отбор `PAID` — правило 2 канона, статус сравнивается
без учёта регистра.

```
выплат всего: 4144 | справочник: 60 | курс: 127 | комиссий: 3361
PAID: 3534 | из них без кода: 469
```

**Join 1 — партнёр, два ключа.** Нормализация названия и два соединения:

```python
def norm(s):
    return (s.str.replace("[«»\"']", "", regex=True)
             .str.replace(r"\s+", " ", regex=True)
             .str.strip().str.casefold())

book_code = partners[partners["Код ЄДРПОУ"] != ""]
book_name = partners.assign(nkey=norm(partners["Назва партнера"])) \
                    .drop_duplicates(subset=["nkey"], keep="first")

with_code = paid[paid["partner_code"] != ""].merge(
    book_code[["Код ЄДРПОУ", "Назва партнера", "Місто", "Тариф"]],
    left_on="partner_code", right_on="Код ЄДРПОУ",
    how="left", validate="m:1")
```

Справочник дедуплицирован в шаге 03 по непустому коду, поэтому
`validate="m:1"` проходит; на справочнике как прочитан (63 строки) он
падает. Нормализованных ключей в справочнике 60 при 60 названиях — второй
`merge` тоже проходит `m:1`.

Потери первого join'а — не число, а список:

```
join 1: вход 3534 сопоставлено 3523 потеряно 11
  потерянные коды: ['39990001', '39990002']
  строк по каждому: {'39990002': 7, '39990001': 4}
```

Все 469 выплат без кода сопоставились по названию; потеряны только строки
с кодом, которого в справочнике нет вовсе. Определение числа 11: база —
3534 выплаты `PAID` обеих выгрузок; ключ — код, при пустом коде
нормализованное название; пустые коды не схлопнуты; справочник
дедуплицирован по непустому коду; названия сравниваются по правилу 3
канона.

**Join 2 — курс, только для валютных строк.** Гривневым присваивается
`rate = 1`, валютные идут в `merge_asof`:

```python
usd = m1[m1["currency"] == "USD"].sort_values("payout_date")
usd = pd.merge_asof(usd, rates.rename(columns={"Дата": "rate_date",
                                               "USD/UAH": "rate"}),
                    left_on="payout_date", right_on="rate_date",
                    direction="backward")
```

```
валютных строк: 282
join 2: вход 3523 сопоставлено 3520 потеряно 3
  даты потерянных: ['2026-01-02', '2026-01-02', '2026-01-04'] | первая дата ряда курсов: 2026-01-05
```

Три строки — это не «выходные»: выходные закрывает `direction="backward"`,
он берёт последний более ранний курс. Это выплаты **раньше** начала ряда,
где брать нечего ни на дату, ни ранее.

**Join 3 — комиссия.** Правило 6 канона: выплата без записи о комиссии
исключается целиком, поэтому здесь `how="inner"`:

```
join 3: вход 3520 сопоставлено 3350 потеряно 170
арифметика: 3534 = 3350 + 11 + 3 + 170 -> True
```

Итоговая таблица — 3350 строк, дублей `payout_id` в ней 0. Первые строки:

```
 payout_id partner_code       Назва партнера payout_date   amount currency  rate fee.amount
   1000002     30000127 ТОВ «Черемош Маркет»  2026-01-01 87701.68      UAH   1.0    2192.54
   1000004     30000302     ФОП «Явір Трейд»  2026-01-01 48921.30      UAH   1.0     978.43
   1000005     30000050  ФОП «Полтва Маркет»  2026-01-01 16624.87      UAH   1.0     332.50
```

**Отчёт о потерях — три строки:**

```
                               join  вход  сопоставлено  потеряно
выплаты PAID × справочник партнёров  3534          3523        11
                 выплаты × курс НБУ  3523          3520         3
                 выплаты × комиссии  3520          3350       170
```

Пятая колонка отчёта — причина; её текст в 1.4.

## 1.6. Типичные ошибки

Все пять измерены на этом датасете.

**Ошибка:** ищете партнёра одним соединением по коду.
**Почему выглядит правильно:** соединение отрабатывает, отчёт собирается,
арифметика сходится: 3534 = 2912 + 480 + 3 + 139.
**Почему неправильно:** сопоставлено **3054** вместо 3523, потеряно
**480** вместо 11. Из 480 потерянных 469 — выплаты с пустым кодом, у
которых партнёр в справочнике есть и находится по названию. До отчёта
доходят 2912 строк вместо 3350.
**Как правильно:** правило 3 канона целиком — таблица делится по наличию
кода, вторая половина соединяется по нормализованному названию.

**Ошибка:** соединяете со справочником как прочитан, тип соединения не
указывает.
**Почему выглядит правильно:** `payouts.merge(partners,
left_on="partner_code", right_on="Код ЄДРПОУ")` — команда без единого
лишнего слова, ошибки нет.
**Почему неправильно:** строк становится **5571** при 3534 на входе,
прирост **+57.6%**. Пустой код совпадает с пустым: каждая из 469 выплат
без кода размножается впятеро по числу записей справочника без кода. Ещё
172 строки добавляют три дубля кода. Определение числа 5571: вход — 3534
выплаты `PAID`, справочник как прочитан (63 строки, дубли не сняты, пять
записей без кода оставлены), тип соединения `inner`. Остальные семь
определений «наивного merge» и их числа — `data/ref_naive_merge.csv`, от
3523 до 5582.
**Как правильно:** `validate="m:1"` на каждом `merge`. На том же
справочнике он даёт `MergeError: Merge keys are not unique in right
dataset; not a many-to-one merge` вместо тихого прироста.

**Ошибка:** снимаете дубли справочника одним `drop_duplicates(subset=["Код
ЄДРПОУ"])` и соединяет по коду.
**Почему выглядит правильно:** строк после соединения ровно **3523** —
столько же, сколько в эталоне. Число сошлось, отчёт собирается.
**Почему неправильно:** пять записей без кода схлопнулись в одну, и все
469 выплат без кода получили одного и того же партнёра-заглушку —
`ФОП «Барвінок Маркет»`, первую по порядку строк листа. Угадала она **55**
выплат из 469, у остальных **414** партнёр не тот. Определение числа 55:
названия сравниваются по правилу 3 канона; при одной обрезке краёв
получится 43, при строгом равенстве строк — 36
(`data/reference_answers.md`, раздел «Ловушка четвёртой строки»).
**Как правильно:** дедупликация только среди строк с непустым кодом (шаг
03), а выплаты без кода — по названию. Сверка по числу строк такое решение
пропускает; ловит его сверка отчёта по партнёрам в шаге 05.

**Ошибка:** не снимаете дубли пагинации в комиссиях.
**Почему выглядит правильно:** соединение отрабатывает, потеря выглядит
правдоподобной — 160 строк, — и арифметика сходится: 3534 = 3360 + 11 + 3
+ 160.
**Почему неправильно:** строк после третьего join'а **3360** вместо 3350,
из них **10** — двойники: элементов в JSON 3372, уникальных 3361, и десять
дублей приходятся на выплаты, дошедшие до этого соединения. «Потеряно 160»
неверно: потеряно по-прежнему 170, просто десять строк посчитаны дважды и
закрыли собой десять потерянных.
**Как правильно:** `drop_duplicates(subset=["payout_id"])` при чтении JSON
(шаг 03) и `validate="m:1"` при соединении — на неснятых дублях он даёт тот
же `MergeError`.

**Ошибка:** соединяете `how="left"` и считаете потери разницей длин до и
после.
**Почему выглядит правильно:** ни одна строка не пропала — на входе 3534,
на выходе 3534, разница 0, терять нечего.
**Почему неправильно:** у **11** строк партнёр пуст, и в отчёте по
партнёрам они собираются в отдельную строку на **427 535.95** грн. В
отсортированном по обороту отчёте она встаёт **61-й из 61** — последней,
куда не смотрят.
**Как правильно:** после `how="left"` считать маску `isna()` по колонке из
правой таблицы, записывать это число в отчёт и только потом отбрасывать
строки.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Соединили таблицу выплат со справочником партнёров. На входе
было 3534 строки, на выходе — 5571. Ошибок и предупреждений нет. С чего
начнёте?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Называет, что join не только теряет строки, но и размножает: ключ в
   правой таблице не уникален, и прирост — это дубли ключа, а не новые
   данные.
2. Проверяет уникальность ключа в справочнике до соединения — счётом
   повторов или параметром, который превращает тихий прирост в исключение.
3. Отдельно проверяет пустой ключ: пустое совпадает с пустым, и строки с
   пустым кодом множатся на число таких же записей справа.
4. Говорит, что потери и прирост считаются по отдельности — маской по
   непопавшим и счётом дублей, — а не одной разницей длин, в которой они
   гасят друг друга.
