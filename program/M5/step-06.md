# M5.06. Собирает `run.py`: одна команда от чистого клона до отчёта

Умение: B4
Модуль: M5
Требуется до этого: `step-01.md`–`step-05.md` этого модуля целиком —
`work\load_all.py`, `work\join_all.py` (с функцией `build_final()`,
дописанной в шаге 05) и `work\metrics.py` уже существуют и работают по
отдельности
Новые файлы, объявляемые этим шагом: `program\M5\run.py`
Время: 5–7 ч

## 1.1. Цель и связь с умением

Умение B4 части 1 blueprint: «Воспроизводит расчёт из чистого клона
репозитория одной командой». Проверка: «`git clone && python run.py`
даёт файл, совпадающий с эталоном; ручных шагов 0».

Граница, которую стоит провести сразу: критерий про **расчёт**, а не про
установку окружения с нуля. Окружение (`.venv`, четыре пакета) — шаг 01,
он делается один раз и в `.gitignore`, как и `program\M5\data\raw\`
(решение 29 `design/decisions.md`). После `git clone` в рабочей копии нет
ни того, ни другого. `run.py` обязан справиться со вторым (данные) сам;
первое (окружение) читатель — тот же человек, что писал шаг 01, и уже умеет
его поднять одной и той же командой из шага 01.

## 1.2. Теория своими словами

**Git не хранит игнорируемое, и это не баг.** `git clone` копирует ровно
то, что закоммичено. Всё, что лежит в `.gitignore` — `.venv\`,
`program\M5\data\raw\`, `__pycache__` — в свежей копии отсутствует. Скрипт,
который предполагает их наличие без проверки, работает у автора (у него
они есть) и падает у любого, кто клонирует репозиторий впервые — это тот
же класс дефекта, что и «на моей машине работает».

**Точка входа собирает уже написанное, а не пишет заново.** `run.py`
импортирует `build_final` из `join_all.py` и `partner_report` из
`metrics.py` — код трёх join'ов и агрегации не копируется. Единственное
новое здесь — проверка, что данные есть, и если нет, вызов
`generate_m5.py` тем же интерпретатором, которым запущен `run.py`
(`sys.executable`, тот же приём, что в 1.3 шага 01).

## 1.3. Разобранный пример на сквозном датасете

без сетевого клонирования: `.venv\` — окружение уровня машины (шаг 01), не
часть повторяемости расчёта, поэтому остаётся; `program\M5\data\raw\`
удалена целиком — это единственное, что `git clone` не кладёт в рабочую
копию из того, от чего зависит расчёт.

`compare_csv.py` на результате — расхождение 0, как в шаге 05. Одна
команда, ноль ручных действий: не открыт ни один файл, не скопировано ни

**Каркас `run.py`:**

```python
import subprocess
import sys
from pathlib import Path

HERE = Path(__file__).resolve().parent          # program\M5
RAW = HERE / "data" / "raw"
GENERATOR = HERE / "data" / "generate_m5.py"

def ensure_dataset() -> None:
    if RAW.exists() and any(RAW.iterdir()):
        return
    print("данных нет — генерирую (data/raw пуста после чистого клона)")
    subprocess.run([sys.executable, str(GENERATOR)], check=True)

def main() -> int:
    ensure_dataset()
    sys.path.insert(0, str(HERE / "work"))
    from join_all import build_final
    from metrics import partner_report
    ...
```

`Path(__file__).resolve().parent`, а не строка `"program\\M5"` — скрипт
обязан находить себя сам, независимо от того, из какой папки его
запустили. Путь `data\raw`, зашитый относительно текущей директории
запуска, а не относительно `__file__`, — тот же класс ошибки, что
захардкоженный путь к чужому диску: работает только тогда, когда команда
случайно набрана из нужного места.

## 1.6. Типичные ошибки

Обе измерены на этом датасете.

**Ошибка:** `run.py` не проверяет наличие `data\raw`, предполагая, что
шаг 01 уже отработал.
**Почему выглядит правильно:** на машине автора, где `data\raw` заполнена
с шага 01, скрипт работает без единой правки.
**Почему неправильно:** на чистом клоне (или после `git clean`, или на
чужой машине сразу после `git clone`) падает на первой строке первого
чтения: `FileNotFoundError: [Errno 2] No such file or directory:
'...\program\M5\data\raw\payouts_2026_q1.csv'`. Ручных шагов 0 — это про
результат для читателя, который ни разу не запускал `generate_m5.py`
вручную.
**Как правильно:** `ensure_dataset()` — проверка перед первым чтением, а
не документация «сначала запустите генератор» в README, которую можно не
прочитать.

**Ошибка:** коммитит `partner_report.csv`, но не сами скрипты `work\`
(«результат же в репозитории, зачем код»).
**Почему выглядит правильно:** на машине автора файл открывается, числа
видны, всё как будто на месте — `git status` не проверялся.
**Почему неправильно:** `git clone && python run.py` на чужой машине
падает немедленно: `ModuleNotFoundError: No module named 'join_all'`.
Файл результата — не доказательство воспроизводимости, а её противоположность:
он мог быть посчитан один раз и вручную положен в репозиторий.
**Как правильно:** `git status` перед коммитом каждого шага модуля
(привычка с шага 01) и проверка по чужому клону — пункт 5 задания.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «В README к проекту написано: клонируйте и запустите `python
run.py`. Коллега это сделал и получил `ModuleNotFoundError: No module
named 'pandas'` на первой же строке. Значит ли это, что критерий
«воспроизводится одной командой» не выполнен?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Различает окружение (интерпретатор и пакеты) и сам расчёт: критерий —
   про повторяемость расчёта на уже готовом окружении, а не про установку
   окружения с нуля.
2. Отмечает, что граница между «окружение» и «расчёт» должна быть названа
   явно — одна команда для установки, отдельная для запуска, а не
   молчаливое предположение.
3. Отдельно называет данные: если бы вместо пакета не хватало файла
   данных (`data\raw` пуста) — это уже дефект `run.py`, а не окружения,
   потому что скрипт обязан справиться с этим сам.
4. Указывает, что «ручных шагов 0» проверяется реальным клоном, а не
   чтением кода: код, который выглядит самодостаточным, может работать
   только потому, что что-то нужное уже лежит на диске автора.
