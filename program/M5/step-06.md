## 1.1. Цель и связь с умением

Умение B3 части 1 blueprint: «Пишет функцию расчёта метрики и 5 тестов к
ней (pytest)». Проверка оттуда же: «5 тестов зелёные, среди них ≥1 на
граничный случай (пустой вход) и ≥1 на деление на ноль». Шаг закрывает
умение целиком: функция `take_rate` — сама метрика, функция
`partner_report` — её применение к результату шага 05, оба протестированы.

Take rate — правило 7 канона модуля (докстрока `data/reference_m5.py`):
комиссия делённая на оборот, округление `ROUND_HALF_UP` до 4 знаков.
Деньги при этом округляются до 2 знаков, и порядок важен: округлить нужно
каждую валютную выплату при пересчёте в гривну, а не сумму по партнёру
целиком — иначе получается другое число, и оно не падает с ошибкой (1.6).

## 1.2. Теория своими словами

**pytest находит тесты по имени файла и функции.**
[Getting started](https://docs.pytest.org/en/stable/getting-started.html):
«pytest will run all files of the form `test_*.py` or `*_test.py` in the
current directory and its subdirectories», и «you can use the `assert`
statement to verify test expectations». Отдельного фреймворка для
проверок учить не придётся: обычный `assert`, а какие значения не
совпали, pytest напечатает сам.

**`round()` и `Decimal` округляют по-разному на границе.** Встроенный
`round()` работает с `float`, а `float` не хранит десятичные дроби точно.
`0.00015` в двоичном виде — не ровно `0.00015`, и `round(0.00015, 4)`
вполне может дать `0.0001` вместо того, что даёт правило «к ближайшему,
от нуля». [`decimal.ROUND_HALF_UP`](https://docs.python.org/3/library/decimal.html#decimal.ROUND_HALF_UP)
документирован как «Round to nearest with ties going away from zero» —
это то самое школьное «0,5 всегда вверх», и оно требует `Decimal`, а не
`float`, потому что `Decimal` хранит число как записанные цифры, а не как
двоичное приближение.

## 1.3. Разобранный пример на сквозном датасете

Прогон на машине автора 2026-08-20, тот же датасет и то же окружение, что
в шагах 01–04 (`pandas` 3.0.5, `pytest` 9.1.1).

**Функция метрики — без пандас вовсе**, она принимает два числа:

```python
from decimal import Decimal, ROUND_HALF_UP

FOUR = Decimal("0.0001")

def take_rate(fee, gross) -> Decimal:
    fee, gross = Decimal(str(fee)), Decimal(str(gross))
    if gross == 0:
        return Decimal("0.0000")
    return (fee / gross).quantize(FOUR, rounding=ROUND_HALF_UP)
```

`Decimal(str(x))`, а не `Decimal(x)` напрямую от `float` — стандартный
приём: `str()` у `float` печатает кратчайшую строку, которая читается
обратно тем же числом, а `Decimal(0.00015)` без `str()` взял бы двоичное
приближение и дал бы другой результат на той же границе.

Первая попытка агрегировать отчёт по партнёру падает молча дважды —
обе находки со шага, где до сих пор ничего не считалось, только
читалось и соединялось:

```
work["fee.amount"].sum()
```

даёт не число, а строку длиной **21481** символ — конкатенацию:
`'2192.54978.43332.5024.501430.501995.091888.851295.531143.292…'`. Причина
— тип колонки: `json_normalize` в шаге 04 прочитал `fee.amount` как
`str`, потому что в самом JSON сумма записана строкой (`"2192.54"`), и
шаг 04 нигде это не проверял — там сумма ни разу не считалась. Ошибка не
падает здесь: `.sum()` у строкового столбца — это конкатенация, а не
арифметика, и она отрабатывает молча. Падает она на следующей строке, при
попытке напечатать результат числом:

```
ValueError: Unknown format code 'f' for object of type 'str'
```

Починка — одна строка до агрегации: `work["fee.amount"] =
pd.to_numeric(work["fee.amount"])`.

**Вторая находка тише первой — не падает вовсе.** Если пересчитать
валютные строки в гривну и просуммировать без промежуточного округления
каждой строки:

```
ФОП «Черемош Трейд»: у вас 4032269.70, в эталоне 4032269.67
```

Портфель целиком: **159881549.92** вместо **159 881 549.91** — разница
одна копейка, но не ноль, и оба числа выглядят правдоподобно. Правило 7
канона требует округлять деньги до 2 знаков, и это применимо к каждой
валютной строке отдельно, до суммирования — иначе сумма плавающих
хвостов округляется один раз в конце и даёт другое число.

**После обеих починок** (`pd.to_numeric` и округление каждой строки перед
суммой) отчёт по 60 партнёрам сходится с `ref_partner_report.csv`
целиком:

```
СОВПАДАЕТ: 60 строк, 8 колонок, расхождение 0.
```

Первая строка отчёта — та же, что в `data/reference_answers.md`: `ФОП
«Черемош Трейд»`, 77 выплат, оборот **4032269.67**, комиссия **80645.37**,
take rate **0.0200**.

## 1.6. Типичные ошибки

Все три измерены на этом датасете; первые две уже разобраны в 1.3.

**Ошибка:** суммируете `fee.amount` как есть, без проверки типа колонки.
**Почему выглядит правильно:** до этого шага колонка ни разу не участвовала
в арифметике: шаги 02–04 её только читали и передавали дальше, join по ней
не строился. Повода усомниться в типе не было ни одного.
**Почему неправильно:** `.sum()` строкового столбца — конкатенация, не
сложение: результат — строка на **21481** символ, а не число. Она не
падает сама, падает следующая строка, которая пытается напечатать её как
число: `ValueError: Unknown format code 'f' for object of type 'str'`.
**Как правильно:** `pd.to_numeric(work["fee.amount"])` до агрегации.
Проверка — `work["fee.amount"].dtype` сразу после этой строки: `float64`,
не `str`/`object`.

**Ошибка:** пересчитываете валютные строки в гривну и суммируете по
партнёру одним выражением, без округления каждой строки.
**Почему выглядит правильно:** число похоже на верное вплоть до
третьего-четвёртого знака, а `.sum()` не падает и ни о чём не
предупреждает.
**Почему неправильно:** у `ФОП «Черемош Трейд»` — **4032269.70** вместо
**4032269.67**, у портфеля целиком — **159881549.92** вместо
**159881549.91**. Копеечную разницу глазом не поймать: в отдельной строке она встречается
реже одного раза на 60 партнёров. `compare_csv.py` ловит её на первой
же.
**Как правильно:** округлять каждую валютную выплату до 2 знаков
`ROUND_HALF_UP` сразу при конвертации, `money_row()` из 1.4, и только
потом суммировать по партнёру.

**Ошибка:** не проверяете `gross = 0` в `take_rate`, полагаясь на то, что
в реальных данных такого не бывает.
**Почему выглядит правильно:** в датасете модуля выручка партнёра нулевой
не бывает — все 60 строк `ref_partner_report.csv` это подтверждают, — и на
реальном прогоне функция не падает ни разу.
**Почему неправильно:** `Decimal("5") / Decimal("0")` поднимает
`decimal.DivisionByZero`; на `float`-версии — `ZeroDivisionError: float
division by zero`. Функция метрики обязана быть безопасной не только на
тех данных, которые есть сегодня, — и проверяется это тестами, а не
датасетом.
**Как правильно:** `if gross == 0: return Decimal("0.0000")` до деления,
проверено тестом `test_take_rate_zero_gross`, не прогоном пайплайна.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Функция считает take rate — комиссию делённую на оборот. На
каких входных данных вы бы её протестировали, кроме обычного случая из
датасета?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Нулевой знаменатель — функция не должна падать необработанным
   исключением, даже если в текущих данных такого случая нет.
2. Пустой вход агрегирующей функции — 0 строк на входе должны давать
   пустой, но структурно верный результат, а не исключение.
3. Граница округления — значение ровно посередине между двумя
   округлёнными результатами; `round()` на `float` и `Decimal` с
   `ROUND_HALF_UP` могут дать разный ответ на одном и том же входе.
4. Некорректные по смыслу, но не запрещённые типом значения (комиссия
   больше оборота, отрицательная сумма) — функция не обязана их
   исправлять, но не должна тихо возвращать бессмысленное число без
   какого-либо сигнала.
