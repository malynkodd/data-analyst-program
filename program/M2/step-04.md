## 1.1. Цель и связь с умением

После шага вы подтягиваете атрибуты товара (название, себестоимость,
категория) из справочника `product_lookup.csv` (60 строк) в выгрузку
продаж по `product_id`, двумя способами — функцией `XLOOKUP` и связкой
`INDEX`+`MATCH`. Это первые 3 из 10 формул-задач D2 (часть 1 blueprint).

## 1.2. Теория своими словами

В `step-02.md` категория приводилась к канону через вложенный `IF` — там
было ровно 5 известных значений, и перечислить их в формуле было разумно.
`product_lookup.csv` — 60 строк: писать 60 вложенных `IF` бессмысленно и
неустойчиво к изменению списка товаров. Здесь нужна функция поиска по
таблице.

**`XLOOKUP`** — современный способ поиска значения по ключу:

```
XLOOKUP(искомое_значение, диапазон_поиска, диапазон_результата)
```

Например, чтобы найти `product_name` по `product_id` из колонки `D`
(`sales_extract_raw.csv`) в справочнике (`product_lookup.csv`, колонки
`product_id` и `product_name`):

```
=XLOOKUP(D2, product_lookup!A:A, product_lookup!B:B)
```

Функция ищет значение `D2` в первом диапазоне и возвращает соответствующее
значение из второго — диапазоны должны быть одной длины, строка за
строкой.

**`INDEX`+`MATCH`** — тот же результат двумя функциями вместе, доступный
и там, где `XLOOKUP` нет (более старые версии Excel):

```
MATCH(искомое_значение, диапазон_поиска, 0)
```

находит **номер строки**, на которой искомое значение встретилось
(0 — точное совпадение, не примерное). `INDEX` берёт значение из другого
диапазона по этому номеру строки:

```
=INDEX(product_lookup!C:C, MATCH(D2, product_lookup!A:A, 0))
```

Разница между двумя способами не в результате (оба находят одну и ту же
строку по одному и тому же ключу), а в том, что `MATCH` возвращает
промежуточный результат (номер строки), который можно переиспользовать
для нескольких `INDEX` подряд, если нужно несколько колонок сразу.

## 1.3. Разобранный пример на сквозном датасете

Датасет — `program/M2/data/sales_extract_raw.csv` (продажи) и
`program/M2/data/product_lookup.csv` (справочник, 60 товаров), схема
объявлена в `step-00.md`.

**XLOOKUP, задача 1 — название товара:**

Заказ `S00001` ссылается на `product_id = P039`.

```
=XLOOKUP("P039", product_lookup!A:A, product_lookup!B:B)
→ appliances-039
```

**XLOOKUP, задача 2 — себестоимость:**

Заказ `S00014` ссылается на `product_id = P021`.

```
=XLOOKUP("P021", product_lookup!A:A, product_lookup!D:D)
→ 5931.14
```

**ИНДЕКС+ПОИСКПОЗ, задача 3 — категория:**

Товар `P036` (без привязки к конкретному заказу — просто товар из
справочника):

```
=INDEX(product_lookup!C:C, MATCH("P036", product_lookup!A:A, 0))
→ Ноутбуки
```

Все три значения — из `data/reference_answers.md`, раздел «Точечные
проверки для D2».

## 1.6. Типичные ошибки

**Ошибка:** в `MATCH` не указывает третий аргумент (тип совпадения) или
указывает `1`/`-1` вместо `0`.
**Почему выглядит правильно:** формула не падает с ошибкой — `MATCH` без
третьего аргумента или с `1` действительно возвращает какое-то число.
**Почему неправильно:** тип совпадения `1` (по умолчанию, если аргумент
не указан) ищет **приблизительное** совпадение и требует, чтобы диапазон
поиска был отсортирован по возрастанию — на `product_lookup.csv`,
отсортированном по `product_id` как текст (`P001`, `P002`…), это может
случайно сработать, но для любого несортированного диапазона `MATCH` без
`0` находит не то значение, а не сообщает об ошибке. Молчаливо неверный
результат опаснее явной ошибки.
**Как правильно:** третий аргумент `MATCH` — всегда `0` для точного
поиска по ключу, если нет специальной причины для приблизительного.

**Ошибка:** в `XLOOKUP` передаёт диапазон поиска и диапазон результата
разной длины (например, `product_lookup!A2:A61` для поиска, но
`product_lookup!B1:B61` для результата — сдвиг на одну строку из-за
случайно включённого заголовка в один диапазон и не включённого в
другой).
**Почему выглядит правильно:** оба диапазона выглядят «примерно той же
длины», разница на одну строку легко не заметить.
**Почему неправильно:** `XLOOKUP` сопоставляет диапазоны строка в строку;
при сдвиге на одну строку результат для `product_id = "P039"` вернёт
значение, соответствующее не `P039`, а соседнему товару в справочнике —
результат не ошибка, а неверное, но правдоподобно выглядящее число.
**Как правильно:** оба диапазона — одной длины и с одинаковым начальным
смещением (либо оба с заголовком, либо оба без).

**Ошибка:** ищет `product_id` без учёта того, что в `sales_extract_raw.csv`
он может быть с лишними пробелами (по аналогии с `category_raw` из
`step-02.md`), и не оборачивает искомое значение в `TRIM`.
**Почему выглядит правильно:** `product_id` в характеристике датасета
(`step-00.md`) не заявлен как «грязная» колонка — в отличие от
`category_raw`, у него нет специфицированного дефекта пробелов.
**Почему неправильно:** это верно для этого конкретного датасета
(`product_id` в `sales_extract_raw.csv` действительно чистый) — но если
из этого сделать общий вывод «искать можно без `TRIM`», перенос той же
формулы на реальную выгрузку, где идентификаторы приходят с лишним
пробелом (частый экспортный артефакт), даст `#N/A` там, где совпадение
есть, просто с невидимым пробелом.
**Как правильно:** оборачивать искомое значение в `TRIM` по умолчанию,
даже когда конкретный датасет кажется чистым — обработка ошибок
поиска (что делать с `#N/A`) — отдельная тема `step-06.md`.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «`ВПР`/`VLOOKUP` в вашей таблице возвращает не то значение,
хотя ключ в обоих диапазонах точно есть. Что проверите в первую
очередь?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Тип совпадения (точное/приблизительное) — не задан ли по умолчанию
   приблизительный поиск там, где нужен точный.
2. Скрытые пробелы или невидимые символы в значении ключа с любой из
   двух сторон (частая причина ложного `#N/A` или неверного совпадения).
3. Совпадение длины и смещения диапазонов поиска и результата (не сдвинут
   ли один из них на строку из-за заголовка).
4. Формат данных ключа — текст с обеих сторон или число с одной стороны и
   текст с другой (`"039"` и `39` не совпадают как ключи, даже если
   выглядят «одинаково»).
