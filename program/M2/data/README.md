# Сквозной датасет модуля M2 (Таблицы)

Синтетика. Используется без изменений во всех восьми шагах M2
(`step-01.md`–`step-08.md`) — правило части 1.3 скилла curriculum-design:
один датасет на модуль, объявлен один раз в `step-00.md`, не меняется
между шагами.

**Категория:** синтетика для модуля, ведущего к проекту (M2 → P1, часть
3.1 blueprint) — генератор и спецификация дефектов лежат в репозитории,
эталон известен точно (первая категория раздела 1.3 curriculum-design).
Собственный датасет P1 («сеть из 12 магазинов») пишется отдельно при
авторинге P1 — это не тот же датасет, что учебный материал M2.

## Файлы

| Файл | Роль |
|---|---|
| `generate_sales_extract.py` | Генератор обоих csv. Детерминирован: `SEED = 20260802`. Перегенерация даёт побайтово тот же результат. |
| `sales_extract_raw.csv` | 20 000 строк — «грязная» выгрузка продаж, эталон для D1. |
| `product_lookup.csv` | 60 товаров (`P001`–`P060`) — справочник для XLOOKUP/ИНДЕКС+ПОИСКПОЗ (D2). |
| `build_reference.py` | Строит SQL-эталон (sqlite): применяет ровно те правила очистки, которые описаны в шагах, и печатает контрольные суммы. Источник всех чисел в шагах и в `reference_answers.md` — его вывод, не ручной подсчёт. |
| `reference_answers.md` | Предвычисленные контрольные числа — итог запуска `build_reference.py`, оформленный читаемо. |

## Схема `sales_extract_raw.csv` (8 колонок)

| Колонка | Смысл | Особенность |
|---|---|---|
| `order_id` | Идентификатор заказа | `S00001`…`S20000` |
| `order_date_raw` | Дата заказа | Два формата: ISO (`2025-09-21`) и `ДД.ММ.ГГГГ` (`08.03.2025`) — различимы по разделителю (`-` против `.`), без обратной неоднозначности |
| `category_raw` | Категория товара | 5 канонических категорий (см. ниже), каждая — в 5 вариантах регистра/пробелов |
| `product_id` | Ссылка на `product_lookup.csv` | 4.19% строк (838 из 20 000) ссылаются на товар, которого нет в справочнике — снят с продажи |
| `channel` | Канал продажи | `online` / `retail` / `wholesale` — уже чистое поле, второй срез D1 |
| `quantity` | Количество | Целое, 1–5, чистое поле |
| `unit_price` | Цена за единицу | Число с двумя знаками после точки, чистое поле — контрольная величина для сверки с `amount_raw` |
| `amount_raw` | Сумма заказа | Текст, не число: 4 формата (точка, запятая как десятичный разделитель, пробел как разделитель тысяч, суффикс «грн»); возвраты — отрицательные суммы **в той же колонке**, часть — в «бухгалтерском» формате (в скобках вместо минуса) |

## 5 канонических категорий

| Кириллица (канон) | Код (для ASCII-вывода скриптов) |
|---|---|
| Ноутбуки | `laptops` |
| Смартфони | `phones` |
| Аксесуари | `accessories` |
| Побутова техніка | `appliances` |
| Одяг | `clothing` |

## Схема `product_lookup.csv` (4 колонки)

| Колонка | Смысл |
|---|---|
| `product_id` | `P001`…`P060` |
| `product_name` | вида `<код категории>-<номер>`, например `laptops-021` |
| `category` | канонический кириллический текст, без дефектов |
| `unit_cost` | себестоимость единицы, число |

Заказы `sales_extract_raw.csv` иногда ссылаются на `product_id` за
пределами `P001`–`P060` (диапазон `P061`–`P075`, «снятые с продажи»
товары) — таких строк 838 из 20 000. Для них `XLOOKUP`/`ИНДЕКС+ПОИСКПОЗ`
не находят совпадения — это материал для задач на обработку ошибок в D2.

## Почему значения полей латиницей/кириллицей — где именно

Часть значений (`category_raw`, значения `category` в справочнике) —
кириллица: это соответствует реальной украинской выгрузке и напрямую
относится к умению (очистка написания категорий). Скрипт
`build_reference.py`, который печатает агрегаты в консоль, использует
ASCII-коды категорий (`laptops`, `phones`…) вместо кириллического текста
в самом выводе — печать кириллицы в stdout ломается на части
Windows-консолей (см. довод в `program/M1/data/count_active.py` и
`program/M0/data/README.md`). Сам csv-файл при этом полноценно в UTF-8 и
открывается в Excel/Sheets без проблем — ограничение касается только
вывода в консоль.

## Почему без sha256 и без снапшота

Правило снапшота (файл + дата выгрузки + sha256, часть 5 blueprint)
относится к реальным источникам (P3, P4, P6). Здесь датасет
синтетический — эталон фиксируется генератором с зашитым `SEED`.

## Как использовать `build_reference.py`

```
python3 build_reference.py
```

Скрипт ничего не меняет в csv-файлах — только читает их, строит временную
таблицу sqlite в памяти и печатает контрольные суммы и счётчики дефектов.
Все числа воспроизводимы: тот же `SEED` в генераторе даёт тот же csv, тот
же csv даёт тот же вывод `build_reference.py`.
