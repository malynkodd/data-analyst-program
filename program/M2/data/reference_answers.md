## Наивный пересчёт `quantity * unit_price` против очищенной суммы

Обе колонки `quantity` и `unit_price` в файле чистые (не текст), поэтому
пересчёт «в лоб» синтаксически всегда работает — и именно поэтому
опасен: он не учитывает знак возврата, зашитый только в `amount_raw`.

| Показатель | Значение |
|---|---|
| Наивная сумма `quantity * unit_price` (знак возврата игнорируется) | 590 697 683.72 |
| Очищенная сумма `amount` (с учётом знака возврата) | 530 839 498.36 |
| Расхождение | 59 858 185.36 |

Расхождение — не ошибка округления: это ровно удвоенная сумма модулей
всех возвратов (952 строки возврата, наивный пересчёт прибавляет их
дважды вместо вычитания один раз).

## Три определения выручки (для решения без единственного ответа в `step-02.md`)

| Определение | Формула | Значение |
|---|---|---|
| Чистая выручка (продажи минус возвраты, `amount_clean` как есть) | `SUM(amount_clean)` по всем строкам | **530 839 498.36** |
| Выручка без учёта возвратов вовсе (строки-возвраты исключены из суммы) | `SUM(amount_clean)` по строкам, где `is_return` = ЛОЖЬ | **560 768 591.04** |
| Валовая выручка, если бы возвраты считались продажами (знак игнорируется) | `SUM(ABS(amount_clean))` по всем строкам | **590 697 683.72** |

Проверка: 560 768 591.04 − 530 839 498.36 = 29 929 092.68 = сумма модулей
всех 952 возвратов. 590 697 683.72 совпадает с «наивным пересчётом»
`quantity*unit_price` из раздела выше — это ожидаемо: обе величины
считают возвраты как обычные положительные продажи, просто разными
формулами (пересчёт через `quantity*unit_price` и обнуление знака через
`ABS(amount_clean)`).
