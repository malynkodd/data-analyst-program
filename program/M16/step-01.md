# M16.01. Строит отчёт в Looker Studio поверх BigQuery с тремя рабочими фильтрами

Умение: C4
Модуль: M16
Требуется до этого: `step-00.md` этого модуля; `program/M7/step-01.md`
(таблица `transactions`, 4 386 000 строк, в BigQuery)
Новые файлы, объявляемые этим шагом: `program\M16\work\report_log.md`
Время: 4–6 ч

## 1.1. Цель и связь с умением

Умение C4 части 1 blueprint: «Строит один отчёт в Looker Studio поверх
BigQuery». Критерий: «Отчёт открывается по ссылке, 3 контрола-фильтра
работают, цифры сходятся с SQL».

Три части критерия проверяются тремя разными способами: ссылка —
открытием вручную (1.5, почему не скриптом — `step-00.md`), фильтры —
тем, что число на отчёте меняется при применении каждого, цифры — сверкой
итога отчёта с независимым SQL-запросом на той же таблице.

## 1.2. Теория своими словами

**Billing нужен раньше, чем коннектор.** Решение 34 (`design/decisions.md`):
«To access BigQuery data in Data Studio, you'll need to provide a Google
Cloud Billing account» — включить его нужно **до** первого подключения,
иначе коннектор откажет. Включённый биллинг сам по себе не тарифицируется:
«There is no cost to using a product or service that participates in the
Free Tier program when you stay within the specified monthly usage limits»
([Free Cloud Features](https://cloud.google.com/free/docs/free-cloud-features)).
Таблица M7 (4 386 000 строк, 7 колонок) далеко внутри лимита хранения
10 GiB; один полный скан таблицы — далеко внутри лимита 1 TiB
запросов/месяц.

**Подключение.** Документация
([Connect to Google BigQuery](https://cloud.google.com/looker/docs/studio/connect-to-google-bigquery)):
«Sign in to Data Studio. Click Create and then select Report… To create a
new embedded data source, select the BigQuery connector. Configure the
data source connection to your BigQuery data» — нужно указать проект,
датасет и таблицу (в облачной консоли BigQuery, не в файле на диске:
M7 не пишет CSV, `program/M7/step-00.md`).

**Доступ авторизует владелец данных, а не зритель.** Для публичной
ссылки это решающее различие. У источника данных два режима авторизации:
«Owner's credentials… lets you share reports that use this data source
without requiring report viewers to have their own access to the
underlying dataset» против «Viewer's credentials… require anyone who
attempts to view the data… to have their own access to the dataset»
([Data credentials](https://docs.cloud.google.com/looker/docs/studio/data-credentials)).
Публичный зритель без своего доступа к BigQuery (любой, кто получит
ссылку) увидит данные только при режиме **владельца**. Режим выбирается
при настройке источника данных.

**Публикация — не отдельная кнопка, а переключатель доступа.**
«Share more broadly by turning on link sharing for a report. This lets
anyone in your organization or on the web view the report, even if they
don't have a Google account» ([Ways to share your
reports](https://docs.cloud.google.com/looker/docs/studio/ways-to-share-your-reports)) —
путь: **Share → General access**, включить доступ по ссылке. Без этого
шага ссылка технически существует, но открывается только у тех, кому
явно выдан доступ, — критерий «открывается по ссылке» подразумевает
именно общий доступ, не точечный.

**Три контрола-фильтра — из готового списка типов, не с нуля.**
Looker Studio предлагает готовые элементы: «drop-down and fixed-size
lists that let viewers select from a list of filter values, as well as
input boxes» ([About controls](https://support.google.com/looker-studio/answer/6312144)).
Для таблицы M7 три осмысленных фильтра — по диапазону дат (`txn_date`,
«Date range control»), по счёту (`account_id`, выпадающий список) и по
категории (`category`, выпадающий список): все три — колонки, которые
шаг 02–03 M7 использовал для демонстрации партиционирования и
кластеризации, здесь они же становятся интерактивным разрезом.

## 1.3. Разобранный пример — состав отчёта

**Один диаграмма-скоркард** — `SUM(amount)` без разрезов, число крупным
шрифтом. Это то самое число, с которым сверяется независимый SQL-запрос:

```sql
SELECT SUM(amount) AS total
FROM `<ваш_проект>.<датасет>.transactions`;
```

**Три контрола на той же странице:**

| Контрол | Поле | Тип |
|---|---|---|
| 1 | `txn_date` | Date range control |
| 2 | `account_id` | Drop-down list (фильтр) |
| 3 | `category` | Drop-down list (фильтр) |

**Проверка, что фильтр работает — не по виду, а по числу.** Контрол
может стоять на странице и выглядеть рабочим (открывается список,
что-то выбирается), но если поле фильтра не совпадает с полем на
диаграмме (опечатка в имени поля, разные источники данных у контрола и
диаграммы), число на скоркарде не изменится ни при каком выборе. Тот же
класс дефекта, что «связь построена, но ничего не меняет» в M4/M15 —
здесь ловится тем же способом: числом до и после.

## 1.4. Задание

1. Включите Google Cloud Billing account на проекте с таблицей M7
   (решение 34) — до подключения.
2. Подключите Looker Studio к таблице `transactions`: **Create → Report
   → BigQuery**, укажите проект/датасет/таблицу. При настройке источника
   выберите авторизацию **Owner's credentials** — без этого публичный
   зритель без доступа к BigQuery увидит пустой отчёт.
3. Постройте скоркард `SUM(amount)` и три контрола из 1.3.
4. Выполните SQL-запрос из 1.3 в консоли BigQuery, запишите итог.
5. Сверьте итог SQL с числом на скоркарде **без применённых фильтров** —
   они обязаны совпасть.
6. Примените каждый из трёх фильтров по очереди (любое конкретное
   значение — не «все»), запишите число скоркарда после каждого.
7. **Share → General access** — включите доступ по ссылке. Откройте
   свою ссылку в приватном/инкогнито-окне браузера (без входа в
   аккаунт) — убедитесь, что отчёт открывается и показывает число, а не
   запрос на доступ.
8. Заполните `program\M16\work\report_log.md`:

   ```
   Публичная ссылка: <ваш URL lookerstudio.google.com/reporting/...>
   SQL-итог: <число из задания 4>
   Отчёт без фильтров: <число со скоркарда>
   Отчёт с фильтром по дате: <число после фильтра 1>
   Отчёт с фильтром по account_id: <число после фильтра 2>
   Отчёт с фильтром по category: <число после фильтра 3>
   ```

9. Проверьте:

   ```
   > python program\M16\data\check_report.py
   ```

## 1.5. Критерий готовности

Проверяет `check_report.py` (два из трёх пунктов) и вы сами вручную
(один пункт — 1.4, задание 7). Порог скрипта — **пять строк `[OK]`, ни
одной `[FAIL]`, код возврата 0**:

| Проверка | Кем | Что доказывает |
|---|---|---|
| формат ссылки (`/reporting/…`) | скрипт | ссылка похожа на настоящий отчёт, не на общую страницу |
| ссылка открывается в приватном окне без входа | учащийся, вручную | «отчёт открывается по ссылке» — критерий C4 дословно; скрипт этого не может (`step-00.md`, «Отступление», третий пункт) |
| SQL-итог = отчёт без фильтров | скрипт | «цифры сходятся с SQL» — критерий C4 дословно |
| три фильтра меняют число | скрипт | «3 контрола-фильтра работают» — критерий C4 дословно |

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 2 ошибки
этого шага, каждую с признаком, по которому её видно в своём результате.

## 1.6. Типичные ошибки

**Ошибка:** настраиваете источник данных с авторизацией **Viewer's
credentials** («так безопаснее — каждый смотрит своими правами»).
**Почему выглядит правильно:** формулировка и правда звучит как более
строгий контроль доступа — а на реальных конфиденциальных данных это
вполне может оказаться верным выбором.
**Почему неправильно:** «require anyone who attempts to view the data…
to have their own access to the dataset» — публичный зритель без
BigQuery-доступа к этому проекту увидит запрос на разрешение вместо
отчёта, критерий «открывается по ссылке» не выполняется ни для кого,
кроме автора и тех, кому явно выдан доступ к самому BigQuery-проекту.
**Как правильно:** **Owner's credentials** при настройке источника —
данные показываются от имени владельца отчёта, зрителю ничего лишнего
не нужно.

**Ошибка:** включаете «Share → General access» на **отчёте** и не
проверяете отдельно режим авторизации **источника данных**.
**Почему выглядит правильно:** отчёт и правда становится доступным по
ссылке — страница открывается.
**Почему неправильно:** доступ к отчёту и доступ к данным внутри него —
два разных переключателя. Отчёт откроется, но диаграммы будут пустыми
или покажут ошибку доступа, если источник данных остался на «Viewer's
credentials» — то же расхождение, что в первой ошибке, только
обнаруживается на шаг позже.
**Как правильно:** проверять оба переключателя — доступ к отчёту и
режим авторизации каждого источника данных.

## 1.7. Честная оценка времени

4–6 ч. Оценка проектная, не измерена (структурное ограничение,
`step-00.md`, «Отступление»). Из чего складывается: включение billing и

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы отправили ссылку на дашборд коллеге, и у него вместо
графиков — ошибка доступа. Ссылку вы включили как публичную. Что
проверите?»

**Эталон (ответ покрывает ≥2 из 3 пунктов):**
1. Различает два уровня доступа: доступ к самому отчёту (страница
   открывается) и доступ к источнику данных, стоящему за диаграммами
   (данные показываются) — ошибка может быть на втором уровне при
   открытом первом.
2. Называет два режима авторизации источника — от имени владельца или
   от имени зрителя — и что именно второй режим требует у зрителя
   собственного доступа к базовому хранилищу.
3. Предлагает проверку: открыть ссылку в приватном окне браузера без
   входа в свой аккаунт — тот же тест, что видит зритель без прав.
