# M7.03. Переписывает запрос и доказывает падение объёма сканирования

Умение: E1
Модуль: M7
Требуется до этого: `step-02.md` этого модуля — `fintech.transactions_optimized`
существует, партиционирована по `txn_date`, кластеризована по
`account_id`, 4 386 000 строк
Новые файлы, объявляемые этим шагом: `program\M7\work\optimized_query.sql`
Время: 5–7 ч

## 1.1. Цель и связь с умением

Умение E1 части 1 blueprint целиком: «переписывает запрос под неё.
Объём сканирования падает ≥5× (байты до/после зафиксированы
скриншотом)». Шаг закрывает вторую половину — доказательство, а не
только построение таблицы.

## 1.2. Теория своими словами

**Один и тот же запрос на двух таблицах — не одно и то же измерение.**
Падение объёма сканирования доказывается снятием оценки валидатора для
**одного и того же логического запроса** на старой и новой таблице: тот
же фильтр, та же дата, та же группировка. Два разных запроса на двух
разных таблицах про партиционирование не доказывают ровно ничего.

**Партиция считается по значению, не по диапазону дат внутри строки.**
Фильтр `WHERE txn_date = '2025-06-15'` на партиционированной таблице
задействует partition pruning напрямую: BigQuery видит границу партиции
в самом плане запроса до чтения данных. Фильтр через функцию над
колонкой (`WHERE EXTRACT(MONTH FROM txn_date) = 6`) partition pruning
**не** задействует — колонка обёрнута выражением, и BigQuery не может
сопоставить его с границами партиций без вычисления самого выражения
по каждой строке.

## 1.3. Разобранный пример на сквозном датасете

Переписанный запрос — та же логика, что в `step-02.md`, на новой
таблице:

```sql
SELECT account_id, SUM(amount) AS day_total
FROM fintech.transactions_optimized
WHERE txn_date = '2025-06-15'
GROUP BY account_id
ORDER BY day_total DESC;
```

731 партиция равного объёма (`step-00.md`: 6000 строк на партицию без
исключений) означает, что фильтр на одну дату структурно читает 1
партицию из 731 — сокращение, кратное числу партиций при равномерном
распределении. Порог умения E1 — **≥5×**; конструкция датасета даёт
многократный запас над порогом, а не число, балансирующее у него.

**Точные байты — из собственного прогона, не из этого текста.** Автор
модуля не имеет доступа к консоли BigQuery (`step-00.md`) и не может
подставить сюда реальные килобайты/мегабайты обоих запросов. Критерий
шага требует зафиксировать оба числа скриншотом — это первое измерение
модуля, которое существует только в вашей копии.

## 1.4. Задание

1. Напишите `work\optimized_query.sql` — тот же запрос, что
   `baseline_query.sql` шага 02, с заменой только имени таблицы на
   `fintech.transactions_optimized`. Дата фильтра — та же самая, что в

3. Сохраните скриншот **обоих** оценок рядом — старой (из
   `step-02.md`) и новой — в `program\M7\work\comparison.png`. Кратность
   падения посчитайте сами: старое число делённое на новое.
4. Впишите оба числа и кратность в комментарий в начале
   `optimized_query.sql`.
5. Проверьте план запроса: в консоли, вкладка Execution details (после
   реального запуска, не только оценки) должно быть видно число
   просканированных партиций — 1 из 731, а не 731 из 731.
6. Коммит:

## 1.5. Критерий готовности

Три проверки, каждая — «да/нет» без второго человека.

| Проверка | Эталон | Допуск |
|---|---|---|
| кратность падения (старое число / новое, оба в одной единице измерения) | ≥5× | меньше 5× — либо фильтр не по партиционирующей колонке в одном из двух запросов, либо единицы измерения перепутаны (KiB против MiB) |
| `optimized_query.sql` и `baseline_query.sql` фильтруют по одной и той же дате | совпадают дословно | разные даты — сравнение недействительно |
| скриншот `comparison.png` существует и содержит оба числа | файл на месте, оба значения читаемы | отсутствие любого из двух — недостаточно для доказательства |

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 2 ошибки
этого шага, каждую с признаком, по которому её видно в своём результате.

## 1.6. Типичные ошибки

Обе — выведены из документированного механизма partition pruning, не
измерены прогоном (`step-00.md`).

**Ошибка:** фильтруете по дате через функцию, например
`WHERE EXTRACT(DATE FROM created_at) = '2025-06-15'` или
`WHERE CAST(txn_date AS STRING) = '2025-06-15'`, вместо прямого
сравнения `txn_date = '2025-06-15'`.
**Почему выглядит правильно:** запрос синтаксически верен и вернёт тот
же результат. С точки зрения ответа разницы действительно нет.
**Почему неправильно:** BigQuery не может сопоставить произвольное
выражение над колонкой с границами партиций без вычисления этого
выражения для каждой строки — partition pruning не срабатывает, и
объём сканирования остаётся таким же, как на неразмеченной таблице,
несмотря на то что таблица партиционирована. Падение будет заметно
ниже 5×, часто около 1× (без выигрыша вовсе).
**Как правильно:** фильтр — прямое сравнение партиционирующей колонки с
литералом или параметром, без обёртывающих функций.

**Ошибка:** сравниваете число байт с числом мегабайт (или гигабайт),
не приведя к одной единице.
**Почему выглядит правильно:** оба числа пришли из одного и того же
валидатора — значит, и сравнивать их можно напрямую.
**Почему неправильно:** валидатор подбирает единицу измерения по
величине числа (KiB, MiB, GiB) — 623.1 KiB и 4.2 MiB на глаз может
показаться «почти тем же порядком», хотя формально 4.2 MiB ≈ 4301 KiB —
разница почти в 7 раз, легко перепутать местами при беглом чтении.
**Как правильно:** привести оба числа к одной единице (например, байтам)
перед делением; вкладка Details выполненного запроса показывает точное
число байт без сокращённых единиц.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы партиционировали таблицу по дате, но запрос, который
раньше был медленным и дорогим, не стал ни быстрее, ни дешевле. С чего
начнёте искать причину?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Проверяет, фильтрует ли запрос вообще по партиционирующей колонке —
   партиционирование без соответствующего фильтра ничего не даёт для
   конкретного запроса.
2. Проверяет, не обёрнута ли партиционирующая колонка в фильтре
   функцией или преобразованием типа — это отключает partition pruning
   даже при формально верном фильтре.
3. Смотрит в план выполнения (Execution details), сколько партиций
   реально прочитано, а не полагается на предположение, что
   партиционирование «просто работает» само по себе.
4. Отмечает, что «быстрее» и «дешевле» — не одно и то же: партиционирование
   влияет на объём прочитанных данных (стоимость), а скорость дополнительно
   зависит от доступных слотов и объёма самого запроса — падение
   стоимости не всегда пропорционально падению времени выполнения.
