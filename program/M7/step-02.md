## 1.1. Цель и связь с умением

Умение E1 части 1 blueprint: «Загружает... таблицу, создаёт
партиционированную и кластеризованную, переписывает запрос... Объём
сканирования падает ≥5×». Шаг закрывает первую половину: видит, сколько
стоит запрос на таблице без партиционирования, и строит вторую таблицу
правильно. Доказательство падения объёма — `step-03.md`.

## 1.2. Теория своими словами

**BigQuery — колоночное хранилище: запрос читает колонки, а не строки.**
Прежде чем считать объём сканирования запроса, нужно знать, что он вообще
значит: колонка `amount` хранится физически отдельно от `txn_date`, и
запрос, использующий только эти две, не трогает остальные пять на диске
— подробно в E2, `step-04.md`. Здесь важно другое следствие: объём
сканирования запроса без фильтра по партиционирующей колонке равен сумме
объёма всех использованных колонок **по всей таблице**, независимо от
того, сколько строк вернёт результат.

**Партиционирование делит таблицу на физические сегменты по значению
колонки.** [Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables):
запрос, фильтрующий по партиционирующей колонке, «can scan the
partitions that match the filter and skip the remaining partitions» —
partition pruning. В этом датасете партиционирование по `txn_date` делит
4 386 000 строк на 731 сегмент по 6000 строк каждый.

**Кластеризация сортирует данные внутри партиции физически.** Она не
уменьшает число партиций, а помогает запросам, дополнительно
фильтрующим или группирующим по кластеризующей колонке (здесь —
`account_id`) внутри уже выбранных партиций.

**Стоимость видна до запуска запроса.**
[Estimate and control costs](https://docs.cloud.google.com/bigquery/docs/estimate-costs):
редактор запросов в консоли проверяет синтаксис на лету и печатает
«This query will process **623.1 KiB** when run» рядом со значком
галочки — до нажатия Run. Это и есть измерение, которое требует
критерий шага: не время выполнения, а объявленный объём сканирования.

## 1.3. Разобранный пример на сквозном датасете

**Базовый запрос — оборот за один день, без партиционирования:**

```sql
SELECT account_id, SUM(amount) AS day_total
FROM fintech.transactions_raw
WHERE txn_date = '2025-06-15'
GROUP BY account_id
ORDER BY day_total DESC;
```

На таблице без партиционирования BigQuery не может пропустить ни одной
строки заранее: колонки `account_id`, `amount`, `txn_date` читаются по
всем 4 386 000 строкам, что бы ни стояло в `WHERE`. Оценка объёма
(значок валидатора) для этого запроса и есть число, которое фиксируется
в 1.4 — оно зависит от типов и физического размера трёх колонок по
всей таблице и не предсказывается автором посимвольно (`step-00.md`).

**Создание партиционированной и кластеризованной таблицы:**

```sql
CREATE TABLE fintech.transactions_optimized
PARTITION BY txn_date
CLUSTER BY account_id
AS SELECT * FROM fintech.transactions_raw;
```

`PARTITION BY txn_date` требует, чтобы колонка была `DATE`, `TIMESTAMP`
или `DATETIME` (здесь — `DATE`, ровно то, что нужно) — до 4000 партиций
на таблицу без явного запроса лимита выше, 731 партиция этого датасета
далеко внутри лимита. `CLUSTER BY account_id` сортирует строки внутри
каждой партиции по значению счёта.

## 1.5. Критерий готовности

Четыре проверки, каждая — «да/нет» без второго человека.

| Проверка | Эталон | Допуск |
|---|---|---|
| `work\baseline_query.sql` содержит фильтр по `txn_date` и не содержит `_PARTITIONTIME`/`_PARTITIONDATE` | запрос читает `transactions_raw`, не `transactions_optimized` | несоответствие — измеряется не тот запрос |
| оценка валидатора для базового запроса записана в комментарии файла | число присутствует, с единицей измерения (KiB/MiB/GiB) | отсутствие числа или единицы — шаг не сдан |
| `fintech.transactions_optimized` существует, партиционирована по `txn_date` | видно в панели Details таблицы в консоли: `Partitioned by DAY on txn_date` | несоответствие означает пропущенный `PARTITION BY` |
| строк в `transactions_optimized` | 4 386 000 | точное совпадение с `transactions_raw` — `CREATE TABLE AS SELECT` не должен терять строки |

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 2 ошибки
этого шага, каждую с признаком, по которому её видно в своём результате.

## 1.6. Типичные ошибки

Обе — не измерены прогоном (доступа к консоли нет, `step-00.md`), а
выведены из документированного поведения DDL; помечены явно, а не
выданы за измеренные (решение 28 требует различать эти два класса).

**Ошибка:** партиционируете по `account_id`, а не по `txn_date`.
**Почему выглядит правильно:** `account_id` тоже часто используется в
фильтрах, и кажется естественной колонкой для партиционирования —
разбить таблицу «по тому, с чем работаем чаще всего».
**Почему неправильно:** `PARTITION BY` в BigQuery принимает только
`DATE`/`TIMESTAMP`/`DATETIME`-колонку без модификации выражением (или
`INT64`-колонку с явно заданным диапазоном через `RANGE_BUCKET`, здесь
не тот случай) — `account_id` типа `STRING` не подходит вовсе,
`CREATE TABLE` завершится ошибкой на этапе выполнения, а не тихо
проигнорирует запрос.
**Как правильно:** партиционировать по колонке дат (`txn_date`), а
`account_id` — кластеризовать (`CLUSTER BY`), которая работает с любым
типом, включая `STRING`.

**Ошибка:** после `CREATE TABLE ... AS SELECT` не проверяете число строк
в новой таблице, полагаясь на то, что запрос выполнился без ошибок.
**Почему выглядит правильно:** «выполнилось без ошибок» — обычный
сигнал успеха для DDL-команд в других СУБД.
**Почему неправильно:** `CREATE TABLE ... AS SELECT` не проверяет, что
исходный запрос вернул ожидаемое число строк, — например, случайно
добавленный `WHERE` или `LIMIT` в `SELECT` даст новую таблицу меньше
исходной без единого предупреждения: DDL успешно выполнится и создаст
таблицу с любым числом строк, которое вернул `SELECT`.
**Как правильно:** контрольный запрос из `step-01.md` — тот же, что
сверял исходную таблицу, применить и к новой.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Таблица на несколько миллионов строк, запросы почти всегда
фильтруют по дате операции. Партиционировать её или нет — и по какой
колонке?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Партиционировать — да, именно потому что фильтр по дате есть почти
   всегда: partition pruning пропускает нерелевантные сегменты целиком.
2. Партиционирующая колонка — сама колонка даты (или конвертируемая в
   дату), не производное выражение над ней: партиционирование требует
   типа `DATE`/`TIMESTAMP`/`DATETIME` или явного `INT64`-диапазона.
3. Называет дополнительную кластеризацию по второй часто используемой
   колонке фильтра (не дата) как отдельный, совместимый механизм — не
   альтернативу партиционированию, а дополнение к нему.
4. Отмечает, что партиционирование без соответствующего фильтра в
   запросе ничего не даёт — если запрос не фильтрует по дате, разбиение
   на партиции не сокращает объём сканирования этого конкретного
   запроса.
