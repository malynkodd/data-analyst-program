# Эталонные ответы модуля M7 (BigQuery / DWH)

**Отличие от M0–M6, названо прямо.** Все числа в этом файле, кроме
контрольной точки датасета, — не результат прогона (у среды написания
модуля нет доступа к консоли BigQuery, `step-00.md`), а гарантированное
свойство SQL-схемы: партиционирование по дню на 731 равный по объёму
партиции структурно даёт кратность сокращения сканирования, кратную
числу партиций, при фильтре на одну дату — это следует из документированного
механизма partition pruning
([Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables):
BigQuery «can scan the partitions that match the filter and skip the
remaining partitions»), а не из измерения. Точные байты, время
выполнения и денежная стоимость — то, что учащийся получает из
собственного прогона и фиксирует скриншотом (критерии шагов 02–04).

## Контрольная точка — сверять ДО задач шагов 02–04

Результат запроса из `generate_m7.sql` (раздел «Контрольная точка»),
арифметика проверена независимо от BigQuery (`731 × 6000`, построчная
симуляция уникальности `txn_id`, без RAND-зависимых полей):

| Показатель | Значение |
|---|---|
| `rows_total` | 4 386 000 |
| `unique_ids` | 4 386 000 |
| `unique_dates` | 731 |
| `min_date` | 2024-01-01 |
| `max_date` | 2025-12-31 |
| `accounts` | 500 |

Расхождение `rows_total` ≠ `unique_ids` при совпадении общего числа
строк — признак того, что скрипт создания выполнен без
`CREATE OR REPLACE` дважды (`step-01.md`, 1.6): в этом случае оба числа
будут **8 772 000**, ровно вдвое больше эталона.

## Шаг 02–03 (E1) — гарантия конструкции, не измерение

731 партиция, каждая ровно **6000** строк (`GENERATE_ARRAY(1, 6000)` без
исключений на каждый день). Запрос с фильтром `WHERE txn_date =
<конкретная дата>` на партиционированной таблице структурно читает
1 партицию из 731 — при равномерном распределении (гарантированном
конструкцией, не выборкой) это **731×** сокращение объёма, с огромным
запасом относительно порога умения E1 (**≥5×**). Точное число байт до и
после — из собственного прогона учащегося, критерий шага требует
скриншот обоих чисел, а не совпадения с этим файлом.

Кластеризация (`CLUSTER BY account_id`) не сокращает сканирование при
фильтре только по дате — она даёт эффект на запросах, дополнительно
фильтрующих по счёту внутри даты или диапазона дат; это направление, а
не число, следует из документации BigQuery по кластеризации, ссылка —
`step-02.md`.

## Шаг 04 (E2) — стоимость запроса

Верифицированные фактом из документации утверждения (не измерение):

1. **On-demand pricing** тарифицируется по объёму прочитанных данных, с
   бесплатным лимитом 1 ТиБ в месяц (то же число, что лимит sandbox —
   1 ТБ обработанных данных, `step-00.md`). Точный тариф за ТиБ сверх
   лимита — проверять на [BigQuery pricing](https://cloud.google.com/bigquery/pricing)
   на момент прохождения шага, а не по числу, зафиксированному здесь: он
   меняется со временем, и хранить его в тексте шага означало бы
   гарантированно устаревающее число.
2. **`SELECT *` читает все колонки таблицы целиком**, независимо от
   того, сколько строк вернёт `LIMIT`:
   [Control projection](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-input)
   — «Applying a LIMIT clause to a SELECT * query does not affect the
   amount of data read. You are billed for reading all bytes in the
   entire table». В датасете модуля — 7 колонок; запрос, которому нужны
   `txn_date` и `amount`, при `SELECT *` платит за все семь вместо двух.
