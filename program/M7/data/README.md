# Сквозной датасет модуля M7 (BigQuery / DWH)

## Статус этого файла

Полная декларация — `program/M7/step-00.md`, раздел «Отступление от
конвенции модуля»: здесь нет `raw/`, нет sha256 и нет `ref_*.csv`. Датасет
живёт внутри BigQuery как таблица, а не как файл на диске — читать
причину стоит там, а не пересказывать здесь.

Домен — fintech (решение 21, п. 2): условная таблица транзакций, 731 день
(2024-01-01…2025-12-31), 6000 операций на день без исключений.

## Файлы

| Файл | Роль | В git? |
|---|---|---|
| `generate_m7.sql` | Единственный генератор: один запрос `CREATE TABLE ... AS SELECT` с `GENERATE_ARRAY`/`UNNEST`, выполняется в консоли BigQuery. Не Python, не CSV — датасет никогда не существует файлом. | да |
| `reference_answers.md` | Контрольная точка (число строк, границы дат, число счетов) и то, что гарантировано конструкцией датасета, а не измерено прогоном (в этом модуле у автора нет доступа к BigQuery — `step-00.md`). | да |

Сам датасет — таблица `fintech.transactions_raw` в проекте учащегося,
никогда не коммитится: коммитить в BigQuery нечего, это не файл.

## Проверка строк

Раздела нет: в этом модуле нет `ref_*.csv`, которые можно было бы
сверить построчно (`tools/check_consistency.py`, `check_data_readme_rows()`
пропускает файлы без этого раздела — не ошибка, а честное отсутствие
второго слоя проверки там, где сверять нечего).

## Как воспроизвести с нуля

1. Открыть [console.cloud.google.com/bigquery](https://console.cloud.google.com/bigquery),
   войти Google-аккаунтом, принять условия sandbox-режима — карта не
   требуется.
2. Скопировать `generate_m7.sql` в редактор запросов, выполнить целиком.
3. Сверить контрольный запрос из `reference_answers.md` с числами там же.

Других команд нет — весь модуль работает внутри консоли BigQuery, без
локального окружения.
