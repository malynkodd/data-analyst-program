# M1.2. Фиксирует определение до расчёта и показывает, что выбор меняет ответ

Умение: A5 (вторая половина: «письменно фиксирует определение в 1
предложении **до** написания запроса»; первая половина — уточняющие
вопросы — закрыта в M1.1)
Модуль: M1
Требуется до этого: M1.1; M0 целиком, включая `git init`/`add`/`commit`
(решение 14, `design/decisions.md`) — теперь жёсткая зависимость части
3.2 blueprint, не факт без строки в карте
Время: 3.5–4.5 ч (оценка проектная, требует калибровки)

## 1.1. Цель и связь с умением

После шага вы фиксируете определение метрики одним предложением до того,
как считаете число, и показываете, что при другом определении число
меняется. Это вторая половина A5. Официальная проверка A5 в части 1
blueprint — «по истории коммитов»: с решением 14 (Git перенесён в M0)
это уже не метафора, а буквальная механика этого шага — определение и
результат фиксируются двумя разными коммитами, и порядок коммитов в
`git log` доказывает, что было раньше.

## 1.2. Теория своими словами

Определение, записанное после того, как вы уже увидели число на экране,
почти всегда подгоняется под увиденное — не намеренно, а потому что мозг
ищет объяснение задним числом. Единственный способ доказать (себе или
кому-то ещё), что определение было первым, — зафиксировать его отдельным
коммитом и иметь коммит с результатом позже в истории.

`git log --format=%ct --reverse -- <файл>` печатает время (в секундах от
начала эпохи Unix) всех коммитов, тронувших этот файл, от самого раннего
к самому позднему — команда самого git, а не внешний инструмент, поэтому
её поведение не зависит от того, запущена она из PowerShell или из Git
Bash (решение 13). Если первый коммит, тронувший `definition.md`, раньше
первого коммита, тронувшего `results.txt`, — определение предшествовало
расчёту.

## 1.3. Разобранный пример на сквозном датасете

Файлы: `program/M1/data/clients.csv` (не менять), `count_active.py`,
`reference_answers.md` — тот же датасет, что в M1.1. Репозиторий уже
инициализирован в M0.

Шаг 1 — записать определение и закоммитить, ничего не считая:

```
$ git add definition.md
$ git commit -m "definition: active client = login or payment within 60 days, include trial"
```

(текст самого определения — в `definition.md`, одним предложением: «Активный
клиент — тот, кто заходил в систему или платил в последние 60 дней,
включая пробных, исключая полностью отменённые».)

Шаг 2 — посчитать по этому определению:

```
$ python3 count_active.py clients.csv --by combo --within 60 --include-trial > results.txt
```

Шаг 3 — посчитать по одному альтернативному определению (меняем ось
источника сигнала: только формальный статус, без учёта пробных) и
закоммитить оба результата вместе:

```
$ python3 count_active.py clients.csv --by status >> results.txt
$ git add results.txt
$ git commit -m "results: two definitions compared"
```

В `results.txt`:

```
rows in input file: 240
active by this definition: 133
rows in input file: 240
active by this definition: 112
```

Разница — 21 клиент (133 против 112). Это ровно число пробных аккаунтов
(`trial` = 21 в этом датасете, `data/reference_answers.md`): все 21 вошли
в систему не позднее 14 дней назад, то есть попадают в любое поведенческое
определение, но полностью выпадают из подсчёта «только по статусу
`active`», потому что их статус — `trial`, а не `active`.

Шаг 4 — доказать порядок по истории коммитов:

```
$ git log --oneline
7bc082d results: two definitions compared
def412a definition: active client = login or payment within 60 days, include trial
$ git log --format=%ct --reverse -- definition.md
1785394230
$ git log --format=%ct --reverse -- results.txt
1785394233
```

1785394230 < 1785394233 — первый коммит, тронувший `definition.md`,
раньше первого коммита, тронувшего `results.txt`. Определение
действительно предшествовало расчёту, и это видно в истории, а не только
со слов.

## 1.4. Задание

Придумайте своё собственное определение «активного клиента» (может
совпадать по смыслу с примером выше, но сформулируйте его сами, одним
предложением). Порядок обязателен:

1. Запишите определение в `definition.md`, закоммитьте отдельным
   коммитом с содержательным сообщением (не «fix»/«update») — и только
   после этого переходите к шагу 2.
2. Запустите `count_active.py` с флагами, которые **точно** соответствуют
   написанному определению (если в определении сказано «включая
   пробных» — флаг `--include-trial` обязан стоять). Вывод — в
   `results.txt` (`>`).
3. Измените одну содержательную ось определения (не косметический сдвиг
   вроде 60→61 день, а именно ось: время / источник сигнала / состав
   базы) и запустите скрипт второй раз с новыми флагами. Вывод — той же
   командой (`>>`) в `results.txt`.
4. Закоммитьте `results.txt` отдельным коммитом.
5. Сравните два числа, посчитайте разницу.
6. Проверьте порядок: `git log --format=%ct --reverse -- definition.md` и
   тот же вызов для `results.txt` — первое число должно быть меньше.

## 1.5. Критерий готовности

- В истории репозитория есть коммит, добавляющий/меняющий `definition.md`,
  и отдельный, более поздний коммит, добавляющий/меняющий `results.txt`.
- Ни один из этих двух коммитов не имеет сообщения «fix» или «update».
- `git log --format=%ct --reverse -- definition.md` (первая строка)
  строго меньше `git log --format=%ct --reverse -- results.txt` (первая
  строка).
- `results.txt` содержит ровно 2 блока вывода `count_active.py`.
- Флаги второго запуска отличаются от первого хотя бы по одной оси
  (время / источник сигнала / состав базы), не только по числовому
  параметру окна.
- Два числа в `results.txt` различаются (расхождение ≠ 0).
- Уложились в ≤45 минут.

**Не сошлось — не переделывайте вслепую:** раздел 1.6 разбирает 4 ошибки
этого шага, каждую с признаком, по которому её видно в своём результате.

## 1.6. Типичные ошибки

**Ошибка:** запускаете `count_active.py`, смотрите на число, только потом
пишете и коммитите `definition.md`, описывая словами то, что уже увидели.
**Почему выглядит правильно:** итоговый текст читается так же, как если
бы был написан заранее.
**Почему неправильно:** `git log --format=%ct --reverse` для
`results.txt` в этом случае даёт число меньше, чем для `definition.md` —
проверка ловит это напрямую, потому что коммит с результатом лежит в
истории раньше. Соблазн особенно велик именно на этом датасете: разница
между определениями доходит до 55 клиентов (112 против 167, `M1.1`) —
есть, под что подгонять формулировку.
**Как правильно:** писать и коммитить `definition.md` первым коммитом,
и только после этого запускать скрипт.

**Ошибка:** пишете `definition.md` и `results.txt`, но коммитите оба разом
одним коммитом («так быстрее»).
**Почему выглядит правильно:** оба файла всё равно оказываются в
репозитории, содержимое то же самое.
**Почему неправильно:** `git log --format=%ct --reverse -- definition.md`
и та же команда для `results.txt` дают **одно и то же** число — оба файла
в одном коммите, порядок «определение до расчёта» технически не
зафиксирован, коммит не доказывает, что определение было первым, а не
дописано по факту увиденного числа.
**Как правильно:** два отдельных коммита, определение — раньше.

**Ошибка:** меняете между двумя прогонами только числовой параметр окна на
соседнее значение (например, `--within 59` и `--within 61`).
**Почему выглядит правильно:** флаги формально разные, числа на выходе
тоже могут отличаться.
**Почему неправильно:** на этом датасете разница между окном 59 и 61 день
— 1 клиент (154 против 155, `data/reference_answers.md`). Это шум, а не
доказательство, что определение имеет значение.
**Как правильно:** менять содержательную ось — например, 30 дней против
90, или статус против поведения, а не соседние числа одного окна.

**Ошибка:** запускаете `--by combo` без `--include-trial`, думая, что
`combo` уже означает «самое полное» определение.
**Почему выглядит правильно:** режим называется «комбинированный», кажется
максимально широким по умолчанию.
**Почему неправильно:** без `--include-trial` результат `combo`-режима на
этом датасете равен 112 — то есть совпадает с чистым подсчётом по
статусу, потому что все 21 пробных клиента исключены из базы независимо
от их поведения. «Комбинированный» относится к источнику сигнала
(логин или платёж), а не к составу базы — это две разные оси.
**Как правильно:** явно решить состав базы отдельным флагом, не полагаясь
на название режима.

## 1.7. Честная оценка времени

3.5–4.5 ч. Оценка проектная, требует калибровки (`research/self.md`) —
строка M1 в части 6.1 blueprint помечена «Требуется», и ориентира у неё
нет ни в [М], ни в [К]. Из чего складывается:

| Слагаемое | Часы |
|---|---|
| чтение 1.2: почему порядок «определение → расчёт» проверяется историей коммитов | 0,75–1 |
| разбор примера 1.3: 133 против 112 и откуда 21 клиент разницы | 0,5 |
| задания 1–2: своё определение, коммит, первый запуск | 0,75 |
| задания 3–4: смена оси, второй запуск, второй коммит | 0,5–0,75 |
| задания 5–6: разница чисел и проверка порядка через `git log --format=%ct` | 0,5 |
| разбор несовпадений по 1.6 (четыре ошибки) | 0,5–0,75 |

Разрыв между вилкой (3,5–4,5 ч) и нормативом заданий (≤45 мин) —
самый большой в модуле, и он объясним: сами команды выполняются за
минуты, а время уходит на формулировку определения, которое переживёт
проверку флагами, и на разбор того, почему второй запуск дал ту же
цифру, если ось выбрана косметически.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы получили два разных числа по одной и той же метрике от
двух коллег. Как узнать, кто прав?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Спрашивает определение метрики у каждого — дословно, а не «в целом
   одно и то же».
2. Ищет расхождение по конкретной оси: период, источник сигнала, состав
   базы.
3. Не считает, что один из них ошибся математически, пока не исключил,
   что они считали разные вещи.
4. Предлагает зафиксировать одно согласованное определение письменно,
   прежде чем пересчитывать.
