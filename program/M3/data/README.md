# Сквозной датасет модуля M3 (частичная декларация — пилот одного шага)

## Статус этого файла

Правило части 1.3 curriculum-design требует, чтобы сквозной датасет
модуля был объявлен **один раз, в шаге 0**, до первого шага модуля. В
этом пилоте написан только один образец шага (`step-05.md`, умение A2),
остальные шаги M3 не существуют. Поэтому это не полноценная декларация
"шага 0" модуля, а её частичный слепок — минимум, нужный для одного
написанного шага. Когда будут писаться остальные шаги M3, эта схема
почти наверняка потребует расширения: A1 explicitly требует «схему из
5 таблиц», здесь их только 2 (`customers`, `orders`).

Команда `sqlite3 m3.db ".read schema.sql"` в `step-05.md` намеренно не
использует `<`-редирект — в PowerShell он ведёт себя не так, как в
bash (решение 13, `design/decisions.md`). `.read` — внутренняя команда
самого `sqlite3`, одинаковая в любом шелле.

## Файлы

| Файл | Роль |
|---|---|
| `schema.sql` | `CREATE TABLE` для `customers` и `orders`. |
| `seed.sql` | Детерминированные `INSERT` — 12 клиентов, 17 заказов. Числа не случайны, не требуют генератора: набор подобран вручную так, чтобы дать ровно 5 клиентов, теряющихся на типичном баге LEFT JOIN + WHERE (умение A2). |

## Инструмент: sqlite3 CLI

Решение, не зафиксированное в `design/blueprint.md` или
`design/decisions.md`: какой SQL-движок использовать в M3, источники не
называют. Для этого пилота выбран `sqlite3` — однофайловая база без
сервера, кроссплатформенный CLI. На части систем (в частности, чистый
Windows без Git Bash/WSL) `sqlite3` не установлен по умолчанию — установка
станет отдельным пунктом инструкции M3.00 / M0, когда модуль будет
дописан полностью. Установка проверена не была: в среде написания
этого пилота `sqlite3` тоже не был найден (`which sqlite3` →
`command not found`), схема и данные проверялись через встроенный в
Python модуль `sqlite3` — но это инструмент автора для проверки чисел,
а не то, чем пользуется учащийся: Python как инструмент вводится в M5,
после M3, использовать его здесь для решения задания было бы нарушением
порядка модулей.

## Устройство данных

`customers` — 12 строк, `customer_id` 1–12. `orders` — 17 строк, статусы
`completed` / `cancelled` / `pending`. Встроенная неоднозначность:

- `customer_id` 4 и 10 — заказов нет вовсе.
- `customer_id` 6 и 11 — заказы есть, но все `cancelled`.
- `customer_id` 7 — заказ есть, но `pending`.

Итого 5 клиентов из 12 пропадают из результата, если фильтр
`WHERE o.status = 'completed'` стоит после `LEFT JOIN`, а не в `ON`.
Контрольная сумма выручки по `completed`-заказам — 8600.00 — совпадает
и в сломанном, и в исправленном запросе: сумма не ловит баг, ловит
только количество строк. Числа проверены выполнением обоих вариантов
запроса (см. `step-05.md`, 1.3).
