# Сквозной датасет модуля M3

## Статус этого файла

Правило части 1.3 curriculum-design требует, чтобы сквозной датасет
модуля был объявлен **один раз, в шаге 0**, до первого шага модуля.
Полная декларация — `step-00.md` (схема на 5 таблиц + раздел
«Дополнение» для данных A3/A4); этот файл — читаемое описание того же
датасета для человека, открывающего папку `data/`, не источник истины
второй раз. Модуль написан целиком, 12 шагов: `step-01.md`–`step-04.md`
(A2, части 1–4 из 5 — `SELECT`/`WHERE`/`ORDER BY`, `GROUP BY`/агрегаты,
`INNER JOIN`, корректный `LEFT JOIN`), `step-05.md` (A2, часть 5 из 5 —
финальная), `step-06.md` (A1), `step-07.md` (A3, часть 1 из 2),
`step-08.md` (A4, часть 1 из 2), `step-09.md` (**инфраструктура** —
установка PostgreSQL и перенос данных, умения не несёт, решение 23),
`step-10.md` (A2 на перенесённом коде — не часть разбивки, она завершена
на `step-05.md`), `step-11.md` (A3, часть 2 из 2), `step-12.md` (A4,
часть 2 из 2). Части 1–4 не добавляют новых таблиц или строк —
используют те же `customers`/`orders`/`order_items`/`payments`, что и
`step-05.md`.

Шаги 01–08 идут на SQLite, шаги 09–12 — на PostgreSQL: переход после
`step-08.md` (решение 15 задаёт сам переход, решение 19 — его момент,
`design/decisions.md`).

Команда `sqlite3 m3.db ".read schema.sql"` в `step-01.md` намеренно не
использует `<`-редирект — в PowerShell он ведёт себя не так, как в
bash (решение 13, `design/decisions.md`). `.read` — внутренняя команда
самого `sqlite3`, одинаковая в любом шелле.

**Файлы данных загружаются не все сразу**, а каждый в том шаге, где его
данные нужны впервые — таблица в разделе «Порядок загрузки» ниже.
Обоснование, почему порядок именно такой, — `step-00.md`, раздел
«Порядок загрузки данных по шагам».

## Два движка: SQLite (шаги 01–08) и PostgreSQL (шаги 09–12)

Выбор движков зафиксирован решением 15 `design/decisions.md` (SQLite на
входе, PostgreSQL к концу модуля) и решением 19 (переход после
`step-08.md`).

**SQLite.** Консольный клиент `sqlite3` в Windows не входит и в поставку
Python не входит тоже — модуль `sqlite3` стандартной библиотеки Python и
консольный клиент это разные программы. Схема, данные и все числа
эталонов посчитаны через библиотеку (версия 3.45.1); учащийся работает
клиентом.

**Пункт закрыт 2026-07-31** (был открыт с захода 6). Установка клиента
проверена ручным гейтом на живой машине — `research/tools-gate.md`,
раздел 1: `sqlite-tools-win-x64-3530400.zip` (6 557 792 байта),
распаковка четырёх `.exe` плоско, `PATH` на уровне пользователя, прав
администратора не требуется. Инструкция — `program/M3/step-01.md`, 1.3.
Формулировка решения 15 «ставится в 0 действий» относилась к библиотеке
и для клиента была неверна; поправка внесена в само решение.

**Режим вывода клиента.** Версия клиента на машине автора — 3.53.4. По
умолчанию он не печатает CSV ни в одном из двух режимов: интерактивно —
рамками с заголовками, запросом из аргумента — значениями через `|` без
заголовка. Для сверки с эталоном шаги задают `.mode csv`, `.headers on` и
`.once <файл>`; перенаправление вывода шелла (`>`) не годится — клиент
пишет свой `\r\n`, поверх которого стандартный вывод Windows добавляет
свой, и в файле оказывается двойной перевод строки (проверено прогоном).
Сама сверка — `compare_csv.py`, по значениям, а не по байтам.

**PostgreSQL.** Установка проверена: PostgreSQL 17.6 (x86_64-windows)
развёрнут из zip-архива бинарников без прав администратора, кластер
поднят, все числа разделов «Переход на PostgreSQL» в
`reference_answers.md` получены на нём. Путь через обычный установщик
EDB (основной в `step-09.md`) на этой машине не проверялся —
проверялся запасной, для случая без прав администратора.

## Устройство данных

`customers` — 12 строк, `customer_id` 1–12. `orders` — 19 строк, статусы
`completed` / `cancelled` / `pending`. Встроенная неоднозначность:

- `customer_id` 4 и 10 — заказов нет вовсе.
- `customer_id` 6 и 11 — заказы есть, но все `cancelled`.
- `customer_id` 7 — заказ есть, но `pending`.

Итого 5 клиентов из 12 пропадают из результата, если фильтр
`WHERE o.status = 'completed'` стоит после `LEFT JOIN`, а не в `ON`.
Контрольная сумма выручки по `completed`-заказам — 8600.00 — совпадает
и в сломанном, и в исправленном запросе: сумма не ловит баг, ловит
только количество строк. Числа проверены выполнением обоих вариантов
запроса (см. `step-05.md`, 1.3).

## Порядок загрузки (сверяется `tools/check_consistency.py`)

Источник истины по тому, какой шаг что загружает (решение 20
`design/decisions.md` — таблица живёт в одном экземпляре, здесь).
Формат строки:
`<шаг> | <что появляется в базе> | <файлы>`; в третьей колонке
учитываются только файлы `.sql` — генератор `activity_log` создаёт
таблицу сам и в накопительную сборку базы не входит.

| Шаг | Что появляется в базе | Файлы |
|---|---|---|
| `step-01.md` | 5 таблиц модуля, исходные 12 клиентов / 19 заказов | `schema.sql`, `seed.sql` |
| `step-07.md` | +240 клиентов / +347 заказов, 12 месячных когорт для A3 | `retention_seed.sql` |
| `step-08.md` | таблица `activity_log` для A4 | `generate_activity_log.py` |
| `step-14.md` | +`partner_registry` (12) и `invoice_feed` (60) для A7 | `registry_seed.sql` |

Шаги `step-02.md`–`step-06.md`, `step-09.md`–`step-13.md` новых данных
не добавляют: 02–06 работают на состоянии после `step-01.md`, 09–12 — на
перенесённой в PostgreSQL копии состояния после `step-08.md`, а
`step-13.md` — на состоянии после `step-07.md` в SQLite.

`tools/check_consistency.py` собирает по этой таблице накопительное
состояние базы для каждого шага и на нём выполняет эталонные запросы из
`reference_answers.md` — сверка описана там же, в маркерах `Эталон:`.

## Ручная проверка перед публикацией

Не каждый заход, а один раз перед выкладкой репозитория. Закрывает то,
чего `check_consistency.py` не покрывает и покрыть не может без
поднятого сервера: числа шагов `step-09.md`–`step-12.md` получены одним
прогоном на PostgreSQL 17.6, и автоматически их никто не сверяет.

1. Поднять PostgreSQL и собрать базу по `step-09.md`: `schema_pg.sql`,
   затем `export_for_postgres.py` и загрузка пяти CSV через `\copy` в
   порядке `customers`, `products`, `orders`, `order_items`, `payments`.
   Исходная `m3.db` — в состоянии 2 (после `retention_seed.sql`).
2. Сверить перенос с таблицей «Перенос (`step-09.md`)» в
   `reference_answers.md`: 252 / 6 / 366 / 23 / 13 строк,
   `SUM(amount)` = 317959.87 по 366 заказам и 8600.00 по
   `completed AND order_id < 200`, 0 заказов с расхождением
   `SUM(quantity*unit_price) <> amount`.
3. Прогнать все девять расхождений диалектов из таблицы «Девять
   расхождений диалектов (`step-10.md`)» и сверить построчно. Отдельно
   проверить № 5 (`LIKE 'COMPLETED'`): он единственный не падает с
   ошибкой — 360 строк в SQLite против 0 в PostgreSQL. Если какое-то из
   девяти начало вести себя иначе (новая мажорная версия PostgreSQL),
   это правка `step-10.md`, а не опечатка в числе.
4. Сверить A3 на PostgreSQL (`step-11.md`) с
   `a3_cohort_retention_m1.csv` и `a3_cohort_retention_m2.csv` — **по
   значениям, а не побайтово**: `NUMERIC(10,2)` печатает `35.00` там,
   где SQLite печатает `35.0`.
5. Сверить A4 на PostgreSQL (`step-12.md`): планы запросов из таблицы
   «Планы для `activity_log`» (`Seq Scan` → `Bitmap Heap Scan` →
   `Index Only Scan`, `Heap Fetches: 0`). Абсолютные секунды не
   сверяются — они зависят от железа; сверяются планы и порядок
   ускорения.

Расхождение на любом шаге — находка, а не шум: числа в шагах заявлены
как полученные прогоном, и если прогон их больше не даёт, неверен шаг.
