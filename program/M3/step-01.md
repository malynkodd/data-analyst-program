## 1.1. Цель и связь с умением

После шага вы по описанию задачи на естественном языке пишете `SELECT`
с условием `WHERE` (в том числе с несколькими условиями через `AND`/
`OR`) и явной сортировкой `ORDER BY`, точно зная, какие строки вернёт
запрос, не проверяя результат вслепую. Часть 1 из 5 умения A2 — общая
предпосылка: без этого невозможно ни писать корректные условия для
частей 2–5, ни опознать баг `WHERE`/`ON` из `step-05.md`.

## 1.2. Теория своими словами

`SELECT` возвращает набор колонок из таблицы. `WHERE` отбирает строки
до того, как они попадут в результат — условие вычисляется отдельно для
каждой строки таблицы.

При нескольких условиях через `AND` и `OR` приоритет вычисления такой
же, как у `*` и `+` в арифметике: `AND` вычисляется первым, `OR` —
вторым. Значит `A OR B AND C` читается как `A OR (B AND C)`, а не как
`(A OR B) AND C`. Если условие «B» задумано как ограничение для обеих
частей («A» и «B»), а не только для «B», без явных скобок оно
применится только к «B» — без единой синтаксической ошибки, запрос
выполнится и вернёт неверный, но правдоподобный результат.

`ORDER BY` задаёт порядок вывода явно. Без `ORDER BY` СУБД не обязана
возвращать строки в каком-то конкретном порядке — то, что маленькая
таблица «по ощущению» выводится в порядке вставки, свойство конкретного
движка и конкретного запроса на конкретный момент, а не гарантия языка
SQL, и полагаться на это нельзя.

### Шаг 1. Консольный клиент `sqlite3`

Он нужен до первой команды и его на машине может не быть. Проверьте:

```
$ sqlite3 --version
3.53.4 2026-07-24 19:02:57 bf7c7f30031888f4e796e429ab3978879485813aaca6f641c7b33e4e09459bcc (64-bit)
```

Если вместо номера версии выводится сообщение о том, что имя `sqlite3` не
распознано, — клиента нет. Его нет ни в Windows, ни в поставке Python, и
это не то же самое, что модуль `sqlite3` из стандартной библиотеки
Python: библиотекой считаются эталоны программы, а вы весь модуль будете
писать запросы в консольном клиенте. Это разные программы, и одна не
заменяет другую. Обходного пути через `python -m sqlite3` на этой машине
тоже нет: встроенный REPL появился в Python 3.12, здесь 3.11.9.

Установка — распаковка архива, без установщика и без прав
администратора:

1. Откройте [Precompiled Binaries for Windows](https://www.sqlite.org/download.html)
   и скачайте `sqlite-tools-win-x64-<версия>.zip` (около 6.6 МБ).
2. Распакуйте в любой каталог, куда у вас есть право на запись —
   например, `D:\sqlite-tools`. Внутри архива четыре `.exe` лежат плоско,
   без вложенной папки; нужен из них только `sqlite3.exe`.
3. Допишите этот каталог в `PATH` на уровне пользователя (не системы —
   для системного нужны права администратора). После этого команда
   `sqlite3` заработает в **новом** окне терминала; в уже открытом старое
   значение `PATH` останется.
4. Повторите `sqlite3 --version`. Клиент должен напечатать номер версии
   и завершиться.

Версия у вас будет новее той, на которой посчитаны эталоны модуля (3.45.1
— версия библиотеки, встроенной в Python автора). Для запросов этого
модуля разницы не ожидается: CTE поддержаны с 3.8.3, оконные функции — с
3.25. Если какой-то эталон не сойдётся, версия клиента — последнее, что
стоит проверять, а не первое.

### Шаг 3. Режим вывода, в котором результат сверяется с эталоном

Начиная со `step-06.md` критерии готовности требуют сверить вывод вашего
запроса с эталонным CSV из `program/M3/data`. Ни один режим вывода
клиента по умолчанию для этого не годится, и это стоит настроить один раз
сейчас, а не на шаге 06.

Клиент печатает результат по-разному в зависимости от того, как его
запустили. Запущенный интерактивно (`sqlite3 m3.db`, дальше запросы в
приглашении `sqlite>`), он рисует таблицу рамками:

```
╭──────────┬───────────┬────────╮
│ order_id │  status   │ amount │
╞══════════╪═══════════╪════════╡
│      111 │ pending   │  390.0 │
╰──────────┴───────────┴────────╯
```

Тот же запрос, переданный аргументом (`sqlite3 m3.db "SELECT ..."`),
печатает значения через `|` и без заголовка:

```
111|pending|390.0
```

Эталон — CSV с запятой и заголовком. Ни рамки, ни `|` с ним не
сравниваются. Нужный режим включается двумя точечными командами, а
результат отправляется в файл третьей:

```
sqlite> .mode csv
sqlite> .headers on
sqlite> .once my_task1.csv
sqlite> SELECT order_id, status, amount FROM orders WHERE status = 'pending';
```

`.once` направляет в файл **только следующий** запрос, дальше вывод снова
идёт на экран. Именно `.once`, а не перенаправление вывода шелла
(`> my_task1.csv`): клиент пишет конец строки сам, а стандартный вывод
Windows добавляет к нему свой, и в файле получается двойной перевод
строки. Через `.once` клиент пишет файл сам, и этого не происходит —
проверено прогоном.

Сравнивать файлы глазами не нужно и не следует: побайтово они не
совпадут, даже когда запрос верен. В режиме `csv` клиент берёт в кавычки
любое значение с пробелом или кириллицей (`Київ` выводится как `"Київ"`),
а в эталоне кавычек нет — по правилам CSV это одно и то же значение.
Сверку делает готовый скрипт `compare_csv.py` из того же каталога
(запускаете, не пишете — умение I2 из M0):

```
$ python compare_csv.py my_task1.csv a1_task1_running_total.csv
СОВПАДАЕТ: 13 строк, 5 колонок, расхождение 0.
```

При расхождении он печатает первую разошедшуюся строку и колонку:

```
РАСХОЖДЕНИЕ в строке 2, колонка 'running_total': у вас '850.0', в эталоне '2050.0'
```

На этом шаге сверять нечего — эталонных CSV у шагов 01–05 нет, их
критерии проверяются счётом строк. Режим настроен здесь потому, что здесь
единственное место модуля, где ставится и настраивается инструмент.

Задача: «Показать заказы, которые `pending` или `cancelled`, но только
с суммой больше 300».

Написанный «в лоб», без скобок, запрос:

```sql
SELECT order_id, status, amount
FROM orders
WHERE status = 'pending' OR status = 'cancelled' AND amount > 300;
```

Результат — 4 строки:

| order_id | status | amount |
|---|---|---|
| 111 | pending | 390.0 |
| 116 | pending | 260.0 |
| 117 | cancelled | 320.0 |
| 118 | cancelled | 410.0 |

Строка `116` (`pending`, `260.0`) не должна была попасть в результат —
`260 ≤ 300`. Причина: `AND` связал `amount > 300` только с
`status = 'cancelled'`, а условие на `pending` осталось без ограничения
по сумме — запрос фактически выполнил «`pending`, ЛЮБАЯ сумма, ИЛИ
`cancelled` с суммой больше 300».

Исправление — скобки вокруг `OR`-части:

```sql
SELECT order_id, status, amount
FROM orders
WHERE (status = 'pending' OR status = 'cancelled') AND amount > 300;
```

Результат — 3 строки:

| order_id | status | amount |
|---|---|---|
| 111 | pending | 390.0 |
| 117 | cancelled | 320.0 |
| 118 | cancelled | 410.0 |

Письменное объяснение (эталонная форма для 1.4): «`AND` вычисляется
раньше `OR`, поэтому `amount > 300` связался только с `cancelled`, а не
с обеими частями условия. Из-за этого заказ 116 (`pending`, 260)
попал в результат, хотя не проходит условие по сумме. Фикс — скобки
вокруг `status = 'pending' OR status = 'cancelled'`.»

## 1.5. Критерий готовности

- В сломанном запросе найдено, что он возвращает 13 строк — ровно все
  `completed`-заказы независимо от суммы (сравнение с `SELECT COUNT(*)
  FROM orders WHERE status='completed'` = 13, расхождение 0).

  Почему ровно 13, а не больше: правая часть условия
  (`status = 'pending' AND amount > 500`) на этих данных не даёт ни одной
  строки. `pending`-заказов два — 111 (390.0) и 116 (260.0), — и ни один
  не проходит `amount > 500`. То есть сломанный запрос вырождается в
  «все `completed`», и совпадение с `COUNT(*)` — следствие датасета, а не
  свойство ошибки. Это названо здесь вслух, потому что критерий от этого
  зависит: если правка `seed.sql` когда-нибудь добавит `pending`-заказ с
  суммой выше 500, число перестанет быть 13, и причина будет не в
  вас. Числа 111/390.0 и 116/260.0 — из раздела «Устройство данных»
  `program/M3/data/README.md`.
- Найдены все 3 строки, нарушающие условие `amount > 500`: `order_id`
  103 (430), 112 (455), 114 (330).
- Исправленный запрос возвращает ровно 10 строк, без этих трёх.
- Объяснение — не больше 3 предложений, называет приоритет `AND` перед
  `OR` или прямо указывает на отсутствие скобок как причину.
- Норматив: ≤30 минут (часть 1 из 5 проще финальной части A2 в
  `step-05.md`, порог снижен пропорционально; решение пилота, не строка
  источника).

## 1.6. Типичные ошибки

**Ошибка:** пишете условие с `AND`/`OR` без скобок, рассчитывая на
«естественный» порядок чтения слева направо.
**Почему выглядит правильно:** запрос синтаксически верен и
выполняется без ошибок.
**Почему неправильно:** на примере 1.3 это добавляет в результат
лишнюю строку 116 (260 ≤ 300); на задании 1.4 — три лишние строки
(103, 112, 114), не проходящие условие по сумме.
**Как правильно:** явно расставлять скобки вокруг части `OR`, если она
должна ограничиваться тем же дополнительным условием, что и вторая
часть.

**Ошибка:** полагается на порядок строк без `ORDER BY` — например,
считает, что первая строка в выводе `cancelled`-заказов будет
хронологически самой ранней.
**Почему выглядит правильно:** на этой таблице (4 строки `cancelled`)
вывод без `ORDER BY` действительно идёт в порядке вставки: 106, 110,
117, 118.
**Почему неправильно:** порядок по дате другой — 117 (2026-05-07), 110
(2026-05-22), 106 (2026-06-01), 118 (2026-06-09). Если код читает
«первую строку» без `ORDER BY order_date` и трактует её как самую
раннюю, он получает 106 вместо верных 117 — совпадение с порядком
вставки не гарантия, а факт текущего состояния таблицы, который
ломается при любой вставке или удалении строки.
**Как правильно:** если порядок имеет значение — всегда `ORDER BY`
явно по нужной колонке.

**Ошибка:** сравниваете строку без учёта регистра: `WHERE status =
'Completed'`.
**Почему выглядит правильно:** слово написано верно, только с большой
буквы — выглядит как стилевая деталь.
**Почему неправильно:** сравнение строк оператором `=` в SQLite
регистрозависимо. `WHERE status = 'Completed'` возвращает 0 строк —
вместо 13, которые возвращает `WHERE status = 'completed'`.
**Как правильно:** сверять точное значение, как оно записано в данных
(здесь — везде нижний регистр), а не полагаться на то, что выглядит
эквивалентным на глаз.

**Ошибка:** путаете `>` и `>=` на границе — например, ожидаете, что заказ
с суммой ровно 300 пройдёт условие `amount > 300`.
**Почему выглядит правильно:** «больше 300» на слух легко спутать с
«не меньше 300».
**Почему неправильно:** заказ 106 (`cancelled`, 300.0) не проходит
`amount > 300` (300 не больше 300), но прошёл бы `amount >= 300`.
В примере 1.3 это ровно тот заказ, который остаётся за бортом результата
из 4 `cancelled`-заказов — если ожидать 4 строки, а не 3, граница
операторов — первое, что нужно проверить.
**Как правильно:** сверять формулировку задачи буквально: «больше» —
`>`, «не меньше» / «от» — `>=`.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы написали `WHERE status = 'pending' OR status =
'cancelled' AND amount > 300` и получили на одну строку больше, чем
ожидали. С чего начнёте искать причину?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Проверяет приоритет `AND`/`OR` в условии — `AND` вычисляется первым.
2. Явно расставляет скобки и сравнивает результат до/после.
3. Смотрит на сами строки результата (не только на количество), чтобы
   найти конкретную лишнюю строку, а не гадать по сумме или счётчику.
4. Предлагает конкретный фикс — скобки вокруг `OR`-части, а не
   «переписать запрос иначе».
