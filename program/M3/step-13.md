## 1.2. Теория своими словами

**`EXISTS` спрашивает «есть ли хоть одна строка», а не «сколько».** Он
останавливается на первом совпадении и не тянет данные наружу — поэтому
`SELECT 1` внутри достаточно, и подставлять туда колонки бессмысленно.
`NOT EXISTS` — то же наоборот. Тот же результат даёт `LEFT JOIN … WHERE
правая IS NULL` (шаг `step-04.md`): выбор между ними — читаемость, а не
правильность.

**`NOT IN` ломается о `NULL`, и ломается молча.** Если подзапрос вернул
хотя бы один `NULL`, всё выражение `x NOT IN (…)` для любого `x` даёт
`NULL`, а не `TRUE` — потому что «x не равен неизвестному» неизвестно.
Строк на выходе становится **0**, ошибки нет. У `NOT EXISTS` этой
проблемы нет по устройству: он сравнивает не значения, а факт наличия
строки.

**`UNION` схлопывает дубликаты, `UNION ALL` — нет.** `UNION` неявно
делает `DISTINCT` по всем колонкам, то есть сортирует результат целиком.
На больших наборах это цена, которую платят зря, если дубликатов заведомо
нет. Правило: по умолчанию `UNION ALL`, а `UNION` — когда схлопывание
нужно и вы можете сказать, по каким колонкам.

**`CASE WHEN` внутри агрегата заменяет несколько запросов одним.**
`SUM(CASE WHEN условие THEN 1 ELSE 0 END)` даёт счётчик по условию в той
же строке результата, что и остальные счётчики. Ветви проверяются сверху
вниз до первой истинной — порядок условий часть логики.

**Self-join — соединение таблицы с собой под двумя псевдонимами.** Нужен
там, где сравниваются строки одной таблицы между собой: заказ и следующий
заказ того же клиента, сотрудник и его руководитель. Обязательное
условие — исключить пару строки с самой собой (`a.order_id <> b.order_id`)
и задать направление (`b.order_date > a.order_date`), иначе каждая пара
посчитается дважды.

**`LIMIT` возвращает первые N строк результата** и без `ORDER BY` не
означает ничего: «первые» определяются планом выполнения, а не данными.
Отличие от `ROW_NUMBER() ≤ N`: `LIMIT` режет весь результат, оконная
функция — внутри каждой группы. «Топ-5 по стране» — `LIMIT`, «топ-5 в
каждом городе» — окно.

Справочники: [SQLite expressions](https://sqlite.org/lang_expr.html)
(`EXISTS`, `IN`, `CASE`), [`SELECT`](https://sqlite.org/lang_select.html)
(`UNION`, `LIMIT`).

## 1.3. Разобранный пример на сквозном датасете

Прогон на машине автора 2026-08-24, SQLite 3.45.1, база в состоянии
после `step-07.md`: 252 клиента, 366 заказов, 13 платежей.

**Ловушка `NOT IN`, измеренная на этих данных.** Вопрос: сколько заказов
не имеют ни одного платежа. Три записи одного и того же вопроса:

```sql
-- (1) подзапрос над LEFT JOIN может вернуть NULL
SELECT COUNT(*) FROM orders
WHERE order_id NOT IN (SELECT p.order_id FROM orders o
                       LEFT JOIN payments p ON p.order_id = o.order_id);
-- (2) то же, но NULL отфильтрован
SELECT COUNT(*) FROM orders
WHERE order_id NOT IN (SELECT p.order_id FROM orders o
                       LEFT JOIN payments p ON p.order_id = o.order_id
                       WHERE p.order_id IS NOT NULL);
-- (3) NOT EXISTS
SELECT COUNT(*) FROM orders o2
WHERE NOT EXISTS (SELECT 1 FROM payments p WHERE p.order_id = o2.order_id);
```

```
(1) 0
(2) 353
(3) 353
```

Первый запрос **не падает и не предупреждает**. Он возвращает ноль строк —
и ноль читается как «таких заказов нет», то есть как содержательный ответ.
Разница между 0 и 353 — вся разница между «у нас всё оплачено» и «оплачено
13 заказов из 366».

**`CASE WHEN` в агрегате: три счётчика одним проходом.**

```sql
SELECT c.city,
       SUM(CASE WHEN o.amount <  500 THEN 1 ELSE 0 END) AS small,
       SUM(CASE WHEN o.amount >= 500 AND o.amount < 1000 THEN 1 ELSE 0 END) AS medium,
       SUM(CASE WHEN o.amount >= 1000 THEN 1 ELSE 0 END) AS large
FROM orders o JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status = 'completed'
GROUP BY c.city ORDER BY c.city;
```

```
Дніпро   14  27  36
Київ     10  25  31
Львів    11  24  23
Одеса    20  28  37
Харків   17  32  25
```

Тот же результат тремя отдельными запросами — три прохода по таблице и
три набора строк, которые потом надо совмещать руками.

**`UNION` против `UNION ALL` на одном и том же вопросе.** «Клиенты,
делавшие заказы в 2025 или в 2026»:

```
UNION ALL   366 строк
UNION       250 строк
```

366 — это все заказы (каждый клиент столько раз, сколько у него заказов).
250 — уникальные клиенты. Обе цифры верны; неверно — назвать первую
числом клиентов.

## 1.6. Типичные ошибки

Все три измерены на этой базе при написании шага и его эталонов.

**Ошибка:** пишете `NOT IN` по подзапросу, который может вернуть `NULL`,
и получаете пустой результат.
**Почему выглядит правильно:** синтаксис корректен, запрос выполняется за
миллисекунды, результат — `0`, и ноль выглядит как ответ «таких нет».
**Почему неправильно:** заказов без платежа — **353** из 366. Ноль вместо
353 — не «немного неточно», это противоположное утверждение о состоянии
бизнеса. Признак в своём результате: в задаче 2 первая строка даёт 0, а
две другие — 353; если у вас все три дают одно и то же, подзапрос не
содержит `NULL`, и ловушка не воспроизведена.
**Как правильно:** либо `NOT EXISTS`, либо `NOT IN` с явным
`WHERE … IS NOT NULL` внутри подзапроса. Первое предпочтительнее: оно не
зависит от того, появится ли `NULL` в колонке завтра.

**Ошибка:** в self-join не исключаете строку саму с собой и не задаёте
направление сравнения.
**Почему выглядит правильно:** соединение выполняется, клиенты находятся,
число получается больше — то есть «нашли больше повторных заказов».
**Почему неправильно:** без `b.order_id <> a.order_id` каждый заказ
образует пару сам с собой, и повторным становится любой клиент с хотя бы
одним заказом; без `b.order_date > a.order_date` каждая настоящая пара
считается дважды. На этих данных верный ответ — **42** клиента суммарно
по пяти городам (11 / 4 / 5 / 12 / 10); без обоих условий число вырастает
до сотен. Признак: сумма по городам больше числа клиентов, у которых
вообще есть два заказа.
**Как правильно:** оба условия обязательны и пишутся в `ON`, а не в
`WHERE`, — иначе они превращают соединение в `INNER JOIN` по побочному
эффекту (тот же механизм, что в `step-05.md`).

**Ошибка:** `LIMIT 5` без `ORDER BY` либо с `ORDER BY` только по сумме.
**Почему выглядит правильно:** пять строк на выходе, суммы большие,
результат выглядит как топ.
**Почему неправильно:** без `ORDER BY` порядок задаётся планом
выполнения и меняется при добавлении индекса — то есть «топ-5» перестаёт
быть топом молча. С `ORDER BY total DESC` без второго ключа две строки с
одинаковой суммой могут поменяться местами между прогонами, и
`compare_csv.py` даст `НЕ СОВПАДАЕТ` на строке, где данные не менялись.
**Как правильно:** `ORDER BY total DESC, customer_id ASC` — второй ключ
делает порядок однозначным.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы написали `WHERE client_id NOT IN (SELECT manager_id FROM
staff)` и получили ноль строк, хотя знаете, что подходящие клиенты есть.
Что произошло?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Называет причину: в подзапросе есть `NULL` (у части сотрудников нет
   руководителя), и `x NOT IN (…, NULL)` даёт `NULL`, а не `TRUE`, для
   любого `x`.
2. Говорит, что ошибки при этом не будет: запрос отработает и вернёт
   пустой результат, который читается как содержательный ответ.
3. Предлагает две починки: `NOT EXISTS` либо явный `WHERE manager_id IS
   NOT NULL` в подзапросе, — и объясняет, почему первая надёжнее.
4. Добавляет проверку, которая ловит это заранее: посчитать
   `COUNT(*)` и `COUNT(manager_id)` в подзапросе; расхождение и есть
   число `NULL`.
