# M3.08. Переписывает медленный запрос так, что он перестаёт сканировать таблицу целиком

Умение: A4
Модуль: M3
Требуется до этого: `step-06.md` (A1), `step-07.md` (A3). Дополнительные
данные сверх исходных 5 таблиц модуля: таблица `activity_log`
(`program/M3/data/generate_activity_log.py`, `SEED = 20260804`,
4 800 000 строк) — генерируется **локально**, не коммитится (декларация
и причина — `step-00.md`, раздел «Дополнение»).
Время: 5–7 ч (оценка проектная, не измерена)

## 1.1. Цель и связь с умением

После шага вы, получив запрос, который выполняется медленно на большом
датасете, находите место, где запрос сканирует таблицу целиком без
необходимости, и переписываете его так, чтобы время выполнения
сократилось на порядки — без изменения результата. Дословно умение A4
из части 1 blueprint: «Дан запрос, выполняющийся 40 с: переписывает
так, что время < 5 с на том же датасете».

**Оговорка по абсолютным секундам.** «40 с» и «< 5 с» в формулировке
умения — числа с референсной машины автора программы, не гарантия для
машины учащегося: время SQL-запроса зависит от процессора, диска и
текущей загрузки машины, а не только от запроса. Механически проверяем
не конкретный порог в секундах, а то, что сформулировано в 1.5:
отношение «до/после» и план запроса. На референсной машине автора
разобранный пример в 1.3 дал 70.66 с → 0.044 с — в том же порядке, что
формулировка умения, но это отдельное измерение, не то же самое число.

## 1.2. Теория своими словами

`EXPLAIN QUERY PLAN <запрос>` показывает, как SQLite собирается
выполнить запрос, не выполняя его. Ключевое слово, которое отличает
медленный план от быстрого, — `SCAN` против `SEARCH`:

- `SCAN имя_таблицы` — движок проверяет строки таблицы одну за другой
  (в худшем случае — все). Стоимость растёт линейно с числом строк
  таблицы, а если такой скан происходит **внутри** цикла по другой
  таблице (коррелированный подзапрос или `JOIN` без индекса на ключе
  соединения) — стоимость перемножается: строки внешнего запроса ×
  строки внутреннего скана.
- `SEARCH имя_таблицы USING INDEX ...` (или `USING COVERING INDEX`) —
  движок находит нужные строки через индекс (структуру, заранее
  отсортированную по колонкам индекса), не проверяя остальные. Стоимость
  растёт логарифмически с числом строк, а не линейно.

Индекс (`CREATE INDEX имя ON таблица(колонка1, колонка2, ...)`) —
дополнительная структура, которую SQLite поддерживает автоматически при
каждой вставке/изменении строки; создаётся один раз, ускоряет чтение,
слегка замедляет запись (в этом модуле не важно — таблица только
читается после генерации). Порядок колонок в составном индексе имеет
значение: `(customer_id, event_type)` эффективен для запроса,
фильтрующего по `customer_id`, и, если после этого ещё и по
`event_type` — но не помогает эффективно отфильтровать только по
`event_date`, если `event_date` не входит в индекс вовсе. Индекс,
построенный «под одну колонку не туда», может частично ускорить запрос
(SQLite всё равно использует его для сужения по той колонке, что в
индексе есть), не доводя время до нужного порога — это не значит, что
индекс не нужен, значит, что нужен **другой** индекс.

## 1.3. Разобранный пример на сквозном датасете

Установка (после `schema.sql`, `seed.sql`, `retention_seed.sql` из
предыдущих шагов):

```
$ python program/M3/data/generate_activity_log.py m3.db
```

Скрипт создаёт таблицу `activity_log` (4 800 000 строк, без индекса на
`customer_id`) внутри уже существующей `m3.db`.

Задан запрос — число `login`-событий на каждого клиента:

```sql
SELECT c.customer_id,
       (SELECT COUNT(*) FROM activity_log a
        WHERE a.customer_id = c.customer_id AND a.event_type = 'login') AS n_logins
FROM customers c
ORDER BY c.customer_id;
```

На референсной машине автора — **70.66 с**. `EXPLAIN QUERY PLAN` для
этого запроса:

```
SCAN c
CORRELATED SCALAR SUBQUERY 1
SEARCH a  (или SCAN a, до индекса)
```

До индекса вложенный подзапрос — `SCAN a`: для каждого из 252 клиентов
`activity_log` проверяется целиком (252 × 4.8 млн построчных проверок).

Фикс — индекс на паре колонок, по которым фильтрует подзапрос:

```sql
CREATE INDEX idx_activity_customer_type ON activity_log(customer_id, event_type);
```

После индекса — тот же запрос, **0.044 с** на референсной машине,
план — `SEARCH a USING COVERING INDEX idx_activity_customer_type
(customer_id=? AND event_type=?)`. Результат (252 строки) побайтово
совпадает с версией до индекса — индекс меняет план и время выполнения,
не меняет ответ. Полные числа — `program/M3/data/reference_answers.md`,
раздел «A4».

## 1.4. Задание

Тот же `activity_log`, без изменений. Дан запрос — число **любых**
событий клиента за июнь 2025:

```sql
SELECT c.customer_id,
       (SELECT COUNT(*) FROM activity_log a
        WHERE a.customer_id = c.customer_id
          AND a.event_date BETWEEN '2025-06-01' AND '2025-06-30') AS n_events_june
FROM customers c
ORDER BY c.customer_id;
```

1. Замерьте время выполнения на своей машине (индекс из 1.3 ещё не
   создан либо уже создан — оба варианта допустимы, начните с того
   состояния базы, в котором она у вас осталась после 1.3).
2. Постройте `EXPLAIN QUERY PLAN` для этого запроса. Если индекс из 1.3
   (`customer_id, event_type`) уже существует — проверьте, использует
   ли план его, и ускоряет ли это запрос **достаточно** (порог — 1.5).
3. Если недостаточно — создайте индекс, который действительно закрывает
   именно этот запрос (фильтр по `customer_id` и по `event_date`, а не
   по `event_type`), и замерьте время повторно.
4. Проверьте, что результат (252 строки) не изменился между всеми
   замерами.

## 1.5. Критерий готовности

- Индекс, оставшийся в базе после решения задания, ускоряет запрос
  задания **не менее чем в 100 раз** относительно замера без какого-либо
  индекса на `activity_log` (на референсной машине автора — 71.32 с без
  индекса против 0.02 с с правильным индексом, это ×3566; порог ×100
  выбран с запасом на разницу в железе — см. 1.1).
- `EXPLAIN QUERY PLAN` итогового запроса не содержит строки `SCAN
  activity_log` (или `SCAN a`, в зависимости от алиаса) — только
  `SEARCH ... USING INDEX` или `SEARCH ... USING COVERING INDEX`.
- Результат запроса (все 252 строки, включая значения `n_events_june`)
  идентичен до и после построения индекса — расхождение 0.
- Индекс из 1.3 (`customer_id, event_type`) сам по себе **не
  засчитывается** как решение этого задания, даже если он частично
  ускоряет запрос (на референсной машине — с 71.32 до 15.04 с, план
  показывает `SEARCH a USING INDEX idx_activity_customer_type
  (customer_id=?)`, но не покрывает `event_date`) — недостаточно по
  первому пункту критерия.

## 1.6. Типичные ошибки

**Ошибка:** переиспользует индекс `idx_activity_customer_type` из 1.3
для задания 1.4, не создавая новый.
**Почему выглядит правильно:** запрос ускоряется (71.32 → 15.04 с на
референсной машине) и план меняется с `SCAN a` на `SEARCH a USING
INDEX ...` — оба внешних признака «починки» присутствуют.
**Почему неправильно:** 15.04 с — всё ещё далеко не 100-кратное
ускорение (нужный порог — ×100, фактическое — ×4.7), и план,
проверенный внимательно, показывает поиск только по `customer_id`
(`customer_id=?`), а не по `customer_id=? AND event_date...` — колонки
`event_date` в индексе нет, поэтому внутри найденного по `customer_id`
диапазона SQLite всё ещё построчно проверяет `event_date`.
**Как правильно:** строить индекс на колонках, которые **реально**
участвуют в условии фильтрации именно этого запроса
(`customer_id, event_date`), а не переиспользовать любой существующий
индекс на той же таблице.

**Ошибка:** создаёт индекс только на `event_date`, без `customer_id`:
`CREATE INDEX ... ON activity_log(event_date)`.
**Почему выглядит правильно:** `event_date` — колонка, по которой
запрос действительно фильтрует диапазоном (`BETWEEN`).
**Почему неправильно:** запрос — коррелированный подзапрос,
выполняющийся отдельно для **каждого** клиента; индекс без
`customer_id` первой колонкой не даёт SQLite быстро найти строки
конкретного клиента — движок вынужден искать по диапазону дат во всей
таблице на каждой из 252 итераций, что почти не отличается по
стоимости от `SCAN` (проверено: план в этом случае — `SEARCH a USING
INDEX ... (event_date>? AND event_date<?)` без `customer_id=?`, время
остаётся на уровне десятков секунд, не долей секунды).
**Как правильно:** первой колонкой составного индекса — та, что
используется для точного равенства (`customer_id=?` в коррелированном
подзапросе), второй — та, что для диапазона (`event_date`).

**Ошибка:** проверяет ускорение «на глаз» (запрос точно стал быстрее),
не сравнивая с конкретным порогом и не глядя в `EXPLAIN QUERY PLAN`.
**Почему выглядит правильно:** любое ускорение выглядит как успех,
особенно после того, как первый замер занял больше минуты.
**Почему неправильно:** ускорение с 71 до 15 секунд (в 4.7 раза) —
тоже «стало быстрее», но не проходит порог ×100 критерия 1.5, и план
всё ещё может показывать неэффективный `SEARCH` без нужных колонок.
Единственная надёжная проверка — план запроса и порог отношения
времени, а не субъективное «быстрее, чем было».
**Как правильно:** сверяться с `EXPLAIN QUERY PLAN` и с числовым
порогом, а не с направлением изменения времени.

## 1.7. Честная оценка времени

5–7 ч. Оценка проектная, не измерена. Включает время на саму генерацию
`activity_log` (около 10–15 с на референсной машине автора, но
зависит от диска и может быть больше на медленной машине) и на
несколько последовательных замеров медленного запроса (десятки секунд
каждый, до фикса).

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вам дали медленный SQL-запрос и просят его ускорить. Что
вы посмотрите в первую очередь?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. План запроса (`EXPLAIN`/`EXPLAIN QUERY PLAN` или аналог в конкретной
   СУБД) — ищет полный скан таблицы там, где ожидается точечный поиск.
2. Проверяет, есть ли индекс на колонках, по которым запрос
   фильтрует/соединяет таблицы, и совпадает ли порядок колонок индекса
   с тем, что запрос реально использует (равенство раньше диапазона).
3. Отдельно ищет коррелированные подзапросы и `JOIN` без индекса на
   ключе соединения — именно там линейная стоимость скана
   перемножается на число внешних строк.
4. Проверяет результат до и после любого изменения — ускорение,
   меняющее ответ, не является решением задачи.
