## 1.1. Цель и связь с умением

После шага у вас на машине работает PostgreSQL, в нём лежат те же 5
таблиц модуля, и вы доказали числами — а не осмотром — что перенос не

## 1.2. Теория своими словами

**Файл против сервера.** SQLite — библиотека: база это один файл
(`m3.db`), никакого отдельного процесса нет, «подключение» — это открытие
файла. PostgreSQL — сервер: отдельный процесс, который держит файлы базы
и принимает подключения по сети (по умолчанию порт 5432). Отсюда всё
остальное различие в обращении: у PostgreSQL есть пользователь, пароль,
имя базы внутри одного сервера (`createdb m3`), и клиент (`psql`),
который к нему подключается. Файл базы PostgreSQL руками не открывают и
не копируют.

**Строгие типы против гибких.** SQLite объявленный тип колонки трактует
как пожелание: в колонку `INTEGER` можно записать строку, и ошибки не
будет (`sqlite.org/quirks.html`, разделы 3 и 10). PostgreSQL тип
проверяет: несовпадение — ошибка вставки. Для переноса это означает, что
типы нельзя отобразить механически, слово в слово: три из них в этой
схеме означают на двух движках разное.

| В `schema.sql` (SQLite) | Наивное отображение | Что берём и почему |
|---|---|---|
| `order_date TEXT` (дата строкой) | `TEXT` | `DATE`. У SQLite отдельного типа даты нет вовсе (`quirks.html`, 3.2), поэтому даты в M3 лежат текстом; у PostgreSQL тип есть, и держать дату текстом в нём — сознательно хуже. Цена: `substr()`/`strftime()` по дате перестают работать — разбор в `step-10.md` |
| `amount REAL` (деньги) | `REAL` | `NUMERIC(10,2)`. `REAL` в PostgreSQL — 4 байта, 6 десятичных знаков; в SQLite `REAL` — 8 байт. Отображение `REAL` → `REAL` теряет точность **молча**, замер в 1.3 |
| `customer_id INTEGER PRIMARY KEY` | `SERIAL` / `GENERATED ... AS IDENTITY` | `INTEGER PRIMARY KEY` как есть. Автогенерация нужна, когда id не задан; здесь все id приходят из CSV явно, генерировать нечего |

Документация, на которую опирается таблица: типы PostgreSQL —
[datatype-numeric](https://www.postgresql.org/docs/17/datatype-numeric.html)
(там же прямо: «для денежных сумм используйте `numeric`»); отличия SQLite
от остальных СУБД — [sqlite.org/quirks.html](https://www.sqlite.org/quirks.html).

**Почему не Docker.** Docker Desktop на Windows работает поверх WSL2 или
Hyper-V, то есть требует ровно того, чего решение 13 `design/decisions.md`
велит не требовать на пустом месте. Установщик PostgreSQL под Windows
самодостаточен и WSL не использует — он и берётся основным путём.

## 1.3. Разобранный пример на сквозном датасете

Датасет тот же: `m3.db` после `schema.sql` + `seed.sql` +
`retention_seed.sql` (252 клиента, 366 заказов, 6 товаров, 23 позиции, 13
платежей — числа из `step-00.md` и `data/README.md`).

**Шаг 1. Установка.** Страница загрузки —
[postgresql.org/download/windows](https://www.postgresql.org/download/windows/):
там два варианта, «Interactive installer by EDB» (обычный установщик,
ставит сервер, `psql` и pgAdmin) и «zip archive» — те же бинарники без
установщика, для случая, когда прав администратора на машине нет.
Платформа программы — Windows (решение 21 `design/decisions.md`), и
проверялся только Windows-путь; страницы загрузки для других ОС на сайте
есть, но в программе не используются и не проверялись. При установке
запрашивается пароль пользователя `postgres` — запишите его, он
понадобится при каждом подключении.

После установки `psql` может не оказаться в `PATH`: тогда его запускают
ярлыком «SQL Shell (psql)» из меню либо добавляют в `PATH` папку `bin`
установки. Проверка, что сервер поднялся:

```
$ psql -U postgres -c "SELECT version();"
```

На референсной машине автора (Windows 11, вариант с zip-архивом, без прав
администратора) это напечатало:

```
PostgreSQL 17.6 on x86_64-windows, compiled by msvc-19.44.35213, 64-bit
```

Ваша версия и строка сборки будут другими; проверяется не совпадение
строки, а то, что команда вообще вернула ответ, а не ошибку подключения.

**Шаг 2. База и схема.**

```
$ createdb -U postgres m3
$ psql -U postgres -d m3 -f program/M3/data/schema_pg.sql
```

`schema_pg.sql` — те же 5 таблиц с типами из таблицы в 1.2. Вывод — пять
строк `CREATE TABLE`.

**Шаг 3. Выгрузка данных из SQLite.**

```
$ python program/M3/data/export_for_postgres.py m3.db
```

Скрипт кладёт по одному CSV на таблицу в папку `pg_csv` и печатает число
строк по каждой. Прогон на референсной машине:

```
customers: 252 строк -> pg_csv\customers.csv
products: 6 строк -> pg_csv\products.csv
orders: 366 строк -> pg_csv\orders.csv
order_items: 23 строк -> pg_csv\order_items.csv
payments: 13 строк -> pg_csv\payments.csv
Итого выгружено строк: 660
```

Порядок в выводе не случайный: он же — порядок загрузки. `customers` и
`products` идут раньше `orders`, `orders` раньше `order_items` и
`payments`, потому что внешний ключ отклонит строку, у которой родителя
ещё нет.

**Шаг 4. Загрузка в PostgreSQL.** По одной команде на таблицу, в том же
порядке:

```
$ psql -U postgres -d m3 -c "\copy customers FROM 'pg_csv/customers.csv' CSV HEADER"
$ psql -U postgres -d m3 -c "\copy products FROM 'pg_csv/products.csv' CSV HEADER"
$ psql -U postgres -d m3 -c "\copy orders FROM 'pg_csv/orders.csv' CSV HEADER"
$ psql -U postgres -d m3 -c "\copy order_items FROM 'pg_csv/order_items.csv' CSV HEADER"
$ psql -U postgres -d m3 -c "\copy payments FROM 'pg_csv/payments.csv' CSV HEADER"
```

`\copy` — команда клиента `psql`, а не сервера: файл читает `psql` с
вашей машины и с вашими правами
([app-psql](https://www.postgresql.org/docs/17/app-psql.html)). Похожая по
имени серверная команда `COPY` читала бы файл с диска сервера и требовала
бы прав суперпользователя — на своей машине разница незаметна, на рабочем
сервере это две разные вещи. Вывод каждой команды — `COPY <число строк>`:
252, 6, 366, 23, 13.

**Шаг 5. Наивное отображение типа, которое проходит молча.** Проверьте,
чего стоило решение из 1.2 взять `NUMERIC(10,2)`, а не `REAL`:

```sql
CREATE TEMP TABLE t_real (amount REAL);
CREATE TEMP TABLE t_dbl  (amount DOUBLE PRECISION);
INSERT INTO t_real SELECT amount FROM orders;
INSERT INTO t_dbl  SELECT amount FROM orders;

SELECT 'NUMERIC(10,2)'    AS mapping, SUM(amount)::text AS total FROM orders
UNION ALL SELECT 'REAL (float4)',     SUM(amount)::text FROM t_real
UNION ALL SELECT 'DOUBLE PRECISION',  SUM(amount)::text FROM t_dbl;
```

Результат на референсной машине:

| mapping | total |
|---|---|
| `NUMERIC(10,2)` | 317959.87 |
| `REAL (float4)` | **317959.84** |
| `DOUBLE PRECISION` | **317959.87000000005** |

В SQLite та же сумма (`SELECT SUM(amount) FROM orders` на `m3.db`) —
**317959.87**. То есть отображение `REAL` → `REAL`, самое очевидное из
трёх, расходится с исходной базой на 0.03 — без ошибки, без
предупреждения, при полностью успешной загрузке всех 366 строк.

Отдельно проверяется, что расходится именно агрегат, а не отдельные
значения:

```sql
SELECT COUNT(*) FROM (SELECT amount, amount::real::numeric(10,2) AS back FROM orders) s
WHERE amount <> back;
```

Результат — **0**: ни одно из 366 значений по отдельности не искажено
настолько, чтобы отличаться в двух знаках после запятой. Поэтому построчная
сверка «глазами» такой перенос принимает, а сумма — нет. Это ровно тот
механизм, что в частях 1–5 умения A2: проверять надо то число, которое
ломается, а не то, которое сходится.

- Число строк в PostgreSQL по каждой из 5 таблиц: `customers` 252,
  `products` 6, `orders` 366, `order_items` 23, `payments` 13 —
  расхождение 0 по каждой таблице.

- Записано численно, на сколько разошлась сумма при наивном отображении

## 1.6. Типичные ошибки

**Ошибка:** загружает таблицы в том порядке, в каком они перечислены в
`schema.sql`, — `customers`, `orders`, `products`, `order_items`,
`payments`.
**Почему выглядит правильно:** это порядок объявления таблиц в схеме
модуля, он же порядок, в котором таблицы читаются глазами.
**Почему неправильно:** `order_items` ссылается внешним ключом и на
`orders`, и на `products`; при таком порядке `products` (6 строк) ещё не
загружены к моменту загрузки 23 строк `order_items`, и PostgreSQL
отклоняет вставку целиком: `insert or update on table "order_items"
violates foreign key constraint`. Ноль загруженных строк вместо 23.
**Как правильно:** порядок из вывода `export_for_postgres.py` — сначала
`customers` и `products`, потом `orders`, потом `order_items` и
`payments`.

**Ошибка:** отображает `REAL` в `REAL`, потому что слово то же самое.
**Почему выглядит правильно:** тип называется одинаково, загрузка всех
366 строк проходит без единой ошибки, построчная сверка значений
расхождений не даёт (0 строк, замер в 1.3).
**Почему неправильно:** `SUM(amount)` по таблице даёт 317959.84 вместо
317959.87 — расхождение 0.03 на 366 строках, и оно растёт с числом строк.
Отчёт по выручке, собранный на такой базе, не сходится с исходным ни
одной итоговой цифрой, при том что каждая отдельная строка выглядит
правильной.
**Как правильно:** для денег — `NUMERIC(точность, знаки)`, у которого
хранение точное; `REAL`/`DOUBLE PRECISION` в PostgreSQL — приближённые
типы, о чём документация
[datatype-numeric](https://www.postgresql.org/docs/17/datatype-numeric.html)
предупреждает прямо.

**Ошибка:** переносит и схему, и данные одним файлом — выгрузкой
`.dump` из SQLite, поданной в `psql`.
**Почему выглядит правильно:** `.dump` выдаёт готовый SQL со всеми
`CREATE TABLE` и `INSERT` сразу, и это выглядит как самый прямой путь,
без промежуточных CSV и без отдельного файла схемы.
**Почему неправильно:** проверено прогоном — загрузка обрывается на 25-й
строке: `ERROR: relation "orders" does not exist`. Причина та же, что в
первой ошибке этого раздела: `.dump` выдаёт таблицы в порядке их создания
в SQLite (`customers`, затем `order_items`), а `order_items` ссылается на
`orders`, которая идёт ниже. SQLite при выгрузке это не смущает,
PostgreSQL отклоняет. Дальше каждая строка отвечает `current transaction
is aborted`, и после отката в базе остаётся **0 таблиц** (проверено
запросом к `information_schema.tables`). Отдельно: `sqlite3` начинает
выгрузку строкой `PRAGMA foreign_keys=OFF;`, на которой `psql` отвечает
`syntax error at or near "PRAGMA"`. И даже если бы файл загрузился, он
воссоздал бы типы SQLite дословно — `order_date TEXT` и `amount REAL`, то
есть ровно те два отображения, которые отвергнуты в 1.2.
**Как правильно:** схему задавать отдельным файлом под PostgreSQL
(`schema_pg.sql`, где порядок таблиц и типы выбраны осознанно), данные
переносить в формате, который принимают оба движка, — CSV через
`export_for_postgres.py` и `\copy`.

**Ошибка:** проверяет корректность переноса тем, что открывает пару
таблиц и смотрит, что данные «на месте».
**Почему выглядит правильно:** строки действительно на месте, кириллица
отображается, суммы похожи на исходные.
**Почему неправильно:** на этом переносе такая проверка пропускает
расхождение 0.03 в `SUM(amount)` (317959.84 против 317959.87) — оно не
видно ни в одной отдельной строке, потому что каждое из 366 значений по
отдельности совпадает (0 строк расхождения при построчной сверке).
**Как правильно:** сверять числа, которые считаются по всей таблице
сразу, — число строк и контрольные суммы, объявленные в `step-00.md`.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «Вы перенесли таблицу из одной СУБД в другую. Загрузка прошла
без ошибок, число строк совпало. Что ещё проверите, прежде чем сказать,
что перенос корректен?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Контрольные суммы по числовым колонкам (`SUM`, `AVG`) на обеих
   сторонах, а не только число строк: совпадение количества строк не
   гарантирует совпадения значений.
2. Проверяет, во что отобразились типы — отдельно денежные колонки
   (точный `NUMERIC` против приближённого `REAL`/`DOUBLE PRECISION`) и
   даты (настоящий тип даты против строки).
3. Проверяет инварианты между таблицами, которые были верны до переноса
   (сумма позиций равна сумме заказа; платёж есть только у оплаченного
   заказа), а не каждую таблицу по отдельности.
4. Называет, что расхождение может быть невидимо построчно и видно
   только в агрегате, — то есть проверять надо то число, которое
   ломается, а не то, которое сходится.
