# M3.12. Читает план запроса PostgreSQL и убирает из него Seq Scan по таблице фактов

Умение: A4 (часть 2 из 2. Часть 1 — `step-08.md`, та же оптимизация в
SQLite, где план читается через `EXPLAIN QUERY PLAN` и состоит из двух
слов, `SCAN` и `SEARCH`. Эта часть — тот же запрос и тот же датасет на
движке, где план развёрнут в дерево с фактическими числами строк.
Критерий — тот же по устройству: соотношение времени, пол по
абсолютному времени, отсутствие полного скана в плане; решение 18
`design/decisions.md`)
Модуль: M3
Требуется до этого: `step-08.md` (A4 в SQLite), `step-09.md` (база
перенесена), `step-10.md` (расхождение 9 — `EXPLAIN QUERY PLAN` не
работает в PostgreSQL — уже найдено)
Дополнительные данные сверх перенесённых в `step-09.md`: таблица
`activity_log` (4 800 000 строк), генерируется локально в SQLite
(`generate_activity_log.py`, `SEED = 20260804`) и переносится в
PostgreSQL — в репозиторий не коммитится, декларация и причина —
`step-00.md`, раздел «Дополнение».
Время: 7–9 ч (оценка проектная, не измерена)

## 1.1. Цель и связь с умением

После шага вы читаете план запроса PostgreSQL, находите в нём узел,
который перебирает таблицу фактов целиком, и убираете его индексом —
получая тот же результат за время на три порядка меньше. Дословно
умение A4 из части 1 blueprint, включая его проверку «в плане запроса нет
полного скана таблицы фактов». Часть 2 из 2: то же умение на движке,
названном решением 15.

**Оговорка по абсолютным секундам — та же, что в `step-08.md`, 1.1**, и
по той же причине: время зависит от процессора, диска и загрузки машины.
Проверяется соотношение «до/после», план запроса и нижний порог на сам
исходный замер. Устройство критерия и почему он именно такой — решение 18
`design/decisions.md`.

## 1.2. Теория своими словами

`EXPLAIN QUERY PLAN` в PostgreSQL не существует (расхождение 9 из
`step-10.md`). Вместо него:

- `EXPLAIN <запрос>` — план без выполнения, с оценками планировщика.
- `EXPLAIN (ANALYZE) <запрос>` — запрос **выполняется**, и в плане
  появляются фактические числа. На медленном запросе это означает, что
  команда займёт столько же, сколько сам запрос.

Документация — [using-explain](https://www.postgresql.org/docs/17/using-explain.html).

Слова плана, которые заменяют `SCAN` и `SEARCH` из SQLite:

- `Seq Scan on таблица` — последовательный перебор таблицы. Прямой
  аналог `SCAN` из `step-08.md`.
- `Index Scan using индекс on таблица` — поиск через индекс с обращением
  к самой таблице за остальными колонками.
- `Index Only Scan using индекс on таблица` — то же, но все нужные
  колонки есть в самом индексе, и к таблице обращаться не приходится.
  Аналог `COVERING INDEX` из SQLite. Строка `Heap Fetches: 0` под ним
  означает, что к таблице действительно не обращались ни разу.
- `Bitmap Index Scan` + `Bitmap Heap Scan` — промежуточный вариант:
  индекс сузил круг строк, но не до конца, и оставшееся отсеивается
  перебором. Именно сюда попадает частично подходящий индекс.

Две строки плана, которых нет в SQLite и которые здесь важнее слов:

- `loops=N` — сколько раз узел выполнялся. Для коррелированного
  подзапроса это число внешних строк: узел внутри выполняется заново для
  каждой из них.
- `Rows Removed by Filter: N` — сколько строк узел прочитал и выбросил.
  Это прямая мера впустую сделанной работы, которой в плане SQLite
  просто нет: `SCAN` говорит, что таблица перебирается, а `Rows Removed
  by Filter` говорит, сколько именно строк перебрано зря.

## 1.3. Разобранный пример на сквозном датасете

**Перенос `activity_log`.** Таблица создаётся отдельно (в `schema_pg.sql`
её нет — она не часть схемы модуля):

```sql
CREATE TABLE activity_log (
    log_id      INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    event_type  TEXT NOT NULL,
    event_date  DATE NOT NULL
);
```

Выгрузка из SQLite и загрузка — теми же инструментами, что в
`step-09.md`, с флагом для большой таблицы:

```
$ python program/M3/data/export_for_postgres.py m3.db --with-activity-log
$ psql -U postgres -d m3 -c "\copy activity_log FROM 'pg_csv/activity_log.csv' CSV HEADER"
```

Ожидаемый вывод второй команды — `COPY 4800000`. На референсной машине
автора выгрузка заняла 4.4 с, загрузка — 12.1 с, CSV занял 160 МБ (файл
после загрузки можно удалить). Число строк сверяется с контрольной точкой
из `reference_answers.md`, раздел «A4», — той же, что в `step-08.md`.

**Запрос — тот же, что в `step-08.md`, 1.3**, без единой правки: число
`login`-событий на каждого клиента.

```sql
SELECT c.customer_id,
       (SELECT COUNT(*) FROM activity_log a
        WHERE a.customer_id = c.customer_id AND a.event_type = 'login') AS n_logins
FROM customers c
ORDER BY c.customer_id;
```

Замеры на референсной машине автора — оба движка, одна машина, один и
тот же датасет из 4 800 000 строк:

| Замер | SQLite 3.45.1 | PostgreSQL 17.6 |
|---|---|---|
| Без индекса на `activity_log` | 57.378 с | 53.594 с |
| С индексом `(customer_id, event_type)` | 0.034 с | 0.045 с |
| Ускорение | ×1665 | ×1191 |
| Построение индекса | 2.55 с | 2.21 с |

Порядок величины совпал: движок другой, а узкое место то же самое —
перебор таблицы фактов заново для каждого из 252 клиентов.

План до индекса, `EXPLAIN (ANALYZE)`, на запросе из задания 1.4 (фильтр
по дате — он же ниже разбирается подробно):

```
Index Only Scan using customers_pkey on customers c (actual rows=252 loops=1)
  Heap Fetches: 252
  SubPlan 1
    ->  Aggregate (actual rows=1 loops=252)
          ->  Seq Scan on activity_log a (actual rows=1564 loops=252)
                Filter: ((event_date >= '2025-06-01'::date) AND (event_date <= '2025-06-30'::date) AND (customer_id = c.customer_id))
                Rows Removed by Filter: 4798436
```

Читается так: `Seq Scan` перебирает `activity_log`, `loops=252` — делает
это 252 раза, по разу на клиента, и каждый раз выбрасывает 4 798 436
строк из 4 800 000, оставляя 1 564. Итого около 1.2 миллиарда прочитанных
и выброшенных строк. В плане SQLite на том же месте стоит одно слово
`SCAN a`; числа, показывающего масштаб потерь, там нет.

Индекс — тот же, что в `step-08.md`:

```sql
CREATE INDEX idx_activity_customer_type ON activity_log(customer_id, event_type);
```

## 1.4. Задание

Тот же `activity_log`, тот же запрос задания, что в `step-08.md`, 1.4 —
число **любых** событий клиента за июнь 2025:

```sql
SELECT c.customer_id,
       (SELECT COUNT(*) FROM activity_log a
        WHERE a.customer_id = c.customer_id
          AND a.event_date BETWEEN '2025-06-01' AND '2025-06-30') AS n_events_june
FROM customers c
ORDER BY c.customer_id;
```

1. Замерьте время без единого индекса на `activity_log` (`\timing on` в
   `psql` печатает время каждой команды). Если замер быстрее 3 с —
   перегенерируйте `activity_log` с большим числом строк
   (`generate_activity_log.py m3.db <число>`), перенесите заново и
   повторите: порог из 1.5 на слишком быстром железе не проверяет ничего
   (то же предусловие, что в `step-08.md`).
2. Постройте `EXPLAIN (ANALYZE)` и запишите три числа из узла по
   `activity_log`: `loops`, `actual rows`, `Rows Removed by Filter`.
3. Создайте индекс из 1.3 (`customer_id, event_type`) — тот, что решал
   задачу разобранного примера, но не эту. Замерьте время и постройте
   план заново. Запишите, каким узлом он стал.
4. Создайте индекс, закрывающий именно этот запрос, замерьте и постройте
   план ещё раз.
5. Проверьте, что результат (252 строки) не изменился между всеми
   замерами.
6. Сравните итог с `step-08.md`: во сколько раз ускорился запрос на
   каждом движке и совпали ли выводы о том, какой индекс нужен.

## 1.5. Критерий готовности

- **Предусловие:** замер без единого индекса на `activity_log` — не
  быстрее **3 с**. Иначе критерий на вашем железе неприменим как есть:
  увеличьте число строк и повторите (см. `step-08.md`, 1.5; обоснование
  порога — решение 18 `design/decisions.md`).
- При выполненном предусловии: индекс, оставшийся в базе после решения
  задания, ускоряет запрос **не менее чем в 100 раз** относительно
  замера без индексов. На референсной машине автора — 65.097 с против
  0.020 с, это ×3255; порог ×100 взят с запасом на разницу в железе.
- `EXPLAIN (ANALYZE)` итогового запроса **не содержит** узла `Seq Scan on
  activity_log`. Допустимо `Index Scan` или `Index Only Scan`.
- Записаны три числа из плана до индекса: `loops=252`, `actual rows=1564`,
  `Rows Removed by Filter=4798436` (последние два — для датасета в
  4 800 000 строк; при перегенерации с другим числом строк ваши будут
  другими, и это ожидаемо).
- Индекс `(customer_id, event_type)` из 1.3 **не засчитывается** как
  решение: на референсной машине он даёт 11.515 с (×5.7 от 65.097 с) и
  план `Bitmap Heap Scan` с `Rows Removed by Filter: 17484` — индекс
  сузил перебор по `customer_id`, но `event_date` в нём нет, и остаток
  отсеивается перебором. Порог ×100 не пройден.
- Результат запроса (252 строки со значениями `n_events_june`) идентичен
  до и после каждого индекса — расхождение 0.
- Записано сравнение с `step-08.md` по обоим движкам: какой индекс
  оказался нужен и совпал ли вывод.
- Норматив: ≤90 мин на перенос `activity_log` и четыре замера с планами.

## 1.6. Типичные ошибки

**Ошибка:** строит план через `EXPLAIN` без `ANALYZE` и по нему судит,
помог ли индекс.
**Почему выглядит правильно:** план строится мгновенно даже на медленном
запросе, узлы и индексы в нём названы, и выглядит это как полный ответ.
**Почему неправильно:** без `ANALYZE` в плане нет ни `loops`, ни `actual
rows`, ни `Rows Removed by Filter` — только оценки планировщика. Именно
`Rows Removed by Filter: 4798436` показывает, что работа делается
впустую; по одному слову `Seq Scan` без этого числа не видно, перебирается
1 500 строк или 4 800 000.
**Как правильно:** `EXPLAIN (ANALYZE)` для итоговой проверки. Голый
`EXPLAIN` — когда запрос слишком медленный, чтобы его выполнять, и нужно
только увидеть, выбран индекс или нет.

**Ошибка:** видит в плане `Bitmap Index Scan on idx_activity_customer_type`
и считает задачу решённой, потому что индекс в плане присутствует.
**Почему выглядит правильно:** `Seq Scan` из плана исчез, имя индекса в
плане есть, время упало с 65.097 с до 11.515 с — все три внешних признака
починки налицо.
**Почему неправильно:** ×5.7 — не ×100, порог 1.5 не пройден. И в плане
под `Bitmap Heap Scan` стоит `Rows Removed by Filter: 17484`: индекс
нашёл строки клиента, но дату среди них пришлось отсеивать перебором,
потому что `event_date` в индекс не входит.
**Как правильно:** индекс на колонках, по которым фильтрует **этот**
запрос (`customer_id, event_date`), а не любой существующий индекс на той
же таблице. Тот же вывод, что и в `step-08.md`, — движок другой, ответ
одинаковый.

**Ошибка:** переносит `activity_log` в PostgreSQL, оставив `event_date`
типом `TEXT`, «чтобы совпадало с SQLite».
**Почему выглядит правильно:** `BETWEEN '2025-06-01' AND '2025-06-30'`
на тексте работает: даты в формате `ГГГГ-ММ-ДД` сравниваются как строки в
том же порядке, что и как даты, и результат на этом датасете совпадает.
**Почему неправильно:** это ровно то отображение типа, которое отвергнуто
в `step-09.md`, 1.2, и держится оно на совпадении: формат `ГГГГ-ММ-ДД`
единственный, где лексикографический порядок строк совпадает с
хронологическим. Любой другой формат в данных ломает и сравнение, и
индекс — молча.
**Как правильно:** `event_date DATE`, как в 1.3. Тип даты стоит ровно
столько же по скорости и не зависит от формата записи.

**Ошибка:** запускает `EXPLAIN (ANALYZE)` на запросе без индекса, ждёт
мгновенного ответа и прерывает команду, решив, что она зависла.
**Почему выглядит правильно:** `EXPLAIN` без `ANALYZE` на том же запросе
отвечает мгновенно, и разница в поведении выглядит как сбой.
**Почему неправильно:** `ANALYZE` означает, что запрос выполняется
по-настоящему: на референсной машине эта команда заняла 65.107 с — ровно
столько же, сколько сам запрос (65.097 с). Прерванная команда не даёт ни
плана, ни замера.
**Как правильно:** на заведомо медленном запросе `EXPLAIN (ANALYZE)`
запускается один раз и дожидается — это и есть замер, отдельно время
мерить не нужно.

## 1.7. Честная оценка времени

7–9 ч. Оценка проектная, не измерена. Включает перенос 4 800 000 строк
(на референсной машине 4.4 с на выгрузку и 12.1 с на загрузку, но это
зависит от диска), четыре замера, каждый из которых до индекса занимает
около минуты, и разбор дерева плана — формата, который в `step-08.md` не
встречался: там план был тремя строками, здесь это дерево с числами по
каждому узлу. Верхняя граница выше, чем у `step-08.md` (5–7 ч), именно
из-за чтения плана, а не из-за самой оптимизации: вывод про нужный
индекс уже известен из части 1.

## 1.8. Вопрос уровня собеседования

**Вопрос:** «В плане запроса вы видите `Seq Scan` по большой таблице.
Всегда ли это проблема?»

**Эталон (ответ покрывает ≥3 из 4 пунктов):**
1. Нет, не всегда: если запросу нужна большая доля строк таблицы,
   последовательный перебор дешевле индексного поиска, и планировщик
   выбирает его осознанно.
2. Признак настоящей проблемы — не само слово, а числа рядом: `loops`
   заметно больше единицы (узел выполняется повторно для каждой внешней
   строки) и большое `Rows Removed by Filter` (прочитано и выброшено
   почти всё).
3. Проверяет, есть ли индекс на колонках, по которым идёт фильтрация, и
   совпадает ли порядок его колонок с тем, что запрос использует
   (равенство раньше диапазона).
4. Называет, что вывод делается по `EXPLAIN (ANALYZE)` с фактическими
   числами, а не по оценкам планировщика, и что результат до и после
   правки обязан совпадать.
