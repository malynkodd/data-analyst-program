### 1.3. Дефекты

**B1 — блокер. Модуль неисполним с первой команды; инструкции по
установке клиента нет ни в одном файле репозитория.**

Ни `program/M3/step-01.md`, ни `program/M3/step-00.md` не содержат
указаний, как получить консольный клиент. `step-00.md`, раздел
«SQL-движок», утверждает обратное: «модуль начинается на SQLite (**0
действий по установке**…)». Источник ошибки — решение 15
`design/decisions.md`: «M3 начинается на SQLite: ставится в 0 действий
(**входит в стандартную библиотеку Python**, файл базы — обычный файл)».

Утверждение верно для **библиотеки** `sqlite3` из стандартной поставки
Python — ею пользуются скрипты программы. Шаги M3 написаны против
**консольного клиента** `sqlite3`. Это разные вещи, и клиент в поставку
Python не входит. Проверено прогоном (1.2).

Затронуто: решение 15 (формулировка «0 действий»), `step-00.md` раздел
«SQL-движок», `step-01.md` раздел 1.3.

**B2 — критерий сверки с эталонным CSV невыполним из коробки.**

Клиент 3.53.4 по умолчанию печатает результат рамками с заголовками:

```
╭──────────┬───────────┬────────╮
│ order_id │  status   │ amount │
╞══════════╪═══════════╪════════╡
│      111 │ pending   │  390.0 │
╰──────────┴───────────┴────────╯
```

Эталоны модуля — CSV с запятой и заголовком
(`program/M3/data/a1_task1_running_total.csv`):

```
customer_id,order_id,order_date,amount,running_total
1,101,2026-05-02,1200.0,1200.0
```

Критерий `step-06.md`, 1.5 — «вывод собственного запроса **построчно**
(все колонки, все строки, тот же порядок) совпадает с соответствующим
эталонным CSV» — механически не выполняется: сравниваются рамочная
таблица и CSV. Ни один шаг M3 не задаёт `.mode csv` / `.headers on` и не
запускает клиент как `sqlite3 -csv -header`. Проверено поиском по
`program/M3/step-*.md`: совпадений `.mode` — ноль.

Затронуто: `step-06.md` (6 эталонов A1), `step-07.md` (2 эталона A3),
`step-10.md`, `step-11.md`.

**B3 — не назван рабочий каталог.** `step-01.md` даёт `sqlite3 m3.db
".read schema.sql"` без указания, откуда запускать. `schema.sql` и
`seed.sql` лежат в `program/M3/data/`. Из корня репозитория команда не
работает.

**B4 — не описан повторный прогон.** `.read schema.sql` поверх уже
существующей `m3.db` падает на `table already exists`. Шаг не говорит ни
удалить файл базы, ни что делать при повторе. В прогоне это обошли
`Remove-Item m3.db` — команда добавлена агентом, в тексте шага её нет.

**B5 — скрытая зависимость критерия от данных.** Критерий `step-01.md`,
1.5: «сломанный запрос возвращает 13 строк — ровно все `completed`-заказы
независимо от суммы». Это верно только потому, что ни один
`pending`-заказ не проходит `amount > 500`: их два, 111 (390.0) и 116
(260.0). В шаге это не названо. Если будущая правка `seed.sql` добавит
`pending` с суммой выше 500, критерий сломается, и причина будет
неочевидна.

**B6 — проверенная и снятая гипотеза.** `sqlite3.exe -csv > файл` на
Windows даёт двойной возврат каретки. Обнаружено 2026-07-31 при
подготовке данных для Части 2, воспроизведено прогоном:

```
$ sqlite3.exe -csv -header m3.db "SELECT order_id, amount FROM orders
  ORDER BY order_id LIMIT 2;" > b6_test.csv
$ od -c b6_test.csv
o r d e r _ i d , a m o u n t \r \r \n 1 0 1 , 1 2 0 0 . 0 \r \r \n ...
```

В CSV-режиме SQLite сам завершает строку `\r\n`, а stdout в текстовом
режиме Windows переводит `\n` ещё раз — получается `\r\r\n`.

Область поражения ограничена, это проверено, а не предположено:

- Восемь эталонов `program/M3/data/a*.csv` чистые — CRLF, ноль двойных
  `\r` (сгенерированы Python, не редиректом).
- `compare_csv.py` двойной `\r` переживает: `csv.reader` с `newline=""`,
  `.strip()` на ячейках и отсев пустых строк его снимают — проверено
  запуском на битом файле, разбор корректный.

**Дефекта нет — репозиторий это уже знает и лечит.** Проверено после
находки, до записи вывода:

- Восемь эталонов `program/M3/data/a*.csv` чистые — CRLF, ноль двойных
  `\r` (сгенерированы Python, не редиректом).
- `compare_csv.py` двойной `\r` переживает: `csv.reader` с `newline=""`,
  `.strip()` на ячейках и отсев пустых строк его снимают — проверено
  запуском на битом файле, разбор корректный.
- Явление описано в docstring `compare_csv.py` (пункт 2 «Перевод
  строки») со ссылкой на решение 13, и оттуда выведено правило шага.
- Правило действительно есть в тексте: `step-01.md` строки 167–175
  предписывают `.once <файл>` и прямо запрещают перенаправление `>`;
  `step-06.md:162` и `step-07.md:158` на него ссылаются;
  `data/README.md:88` повторяет.

Запись оставлена как след проверки: гипотеза о дефекте выдвигалась и
была отклонена прогоном. Собственная ошибка агента (данные для Части 2
были сгенерированы редиректом, а не `.once`, и вышли с `\r\r\n`) —
подтверждение того, что правило шага нужное.

### 1.5. Фактическая цена установки клиента — измерена

Страница [Precompiled Binaries for Windows](https://www.sqlite.org/download.html)
(fetch 2026-07-30) отдаёт `sqlite-tools-win-x64-3530400.zip`, 6 557 792
байта. Распаковка даёт четыре `.exe` плоско, без вложенной папки и без

| Файл | Байт |
|---|---|
| `sqlite3.exe` | 4 022 272 |
| `sqldiff.exe` | 3 243 520 |
| `sqlite3_analyzer.exe` | 4 484 608 |
| `sqlite3_rsync.exe` | 3 179 520 |

Прав администратора не требуется. `PATH` дописан на уровне пользователя
(`[Environment]::SetEnvironmentVariable("Path", …, "User")`), новое окно
терминала подхватывает. Это тот же путь без админских прав, который
решение 19 п. 2 выбрало для PostgreSQL.

Итого честная цена: **скачать 6.6 МБ, распаковать, дописать `PATH`** —
не «0 действий», но и не установка сервера.

### 2.2. Находка P1 — автоопределение кодировки зависит от содержимого файла; C2 ломается тихо

**Что сделано.** Два CSV выгружены из `m3.db` в `D:\m4-gate\`
(вне репозитория) запросами:

```sql
SELECT customer_id, name, city FROM customers ORDER BY customer_id;
SELECT order_id, customer_id, status, amount,
       substr(order_date,1,7) AS period_ym
FROM orders ORDER BY order_id;
```

Оба записаны в UTF-8 **без BOM**. `customers.csv` содержит украинскую
кириллицу (`Коваленко О.`, `Київ`), `orders.csv` — только латиницу и
цифры.

**Что показал Power BI** в окне предпросмотра «Текстовый или CSV-файл»:

| Файл | Содержимое | «Источник файла», подставлен автоматически |
|---|---|---|
| `customers.csv` | кириллица UTF-8 | `65001: Юникод (UTF-8)` — кириллица отображена верно |
| `orders.csv` | только ASCII | **`1251: Кириллическая (Windows)`** |

Разделитель в обоих случаях определён верно («Запятая»). Определение
типов — «на основе первых 200 строк».

**Почему это дефект, а не курьёз.** Кодировка не определяется заново при
каждом обновлении — она зашивается в код запроса на момент импорта.
Файл, состоящий сегодня только из ASCII, получает 1251. Как только в
очередной выгрузке появится кириллица — название категории, город,
контрагент, статус — тот же запрос прочитает её как 1251 и молча
испортит, без единого сообщения об ошибке.

Это прямое попадание в умение C2, критерий которого сформулирован в
части 1 blueprint как «подмена исходного файла на файл следующего месяца
+ Refresh → 0 ошибок, 0 ручных правок». Он провалится, и провалится
тихо — худший из режимов отказа.

**Следствие для M4.** Шаг обязан требовать явной установки `65001` в
«Источнике файла», а не полагаться на автоопределение. Это не оговорка в
1.6, а часть задания и часть критерия. Отдельно: данные программы
кириллические начиная с M2 (решение 17), то есть проблема не
гипотетическая для этого домена.

### 2.3. Находка P2 — смягчение решения 22 по датам не работает

**Что утверждает решение 22.** Единственная документированная
невоспроизводимость экспорта — формат `datetime` по локали машины. И
далее дословно: «Снимается конструкцией задания: в экспортируемых
визуалах столбцов `datetime` нет, период выражается текстом `YYYY-MM`
или целочисленным ключом даты».

**Что произошло.** Колонка `period_ym` выгружена ровно так, как
предписывает решение — текстом `2026-05`. В предпросмотре Power BI она
показана как **`01.05.2026`**: определение типов распознало строку
`2026-05` как дату и отформатировало по локали машины.

**Почему это важно.** Смягчение из решения 22 само по себе не
срабатывает. «Выразить период текстом» недостаточно — Power BI
преобразует такой текст в дату автоматически, и на выходе получается
ровно то, чего решение избегало: значение, зависящее от локали. Чтобы
смягчение работало, шаг обязан дополнительно **явно задать типу колонки
«Текст»** в Power Query и не полагаться на то, что текст останется
текстом.

Формулировку решения 22 нужно поправить: не «период выражается текстом»,
а «период выражается текстом **и тип колонки принудительно установлен в
Текст**, потому что автоопределение типов превращает `YYYY-MM` в дату».

### 2.4. Остальные находки Части 2

**P3 — родного коннектора к SQLite нет; к PostgreSQL есть.** Поиск
`SQLite` в полном диалоге «Получить данные» не даёт ничего. В списке баз
данных присутствуют: SQL Server, SQL Server Analysis Services, MySQL,
**PostgreSQL**, SQL, SQL Azure, Azure Synapse Analytics, Azure для
PostgreSQL, MongoDB Atlas SQL.

Проектное следствие для M4, лучше исходного замысла: M3 заканчивается
переносом данных на PostgreSQL (`step-09.md`), значит M4 подключается к
той же базе `m3` **напрямую**, а не к промежуточному CSV. Тогда критерий
C1 («числа сходятся с эталонным SQL») сверяет визуал и эталонный запрос
на одних и тех же данных, без экспортной прослойки. Путь через CSV
остаётся только там, где нужен именно навык импорта файла (C2).

**P4 — признак установленности из решения 22 ложноотрицателен для
Store-версии.** Решение 22 фиксирует отсутствие Power BI по трём
признакам, один из которых — ключ реестра `HKLM:\SOFTWARE\Microsoft\
Microsoft Power BI Desktop`. У установленной Store-версии этого ключа
нет. Проверять надо `Get-AppxPackage *PowerBI*`.

**P5 — PBIP и TMDL всё ещё preview; дополнительно включён PBIR.** В
разделе «Функции в предварительной версии» версии 2.156.951.0
присутствуют и включены:

- «Параметр сохранения проекта Power BI (PBIP)» — включено
- «└ Сохранить семантическую модель в формате TMDL» — включено
- «└ Хранение отчетов с использованием расширенного формата метаданных
  (PBIR)» — включено

Первые два подтверждают слой 2 решения 22 (обе функции по-прежнему
preview, обе требуют ручного включения). Третьего решение 22 не знало:
при включённом PBIR текстом сохраняется не только семантическая модель,
но и сам отчёт — включая типы визуалов. Это потенциально переводит часть
слоя 3 («нет 3D, пончиков и двойных осей» — P3, критерий 13) из чеклиста
автора в машинную проверку. **Не проверено прогоном** — гипотеза,
требующая подтверждения на сохранённом проекте.

**P6 — локаль интерфейса.** Интерфейс русифицированный. Решение 21 п. 4
требует «одна локаль»; значит шаги M4 обязаны ссылаться на русские
названия пунктов меню, и это надо объявить в `program/M4/step-00.md`
явно, иначе шаг будет называть английские подписи, которых автор не
увидит.

**P7 — денежная колонка молча уходит в текст при русской локали.**
Прогон 2026-07-31. Импорт `D:\m4-gate\orders.csv` (значения `amount` вида
`1200.0`) штатным коннектором «Текст или CSV» без ручных правок дал в
M-коде:

```
Table.TransformColumnTypes(#"Повышенные заголовки", {{"order_id",
Int64.Type}, {"customer_id", Int64.Type}, {"status", type text},
{"amount", type text}, {"period_ym", type date}}, "ru")
```

Культура `"ru"` подставлена автоматически. В ней десятичный разделитель —
запятая, поэтому `1200.0` не распознаётся как число, и Power Query кладёт
колонку в **текст**, не выдавая ни ошибки, ни предупреждения. Мера
`SUM(orders[amount])` на такой модели не считается.

Тяжелее P2: P2 портит подпись периода, P7 обнуляет само число. Критерии
C1–C4 решения 22 («числа визуала сходятся с эталонным SQL») на модели по
умолчанию невыполнимы — эталон 8600.00 нечем сверять, пока тип не
исправлен вручную. Обход, проверенный прогоном: культура `"en-US"` в
`Table.TransformColumnTypes` — после замены `amount` встал числом,
`period_ym` текстом `2026-05`.

Источник расхождения — не CSV: SQLite пишет `1200.0` с точкой всегда.
Значит любой CSV-эталон проекта, попав в Power BI на машине автора,
получает эту проблему. M4 обязан задавать культуру явно.

**P8 — явный выбор кодировки в GUI не всегда попадает в файл проекта.**
Расширение P1. Прогон 2026-07-31, два файла, одинаковые действия («Источник
файла» = `65001` в диалоге импорта):

| Файл | Содержимое | `Encoding` в `Csv.Document` |
|---|---|---|
| `orders.csv` | чистый ASCII | **параметр отсутствует** |
| `customers.csv` | кириллица | `Encoding = 65001` |

Power BI записывает `Encoding` только когда выбранное значение расходится
с автоопределением. На ASCII-файле выбор совпал с определением, параметр
не записан — кодировка в проекте **не зафиксирована**. Следствие: файл,

### 2.7. Находка P9 — экспортируются форматные строки, и C1 на них падает

Ответ на вопрос задания «форматные строки против сырых чисел»: в экспорт
попадает **отформатированное значение**, а не сырое число. `2480,00` —
это `formatString` меры (2 разряда) плюс десятичная запятая русской
локали, а не `2480`.

Следствие проверено запуском, а не рассуждением. Эталон, сгенерированный
из `m3.db` с тем же заголовком и порядком строк, против `export1.csv`:

```

РАСХОЖДЕНИЕ в строке 1, колонка 'Total Completed':
  у вас '2480,00', в эталоне '2480.00'
  ваша строка:   Київ,2480,00
  строка эталона: Київ,2480.00
код возврата: 1
```

Данные совпадают полностью. Расходится запись числа. `same_value()` в
`compare_csv.py` сначала сравнивает строки, потом пробует `float(got)`;
`float("2480,00")` бросает `ValueError`, и функция возвращает `False`.

BOM скрипт переживает (`utf-8-sig`), кавычки тоже (разбор по правилам
CSV), кириллица прочиталась верно. Ломает ровно десятичная запятая.

Значит **C1 нельзя сдать существующим `compare_csv.py`**. Три выхода, в
порядке предпочтения:

1. Научить `same_value()` заменять запятую на точку перед `float()` —
   правка одной строки, лечит и десятичный разделитель, и любой другой
   визуал M4. Риск: в CSV с запятой-разделителем значение `1 234,56`
   пришло бы в кавычках с неразрывным пробелом — нужна и чистка пробелов.
2. Требовать в шаге M4 задавать мере формат без разрядов и сверять целые
   числа. Сужает задание.
3. Отдельный скрипт сверки для M4. Дублирование, хуже первого.

Побочно: строка «Всего» (grand total) визуала **в экспорт не попала** —
экспортируются только строки данных. Критерий, сверяющий итог, должен
получать его суммированием строк, а не искать в файле.

**Закрыто 2026-07-31 первым выходом из трёх.** `normalize_number()` в
`compare_csv.py` снимает разделитель разрядов (обычный, неразрывный и
узкий неразрывный пробел) и десятичную запятую перед `float()`. Тот же
вызов, что печатал расхождение:

```

СОВПАДАЕТ: 5 строк, 2 колонок, расхождение 0.
код возврата: 0
```

Восемь эталонных пар M3 прогнаны после правки — числа в них с точкой, и
правка их не задела: 8 из 8 `СОВПАДАЕТ`, расхождений 0. Смягчение

### 2.9. TMDL пишет только отклонения от умолчания — проверено прогоном

Гипотеза из 2.8 не оставлена предположением. В GUI изменено одно
свойство связи: «Направление перекрестной фильтрации» с «Простое» на
**«Оба»**, проект пересохранён тем же `.pbip`. `relationships.tmdl` стал:

```
relationship AutoDetected_32360c20-c06a-42dd-b478-fa006adf4b99
	crossFilteringBehavior: bothDirections
	fromColumn: orders.customer_id
	toColumn: customers.customer_id
```

Строка появилась ровно там и ровно тогда, когда значение разошлось с
умолчанием: файл — 174 байта.

После проверки значение возвращено на «Простое» и проект пересохранён.
`relationships.tmdl` вернулся к исходным трём строкам, 133 байта, следов
отменённой правки не осталось — TMDL не копит мусор от откатов.

**Правило для критериев M4, выведенное прогоном.** Свойство при значении
по умолчанию в TMDL отсутствует. Значит проверка формулируется как
утверждение об отсутствии:

- «в `relationships.tmdl` нет строки `crossFilteringBehavior:`» —
  равносильно «направление фильтрации одинарное»;
- «нет строк `fromCardinality:` / `toCardinality:`» — равносильно
  «многие-к-одному»;
- «нет строки `isActive: false`» — равносильно «связь активна».

Формулировка «убедись, что строка `crossFilteringBehavior: oneDirection`
присутствует» была бы невыполнима: такой строки не бывает.

Та же логика распространяется на всю модель, и это надо держать в уме при
написании C3/C4: отсутствие строки в TMDL — не признак того, что автор
чего-то не сделал, а признак значения по умолчанию.

### 2.11. Разбор: P1 и P8 — противоречие или разные вещи (прогон 2026-07-31)

Вопрос задан после свода: P1 утверждает, что кодировка **зашивается в код
запроса** на момент импорта; P8 — что кодировка **в файле проекта не
фиксируется**. Разобрано прогоном, а не сопоставлением формулировок.

**Прогон.** Прочитан с диска сохранённый проект гейта,
`D:\m4-gate\pbi\gate.SemanticModel\definition\tables\*.tmdl` — то самое
место, где живёт M-код (2.8). Обе таблицы, дословно, раздел `partition`:

```

  [Delimiter = ",", Columns = 3, Encoding = 65001, QuoteStyle = QuoteStyle.Csv])
Источник = Csv.Document(File.Contents("D:\m4-gate\orders.csv"),
  [Delimiter = ",", Columns = 5, Encoding = 65001, QuoteStyle = QuoteStyle.Csv])
```

`orders.csv` — чистый ASCII, и `Encoding = 65001` у него **есть**. Это
третий факт, которого до сих пор не было ни в P1, ни в P8.

**Ответ: противоречия между P1 и P8 нет — они про разные моменты.**
P1 про то, **когда и из чего** принимается решение о кодировке (в диалоге
импорта, по содержимому файла). P8 про то, **попадает ли принятое решение
в текст проекта**. Одно не отменяет другого.

**Противоречие есть внутри самого P8 — его объяснение опровергается
измерением P1.** P8 объясняет наблюдение правилом «Power BI записывает
`Encoding` только когда выбранное значение расходится с автоопределением».
Подставляем измеренное:

| Файл | Автоопределение (P1) | Выбрано автором (P8) | Правило P8 предсказывает | Измерено (P8) |
|---|---|---|---|---|
| `orders.csv` | 1251 | 65001 | расходится → **записать** | параметра нет |
| `customers.csv` | 65001 | 65001 | совпало → **не писать** | `Encoding = 65001` |

Правило предсказало противоположное по обеим строкам. Оно вычёркивается;
измерение P8 остаётся в силе. Механизм, по которому GUI решает писать
параметр или нет, гейтом **не установлен** и для конструкции M4 не нужен —
см. ниже.

**Что установлено измерением, без гипотез о механизме:**

1. ASCII-файл в диалоге импорта получает `1251` (P1).
2. Явный выбор `65001` в диалоге для ASCII-файла в проект **не попал** (P8).
   Прибить кодировку через GUI нельзя.
3. `Encoding = 65001`, вписанный в M-код **руками**, лежит в `.tmdl` и
   переживает сохранение проекта — для обоих файлов, включая ASCII
   (прогон выше). Это и есть рабочий путь.

**Что осталось непроверенным и почему это больше не важно.** Открыт один
вопрос: переопределяется ли кодировка при Refresh у запроса, в котором
параметра `Encoding` нет вовсе. Ответ требует GUI автора: подменить
`orders.csv` на файл с кириллицей и нажать «Обновить». Прогон не
выполнялся, гипотеза не выдвигается. На конструкцию M4 ответ не влияет:
шаг всё равно обязан вписывать `Encoding` руками — по P7 (культура) и по
P8 (`QuoteStyle`) это уже требуется, и вопрос «что делает запрос без
параметра» в задании не возникает. Он остаётся значимым ровно для одной
вещи — понимания, насколько тихо ломается модель, собранная кликами.

**Следствие для C2 — критерий в текущей формулировке не работает, и
причина тяжелее, чем предполагал вопрос.** Формулировка части 1
blueprint — «подмена исходного файла на файл следующего месяца + Refresh →
