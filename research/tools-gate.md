### 1.2. Что произошло на первой команде модуля

### 1.3. Дефекты

**B1 — блокер. Модуль неисполним с первой команды; инструкции по
установке клиента нет ни в одном файле репозитория.**

Ни `program/M3/step-01.md`, ни `program/M3/step-00.md` не содержат
указаний, как получить консольный клиент. `step-00.md`, раздел
«SQL-движок», утверждает обратное: «модуль начинается на SQLite (**0
действий по установке**…)». Источник ошибки — решение 15
`design/decisions.md`: «M3 начинается на SQLite: ставится в 0 действий
(**входит в стандартную библиотеку Python**, файл базы — обычный файл)».

Утверждение верно для **библиотеки** `sqlite3` из стандартной поставки
Python — ею пользуются скрипты программы. Шаги M3 написаны против
**консольного клиента** `sqlite3`. Это разные вещи, и клиент в поставку
Python не входит. Проверено прогоном (1.2).

Затронуто: решение 15 (формулировка «0 действий»), `step-00.md` раздел
«SQL-движок», `step-01.md` раздел 1.3.

**B2 — критерий сверки с эталонным CSV невыполним из коробки.**

Клиент 3.53.4 по умолчанию печатает результат рамками с заголовками:

```
╭──────────┬───────────┬────────╮
│ order_id │  status   │ amount │
╞══════════╪═══════════╪════════╡
│      111 │ pending   │  390.0 │
╰──────────┴───────────┴────────╯
```

Эталоны модуля — CSV с запятой и заголовком
(`program/M3/data/a1_task1_running_total.csv`):

```
customer_id,order_id,order_date,amount,running_total
1,101,2026-05-02,1200.0,1200.0
```

Критерий `step-06.md`, 1.5 — «вывод собственного запроса **построчно**
(все колонки, все строки, тот же порядок) совпадает с соответствующим
эталонным CSV» — механически не выполняется: сравниваются рамочная
таблица и CSV. Ни один шаг M3 не задаёт `.mode csv` / `.headers on` и не
запускает клиент как `sqlite3 -csv -header`. Проверено поиском по
`program/M3/step-*.md`: совпадений `.mode` — ноль.

Затронуто: `step-06.md` (6 эталонов A1), `step-07.md` (2 эталона A3),
`step-10.md`, `step-11.md`.

**B3 — не назван рабочий каталог.** `step-01.md` даёт `sqlite3 m3.db
".read schema.sql"` без указания, откуда запускать. `schema.sql` и
`seed.sql` лежат в `program/M3/data/`. Из корня репозитория команда не
работает.

**B4 — не описан повторный прогон.** `.read schema.sql` поверх уже
существующей `m3.db` падает на `table already exists`. Шаг не говорит ни
удалить файл базы, ни что делать при повторе. В прогоне это обошли
`Remove-Item m3.db` — команда добавлена агентом, в тексте шага её нет.

**B5 — скрытая зависимость критерия от данных.** Критерий `step-01.md`,
1.5: «сломанный запрос возвращает 13 строк — ровно все `completed`-заказы
независимо от суммы». Это верно только потому, что ни один
`pending`-заказ не проходит `amount > 500`: их два, 111 (390.0) и 116
(260.0). В шаге это не названо. Если будущая правка `seed.sql` добавит
`pending` с суммой выше 500, критерий сломается, и причина будет
неочевидна.

### 1.5. Фактическая цена установки клиента — измерена

Страница [Precompiled Binaries for Windows](https://www.sqlite.org/download.html)
(fetch 2026-07-30) отдаёт `sqlite-tools-win-x64-3530400.zip`, 6 557 792
байта. Распаковка даёт четыре `.exe` плоско, без вложенной папки и без
установщика:

| Файл | Байт |
|---|---|
| `sqlite3.exe` | 4 022 272 |
| `sqldiff.exe` | 3 243 520 |
| `sqlite3_analyzer.exe` | 4 484 608 |
| `sqlite3_rsync.exe` | 3 179 520 |

Прав администратора не требуется. `PATH` дописан на уровне пользователя
(`[Environment]::SetEnvironmentVariable("Path", …, "User")`), новое окно
терминала подхватывает. Это тот же путь без админских прав, который
решение 19 п. 2 выбрало для PostgreSQL.

Итого честная цена: **скачать 6.6 МБ, распаковать, дописать `PATH`** —
не «0 действий», но и не установка сервера.

`PATH` на машине автора содержит `D:\sqlite-tools` дважды: команда
дописывания выполнена повторно. Ни на что не влияет, но стоит вычистить.

### 2.2. Находка P1 — автоопределение кодировки зависит от содержимого файла; C2 ломается тихо

**Что сделано.** Два CSV выгружены из `m3.db` в `D:\m4-gate\`
(вне репозитория) запросами:

```sql
SELECT customer_id, name, city FROM customers ORDER BY customer_id;
SELECT order_id, customer_id, status, amount,
       substr(order_date,1,7) AS period_ym
FROM orders ORDER BY order_id;
```

Оба записаны в UTF-8 **без BOM**. `customers.csv` содержит украинскую
кириллицу (`Коваленко О.`, `Київ`), `orders.csv` — только латиницу и
цифры.

**Что показал Power BI** в окне предпросмотра «Текстовый или CSV-файл»:

| Файл | Содержимое | «Источник файла», подставлен автоматически |
|---|---|---|
| `customers.csv` | кириллица UTF-8 | `65001: Юникод (UTF-8)` — кириллица отображена верно |
| `orders.csv` | только ASCII | **`1251: Кириллическая (Windows)`** |

Разделитель в обоих случаях определён верно («Запятая»). Определение
типов — «на основе первых 200 строк».

**Почему это дефект, а не курьёз.** Кодировка не определяется заново при
каждом обновлении — она зашивается в код запроса на момент импорта.
Файл, состоящий сегодня только из ASCII, получает 1251. Как только в
очередной выгрузке появится кириллица — название категории, город,
контрагент, статус — тот же запрос прочитает её как 1251 и молча
испортит, без единого сообщения об ошибке.

Это прямое попадание в умение C2, критерий которого сформулирован в
части 1 blueprint как «подмена исходного файла на файл следующего месяца
+ Refresh → 0 ошибок, 0 ручных правок». Он провалится, и провалится
тихо — худший из режимов отказа.

**Следствие для M4.** Шаг обязан требовать явной установки `65001` в
«Источнике файла», а не полагаться на автоопределение. Это не оговорка в
1.6, а часть задания и часть критерия. Отдельно: данные программы
кириллические начиная с M2 (решение 17), то есть проблема не
гипотетическая для этого домена.

### 2.3. Находка P2 — смягчение решения 22 по датам не работает

**Что утверждает решение 22.** Единственная документированная
невоспроизводимость экспорта — формат `datetime` по локали машины. И
далее дословно: «Снимается конструкцией задания: в экспортируемых
визуалах столбцов `datetime` нет, период выражается текстом `YYYY-MM`
или целочисленным ключом даты».

**Что произошло.** Колонка `period_ym` выгружена ровно так, как
предписывает решение — текстом `2026-05`. В предпросмотре Power BI она
показана как **`01.05.2026`**: определение типов распознало строку
`2026-05` как дату и отформатировало по локали машины.

**Почему это важно.** Смягчение из решения 22 само по себе не
срабатывает. «Выразить период текстом» недостаточно — Power BI
преобразует такой текст в дату автоматически, и на выходе получается
ровно то, чего решение избегало: значение, зависящее от локали. Чтобы
смягчение работало, шаг обязан дополнительно **явно задать типу колонки
«Текст»** в Power Query и не полагаться на то, что текст останется
текстом.

Формулировку решения 22 нужно поправить: не «период выражается текстом»,
а «период выражается текстом **и тип колонки принудительно установлен в
Текст**, потому что автоопределение типов превращает `YYYY-MM` в дату».

### 2.4. Побочные находки

**P3 — родного коннектора к SQLite нет; к PostgreSQL есть.** Поиск
`SQLite` в полном диалоге «Получить данные» не даёт ничего. В списке баз
данных присутствуют: SQL Server, SQL Server Analysis Services, MySQL,
**PostgreSQL**, SQL, SQL Azure, Azure Synapse Analytics, Azure для
PostgreSQL, MongoDB Atlas SQL.

Проектное следствие для M4, лучше исходного замысла: M3 заканчивается
переносом данных на PostgreSQL (`step-09.md`), значит M4 подключается к
той же базе `m3` **напрямую**, а не к промежуточному CSV. Тогда критерий
C1 («числа сходятся с эталонным SQL») сверяет визуал и эталонный запрос
на одних и тех же данных, без экспортной прослойки. Путь через CSV
остаётся только там, где нужен именно навык импорта файла (C2).

**P4 — признак установленности из решения 22 ложноотрицателен для
Store-версии.** Решение 22 фиксирует отсутствие Power BI по трём
признакам, один из которых — ключ реестра `HKLM:\SOFTWARE\Microsoft\
Microsoft Power BI Desktop`. У установленной Store-версии этого ключа
нет. Проверять надо `Get-AppxPackage *PowerBI*`.

**P5 — PBIP и TMDL всё ещё preview; дополнительно включён PBIR.** В
разделе «Функции в предварительной версии» версии 2.156.951.0
присутствуют и включены:

- «Параметр сохранения проекта Power BI (PBIP)» — включено
- «└ Сохранить семантическую модель в формате TMDL» — включено
- «└ Хранение отчетов с использованием расширенного формата метаданных
  (PBIR)» — включено

Первые два подтверждают слой 2 решения 22 (обе функции по-прежнему
preview, обе требуют ручного включения). Третьего решение 22 не знало:
при включённом PBIR текстом сохраняется не только семантическая модель,
но и сам отчёт — включая типы визуалов. Это потенциально переводит часть
слоя 3 («нет 3D, пончиков и двойных осей» — P3, критерий 13) из чеклиста
автора в машинную проверку. **Не проверено прогоном** — гипотеза,
требующая подтверждения на сохранённом проекте.

**P6 — локаль интерфейса.** Интерфейс русифицированный. Решение 21 п. 4
требует «одна локаль»; значит шаги M4 обязаны ссылаться на русские
названия пунктов меню, и это надо объявить в `program/M4/step-00.md`
явно, иначе шаг будет называть английские подписи, которых автор не
увидит.

## 3. Где остановились и что делать первым делом

Остановка — на **шаге 2.4**: Power BI Desktop открыт, оба CSV загружены
в модель, дефекты P1 и P2 зафиксированы, но не устранены в самом файле
проекта.

**Первое действие завтра — доделать шаг 2.4** (это правка модели в GUI,
не правка репозитория):

1. Главная → **Преобразовать данные**.
2. Запрос `orders` → «Примененные шаги» → шестерёнка у шага
   **«Источник»** → «Источник файла» = **`65001: Юникод (UTF-8)`**.
3. Там же заголовок колонки **`period_ym`** → Главная → Тип данных →
   **Текст** → «Заменить текущее преобразование».
4. Запрос `customers` → убедиться, что в «Источнике» стоит `65001`.
5. Главная → **Закрыть и применить**.
6. Записать: число строк в каждой таблице и вид `period_ym` (ожидается
   `2026-05`, а не `01.05.2026`).

**Дальше по плану Части 2, в этом порядке:**

7. Представление модели → связь `customers[customer_id]` →
   `orders[customer_id]`. Записать кардинальность и направление
   фильтрации, которые Power BI подставил сам.
8. Мера на таблице `orders`:
   `Total Completed = CALCULATE(SUM(orders[amount]), orders[status] = "completed")`.
   Эталон уже есть и посчитан прогоном — `program/M3/step-00.md`,
   раздел «Схема»: `SUM(orders.amount) WHERE status='completed'` =
   **8600.00**. Это и есть проверка двойного авторства формулы.
9. Штатный визуал «Таблица»: `customers[city]` + мера. Задать явную
   сортировку.
10. Экспорт данных визуала в CSV **дважды подряд**, без изменений между
    экспортами, в два разных файла — это пункт 4 нулевой проверки.
11. Сохранить как **Power BI Project (`.pbip`)** в короткий путь
    (ограничение 260 символов, решение 22).
12. После этого агент читает файлы с диска и закрывает пункты 1–6
    таблицы 2.5: кодировку и разделитель экспорта, наличие «Applied
    filters», побайтовое сравнение двух экспортов, порядок строк,
    `definition/relationships.tmdl` и `definition/tables/*.tmdl`. Плюс
    проверяет гипотезу P5 по PBIR.

**Исходные данные для продолжения** (созданы агентом, вне репозитория,
воспроизводятся запросами из 2.2):

- `D:\m4-gate\customers.csv` — 497 байт, UTF-8 без BOM, 12 строк + заголовок
- `D:\m4-gate\orders.csv` — 655 байт, ASCII, 19 строк + заголовок
