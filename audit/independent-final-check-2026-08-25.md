## 4.1. Два из трёх скриптов приёмки блока «Выход» падают

Прогон `check_cv.py` на **эталонном резюме самой программы**

Прогон `check_portfolio.py` на эталонном портфолио той же папки:

```
[FAIL] P2: карточка не ссылается ни на один существующий файл
[FAIL] P4: карточка не ссылается ни на один существующий файл
[FAIL] P5: карточка не ссылается ни на один существующий файл
НЕ СОШЛОСЬ. Шаг не закрыт.
```

**Механизм.** `check_cv.py` вытаскивает из резюме все пути вида
`program\...` регулярным выражением `PATH_TOKEN` и требует, чтобы каждый
файл существовал (`if (ROOT / rel).exists()`, строка 169; то же в 208 для
раздела «Английский»). Решение 53 переименовало десять эталонных CSV в
`.enc` — существовать они перестали. Комментарий в самом скрипте (строки
75–78) в качестве примера пути приводит
`program\P1\data\ref_by_store.csv`: файл, который скрипт был написан
находить, теперь не находится.

**Атрибуция проверена, не предположена.** `git show 7915404:program/P1/data/ref_by_store.csv`
отдаёт файл — до решения 53 он существовал открытым; эталонное резюме
цитировало три из закрытых файлов и тогда, и сейчас (`git show` даёт 3
вхождения). До решения 53 обе проверки проходили.

**Почему это важнее, чем выглядит.** Блок «Выход» — 8–11 ч и последнее,
что делается перед первым откликом. `check_cv.py` — механизм, который
держит главное обещание портфолио: ни одной строки резюме без файла за
ней. Сегодня он отказывает на заведомо верном резюме, и у человека
остаётся два выхода: перестать доверять проверке или переписать резюме
так, чтобы оно ссылалось на другие файлы. Оба хуже, чем было.

**Почему это не поймали.** `check_consistency.py` не запускает ни одного
из `check_*.py`, которыми проверяются шаги: `grep -c "check_cv\|check_portfolio\|check_search"`
по нему даёт **0**. Сквозная проверка репозитория зелёная и после
поломки. Это дефект самого механизма контроля, а не только этого случая.
