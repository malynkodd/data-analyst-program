## 2. Git — нарушение процесса, не разово

```
$ git status --short          → пусто, дерево чистое
$ git log origin/master..master --oneline
06a99b1 Решение 57: тёмная тема app/ …
7b5fac8 Дерево: раскрытие модуля чинится; тёмная тема пересобрана …
580f30d .claude/settings.json: плагин frontend-design включён
03d48fc Решение 56: редизайн app/ …
```

`HANDOFF.md`, раздел 3: «`git push` в конце каждой сессии — обязателен,
он не делается автоматически». Со вчерашнего финального аудита (который
сам заканчивается строкой «`git push` сделан») этому правилу не следовали
уже дважды подряд.

Отдельно, не про репозиторий, а про среду: в `.git/` лежит `index.lock`
нулевого размера с сегодняшней меткой времени. `git status`/`git log`
работают несмотря на него — не блокирует. Убрать его из-под этой сессии
не получилось (`rm`: `Operation not permitted` — похоже на ограничение
самого моста Cowork↔папка, а не на повреждение репозитория: файл мой же
по владельцу, но не удаляется). Если следующая сессия упрётся в `fatal:
Unable to create '.git/index.lock'`, дело в этом файле — убрать его
может только процесс с правом записи на саму папку на диске автора.

## 3. Единственный `[FAIL]` сегодняшнего прогона — не дефект программы

```
[FAIL] M3: a7_task3_full_outer.csv на состоянии базы step-14.md:
       RIGHT and FULL OUTER JOINs are not currently supported
```

Причина — версия SQLite **этой песочницы** (`sqlite3` Python-модуль тянет
системную `libsqlite3 3.37.2`, Ubuntu 22.04), а не программы: `FULL OUTER
JOIN` появился в SQLite 3.39 (2022). Сборка автора — 3.45.1 (решение 55,
раздел 0, уже разбирала ровно этот вопрос и закрыла его прогоном на
настоящей версии). Проверено заново: страница загрузки sqlite.org сегодня
отдаёт 3.53.4 — читатель, который качает клиент по ссылке из
`M3/step-01.md` сейчас, получит версию значительно новее порога. Риска
для читателя нет; для этой среды — есть, и его стоит держать в уме при
следующих прогонах `check_consistency.py` из песочницы, а не только для
M3.
