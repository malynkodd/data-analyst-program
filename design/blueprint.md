## 3.3. Выбор домена — когда

**Домен выбирается в конце месяца 1 (этап 1), доменный пакет собирается
на этапе 5.**

Формулировка [Г, 0.3] «домен выбирается на шаге 1» относится к ступени
карьеры (до первой работы), а не к учебному модулю. Проектное уточнение:
**выбор** делается рано, **сборка пакета** — после ядра. Причина: если домен
известен с первого месяца, проекты P1–P4 используют данные с доменной
окраской, и к этапу 5 у читателя уже есть 4 артефакта в одной отрасли, а
не разрозненный набор. Если бы выбор делался в конце, портфолио осталось
бы нейтральным, а домен — приклеенным сбоку.

Цена решения: смена домена после этапа 3 обесценивает часть проектов.
Поэтому выбор сопровождается упражнением на 2 ч — разметить 30 украинских
вакансий по домену и посмотреть, в каком из трёх есть junior-позиции.

# ЧАСТЬ 5. ПОРТФОЛИО — 6 ПРОЕКТОВ

Общие правила для всех шести:

- **Три проекта из шести стоят на реальных публичных данных (P3, P4, P6),
  три — на синтетических (P1, P2, P5).** Синтетические генерируются
  автором программы со **специфи­кацией
  встроенных дефектов**. Причина: [К, §3.3.5] — «портфолио, состоящее из
  общеизвестного учебного кейса, — это анти-портфолио»; capstone-кейсы
  Google (Cyclistic, Bellabeat) «рекрутеры узнают с первого взгляда»
  [К, §4]. Титаников, айрисов, Cyclistic и Bellabeat нет ни в одном из шести.
- **Почему не все шесть синтетические.** Синтетика решает две задачи:
  неузнаваемость датасета и механическую проверяемость acceptance criteria
  (эталон известен точно). Третью она не решает — портфолио обязано
  показать, что человек работал с реальностью, а полностью выдуманные
  данные читаются как курсовая. Отсюда разделение по типу задачи:
  - **Реальные публичные данные — P3, P4, P6.** Это проекты, ценность
    которых как раз в неудобстве источника: кириллица не в UTF-8,
    менявшаяся между периодами схема выгрузки, API с лимитами и
    пагинацией, справочники с дублями написания, несходящиеся ключи между
    источниками. Такие дефекты нельзя выдумать убедительно — их можно
    только встретить.
  - **Синтетические данные — P1, P2, P5.** Здесь реальных открытых данных
    не существует в принципе: P2 требует событий на уровне пользователя,
    P5 — кредитов на уровне договора. Ни то, ни другое не публикуется
    никем. P1 остаётся синтетическим по другой причине: он первый, и на
    старте цена запутанного источника выше пользы от его реалистичности.
- **Как реальные данные уживаются с механической проверяемостью.**
  Публичный источник меняется, и требование «сойтись с эталоном» ломается
  через месяц. Решение: автор фиксирует **снапшот** — файл, дата выгрузки,
  контрольная сумма sha256; acceptance criteria считаются по снапшоту.
  Отдельным пунктом в каждый «реальный» проект добавлено требование
  выгрузить данные заново и **объяснить расхождение со снапшотом**. Это не
  обход проблемы, а превращение её в упражнение: расхождение свежей
  выгрузки с зафиксированной — ровно то, с чем аналитик имеет дело на
  работе, и чего нет ни в одной из 14 программ [К, §3.2].
- **Требование к источнику для P3, P4, P6** (отбор конкретных датасетов —
  работа Фазы 2): публичный доступ без логина; выгрузка воспроизводима
  (прямая ссылка или открытый API); ≥50 тыс. строк хотя бы у одного из
  источников проекта; в данных присутствуют ≥3 дефекта из списка —
  несогласованные справочники, смена схемы между периодами, кириллица не в
  UTF-8, пропуски в календарных рядах, дубли ключа, разные единицы
  измерения.
- **Гейт источников пройден 29–30.07.2026** — `research/sources-gate.md`,
  правило 3 CLAUDE.md. Проверялась доступность, не пригодность конкретного
  датасета. Ни один проект на синтетику не возвращается.

  **Проверены и годны:** Prozorro API (`public-api.prozorro.gov.ua`,
  ленты tenders / contracts / plans / agreements, 1 000 записей за 4 с),
  API НБУ (`bank.gov.ua/NBUStatService`, курсовой ряд 1 827 записей за
  5 лет), Держстат SDMX (`stat.gov.ua/sdmx/...`, 118 потоков, один поток —
  249 898 наблюдений), data.gov.ua (CKAN API, 36 911 датасетов, включая
  ЄДР юрлиц). **Годен с оговоркой:** ukrstat.gov.ua — источник дефектов
  (windows-1251, .xls и .xlsx вперемешку), но не объёма; API НАЗК — потолок
  выдачи 10 000 записей на запрос.

  **Вычеркнуты из списка кандидатов части 5:** «открытый бюджет»
  (openbudget.gov.ua) и Є-Дата (spending.gov.ua / edata.gov.ua). Причина не
  в том, что они мертвы: с точек выхода **вне Украины** оба отдают 403
  (Akamai), а проверка из украинского браузера 29.07.2026 показала, что
  порталы живы и наполнены (openbudget — исполнение бюджета за янв–июнь
  2026, spending — транзакции за 28.07.2026). То же у tax.gov.ua,
  mof.gov.ua, ua.energy. Основание для исключения — требование
  воспроизводимости: учащийся может находиться вне Украины, а
  автоматическая проверка ссылок при поддержке программы (правило 3
  CLAUDE.md) для этих доменов невозможна в принципе. Статус: **«доступно
  из UA, недоступно извне»** — резерв, а не опора.

- **Робот данные не качает.** `robots.txt` на data.gov.ua отдельными
  блоками запрещает ClaudeBot, GPTBot, CCBot и другие AI-краулеры при
  общем `User-agent: * → Allow: /`. Скрипту учащегося на своём User-Agent
  ходить можно. Отсюда правило для всей Фазы 2: **шаг даёт инструкцию по
  выгрузке (URL, параметры, ожидаемый размер, sha256, число строк), а сам
  файл выгружает учащийся.** Формулировка «данные лежат в репозитории»
  допустима только для синтетики P1, P2, P5.

- **Привязка проектов к источникам** (из `sources-gate.md`, раскладка
  подтверждена фактическими ответами API):

  | Проект | Источники | Что даёт |
  |---|---|---|
  | P3 | Prozorro API + API НБУ | тендеры категории + курсовой ряд с пропусками в выходные |
  | P4 | Prozorro API (tenders + contracts, разная периодичность) + ЄДР с data.gov.ua + API НБУ | три источника, три формата: JSON / ZIP-выгрузка / JSON |
  | P6 | Держстат SDMX + API НБУ (+ ukrstat.gov.ua как слой грязных Excel) | 249 898 наблюдений внешней торговли; SDMX-XML, а не CSV |

- **Вопрос по P4 решён** (решение 35, `design/decisions.md`, 2026-08-22):
  ЄДР юрлиц на data.gov.ua — датасет из нескольких ZIP разных реестров, не
  один файл на выбор по объёму; нужный — **`UO.zip`** (юридические лица,
  326 858 701 байт на 2026-08-22), потому что P4 сверяет контрагентов по
  ЄДРПОУ, а этот код — только у юрлиц (`FOP.zip`, реестр физлиц-
  предпринимателей, 471 037 214 байт, использует другой идентификатор и в
  P4 не нужен). Загружается **полностью**, не подмножеством. К P4
  учащийся подходит, освоив таблицы (M2), SQL (M3) и Python (M5), то есть
  инструмент для таких объёмов у него есть, но опыта — нет. Выбор в пользу
  полного архива (вместо подмножества по категории Prozorro) сделан
  сознательно: это осознанное упражнение «данные не влезают в Excel, и это
  нормально» с явным шагом по потоковому чтению и отбору нужных колонок —
  честнее и ближе к рабочей реальности, чем подготовленный срез, ценой
  риска упереться в диск и память конкретной машины (фальсификатор — в
  решении 35).

- Кандидат, не прошедший проверку, заменяется; если ни один не проходит,
  проект уходит на синтетику, и это фиксируется в файле, а не заминается.
  Замена уже сделана один раз: роль «данных о публичных финансах» вместо
  openbudget закрывает Prozorro API, роль «официальной статистики» вместо
  «публикаций Держстату» — Держстат SDMX, оказавшийся полноценным API, а не
  набором Excel-файлов.
- У каждого проекта есть **заказчик** — роль с интересом, а не «датасет».
- В каждом есть решение, у которого нет единственно правильного ответа,
  и обе трактовки меняют вывод. Это и есть предмет защиты.
- Acceptance criteria публикуются до задания (решение 3).
- Артефакт — репозиторий + отчёт, а не скриншот.

## P1. «Какая точка худшая» — сеть из 12 магазинов

**Заказчик:** операционный директор розничной сети. Вопрос дословно:
«Какую точку закрывать первой».
**Инструменты:** M2 (Sheets/Excel) + M3 (SQL для сверки). **Часы: 10–14.**

**Неоднозначность в данных:** три точки сменили внутренний ID в середине
периода (та же точка выглядит как две); возвраты записаны отрицательными
суммами в той же колонке, что и продажи; даты в двух форматах; у двух
точек отсутствуют данные за 6 недель ремонта.

**Решение, которое нужно принять и защитить:** считать ли возвраты в
выручку и как склеить сменившиеся ID. При включении возвратов худшая точка
— одна, при исключении — другая. Вопрос ремонтных недель (исключать
период или считать нулевую выручку) переворачивает третье место.

**Acceptance criteria (12):**
1. Executive summary ≤200 слов, содержит ≥1 число и ≥1 рекомендацию к действию.
2. Названа ровно одна точка как ответ на вопрос заказчика.
3. Указано, при каком альтернативном определении выручки ответ меняется, и на какую точку.
4. Все 3 смены ID найдены и перечислены с датами.
5. Правило склейки ID записано одной строкой и применено ко всем случаям.
6. Периоды ремонта обработаны явно; выбранный способ назван и обоснован в ≤2 предложениях.
7. Контрольная сумма: `сумма выручки по точкам = сумма по всему файлу`, расхождение 0.
8. Результат в таблице сходится с контрольным SQL-запросом; запрос приложен.
9. ≥4 диаграммы, у каждой подписаны обе оси и указаны единицы измерения.
10. Раздел «что в данных было сломано и как я это обработал» содержит ≥3 конкретных дефекта с решением.
11. Названы 2 причины, по которым вывод может быть неверным.
12. Нет ни одного графика, который не отвечает на вопрос заказчика.

## P2. «Почему упала конверсия в первую оплату»

**Заказчик:** продуктовый менеджер сервиса подписки.
**Инструменты:** M3 (SQL, ядро проекта) + M10 (Git). **Часы: 16–20.**

**Неоднозначность в данных:** события платежей дублируются из-за retry
платёжного шлюза; часть пользователей имеет два аккаунта с одним email;
трафик пришёл из трёх каналов с разной долей в разные месяцы.

**Решение:** определение конверсии — когорта по дате регистрации или по
дате оплаты. Первое даёт падение, второе — рост. Плюс встроенный
симпсоновский парадокс: конверсия выросла в каждом из трёх каналов
по отдельности и упала в целом.

**Acceptance criteria (14):**
1. Определение конверсии зафиксировано письменно **до** первого запроса (проверяется по истории коммитов).
2. Обе трактовки (когорта регистрации / когорта оплаты) посчитаны, обе цифры в отчёте.
3. Явно назван парадокс: конверсия по каналам и в целом ведёт себя противоположно.
4. Указана причина парадокса — изменение долей каналов; доли приведены таблицей.
5. Дубли платежей найдены; их число названо; правило дедупликации записано одной строкой.
6. Двойные аккаунты найдены; их число названо; влияние на результат посчитано отдельно.
7. Каждая цифра из выводов воспроизводится приложенным SQL-запросом, результат сходится.
8. Использована ≥1 оконная функция и ≥1 CTE.
9. Retention-таблица по 12 когортам сходится с эталоном.
10. Репозиторий: ветка → PR → merge; в истории нет коммитов «fix»/«update»; есть `.gitignore`.
11. Executive summary ≤200 слов с ≥1 числом и ≥1 рекомендацией.
12. Названы 2 причины, по которым вывод может быть неверным.
13. ≥4 диаграммы с подписанными осями и единицами.
14. Человек не из data, прочитав только summary, за 60 секунд называет рекомендацию.

7. Пропуски курса в выходные обработаны явно; способ назван.
8. Неполный период помечен на самом экране визуально, а не в сноске.
9. Подмена исходного файла на файл следующего периода + Refresh: 0 ошибок, 0 ручных правок.

## P4. «Три источника, один объект» — данные, которые не сходятся

**Заказчик:** аналитик отраслевой ассоциации (или журналист-расследователь
— роль с интересом, а не абстрактный «бизнес»). Вопрос: «Сколько на самом
деле потрачено по этой категории за три года и кто десять крупнейших
получателей».
**Инструменты:** M5 (Python) + M6 + M7 (BigQuery). **Часы: 24–30.**

**Данные: реальные публичные**, зафиксированные снапшотом. Три источника
разных форматов и разной периодичности: **Prozorro API** (ленты `tenders` и
`contracts`) + **ЄДР юрлиц с data.gov.ua** (ZIP, сверка контрагентов по
ЄДРПОУ) + **API НБУ** (курсовой ряд). Все три прошли гейт 29–30.07.2026
[`sources-gate.md`, §1–3]. **Файл и объём решены** (решение 35,

лиц, 326 858 701 байт на 2026-08-22, а не `FOP.zip` (реестр ФОП, другая
персона, другой идентификатор) и не подмножество.

**Неоднозначность в данных** (требования к отбираемым источникам):
три выгрузки разных форматов (csv с кириллицей не в UTF-8, xlsx с
многострочной шапкой, json или API с пагинацией); один и тот же
контрагент назван по-разному в разных источниках, а часть записей

## P5. «Портфель просрочки» — доменный проект (fintech)

**Заказчик:** риск-менеджер микрофинансовой компании. Вопрос: «Мы ужесточили

## P6. «Заказчик передумал» — сквозной capstone

**Заказчик:** директор регионального бизнеса. На третий день меняет
вопрос: вместо «где по нашей категории растёт спрос» спрашивает «что
будет, если мы поднимем цену на 15%».
**Инструменты:** всё. **Часы: 22–28.**

**Данные: реальные публичные**, зафиксированные снапшотом. Источники:
**Держстат SDMX + API НБУ**, при необходимости третьим слоем —
ukrstat.gov.ua (старый портал, windows-1251). Прошли гейт 29–30.07.2026
[`sources-gate.md`, §4–5]; конкретный поток SDMX выбирается на Фазе 2.
Учесть заранее: SDMX отдаёт XML и игнорирует `Accept: ...+csv`, а
крупнейший поток возвращает 500 — резать по ключу. Реальный источник здесь
принципиален: публичные данные **действительно** собирались не под вопрос
читателя, поэтому ответ «на эту часть ответить нельзя» получается
настоящим, а не подстроенным автором.

**Неоднозначность в данных:** тот же датасет должен ответить на новый
вопрос, для которого он не собирался. Данных о ценовой чувствительности в
публичном источнике нет вообще — и это не дефект выгрузки, а свойство
источника.

**Решение:** сказать, на какую часть нового вопроса данные ответить не
могут, и что вместо этого можно посчитать. Это единственный проект, где
правильный ответ содержит слово «нельзя» — и его нужно защитить.
Обоснование механики: «автономность / самостоятельная постановка задач» —
слепая зона [М], «повторяющаяся формулировка в вакансиях middle+».

**Acceptance criteria (15):**

3. Названо, какие данные нужно было бы собрать, и как именно.

8. Executive summary ≤200 слов с ≥1 числом и ≥1 рекомендацией.

## 6.5. Объём практики — вторая величина рядом с часами

Заведено 2026-08-24 (решение 47). Метрика заимствована прямо: Karpov
публикует **830+ задач** вместо «X часов контента» [К, 3.4, п. 9] —
«часы измеряют, сколько ты потратил; задачи измеряют, сколько ты
сделал». Для программы, где 19 из 24 часовых вилок не калиброваны и
калибровать их нечем до первого прохождения, это единственная величина
объёма, которая **проверяется без прохождения** — пересчётом файлов.

Часы она не заменяет и не отменяет: часы отвечают на вопрос «сколько это
займёт», задания — «сколько здесь работы». Расхождение между ними и есть
дефект 7 внешнего аудита (`audit/product-audit-2026-08-23.md`).
